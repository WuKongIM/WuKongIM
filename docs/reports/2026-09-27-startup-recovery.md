# 300 万用户重启恢复验证

## 范围与结论状态

结论：本轮实现和验证满足进入代码审查及合并的条件，建议合并后在反馈环境灰度验证；尚未实际合并或发布。流式恢复、checkpoint 复用和恢复中断重试均已通过完整规模验证，新写入试验未观察到吞吐退化。

本实验复现了基线版本在 2 GiB 内存限制下恢复时被 OOM 杀死；不能据此认定反馈现场只有这一种原因。没有现场日志、资源曲线或 profile。4 GiB 基线能够启动，未复现无限等待。

## 环境与方法

- 基线提交：`64f73d99b3b0cb8960d40825f76053f5a0000dbd`；候选位于 `codex/startup-recovery`。
- macOS ARM64 主机、Docker Desktop Linux VM；产品和测试驱动为 Linux ARM64 静态二进制。镜像的 Ubuntu 用户空间标记为 AMD64，不能将本次结果标为 AMD64 产品性能。
- 每例限制 4 CPU，`GOMAXPROCS=4`，真实 cgroup `memory.max=2/4 GiB`、`memory.swap.max=0`。VM 为 8 GiB / 10 CPU。
- 256 个 hash slot、1 个物理 Slot 的单节点集群。公开 `/bench/v1/users/tokens` 导入 3,000,000 个用户及对应 APP 设备；该入口使用与 `/user/token` 相同的集群用户用例。
- 导入完成后，通过 Manager 创建真实快照，再写入一个快照之后的凭据，正常停止并冻结种子。每次升级/基线对比复制停止后的不透明目录树，不修改存储内容。快照约 381 MB，包含 6,000,002 条用户/设备记录。
- 每个普通重启用例通过 Manager 分页核对全部 3,000,000 个 UID 恰好出现一次、设备数量和 token 存在性；另用 WKProto 验证 256 个分布样本及快照之后的凭据。并未逐个验证全部 token 的具体值。
- 每 20 ms 采样产品 `/proc` RSS、I/O、CPU；cgroup 峰值另含驱动和页缓存。普通耗时案例启用 GC trace，没有 CPU profile 插桩。克隆及页缓存条件不代表物理冷盘启动。

## 已完成的常规重启对比

| 版本 | 内存限制 | 结果 | ready 耗时 | 产品 RSS 峰值 | 全量记录核对 |
| --- | --- | --- | ---: | ---: | ---: |
| 基线 | 2 GiB | OOM，未 ready | 1.54 秒时退出 | 1,975 MiB | 未进行 |
| 基线 | 4 GiB | 成功 | 5.91 秒 | 2,322 MiB | 3,000,000 |
| 流式恢复 | 2 GiB | 成功 | 6.50 秒 | 553 MiB | 3,000,000 |
| 流式恢复 | 4 GiB | 成功 | 3.80 秒 | 572 MiB | 3,000,000 |

成功用例均完成 257 次凭据验证。基线 2 GiB 的 cgroup `oom_kill` 从 0 增为 1。单次 ready 时间受 Controller/Slot 选举和缓存影响，不应用这些单次差异宣称稳定的启动延迟百分比收益。

流式安装主要解决峰值内存问题，仍然重写快照：ready 前进程写入约 451 MiB，基线约 453 MiB。checkpoint 的目标是在证明有效时省掉这部分重写。

## 正确性与故障验证

- 快照完整校验在修改数据之前完成；初始安装保留 pending 标记，批次持久化后才推进进度，完成时原子发布 watermark 并删除标记。
- checkpoint 同时校验数据库实例及物理写序列、集群/节点/Slot/ownership、快照内容、准确的 Raft 日志和配置边界；不能单凭 applied index 跳过快照。
- 业务写入与证书在同一批次。未分类写入会删除全部证书并推进进程内 epoch，旧内存证明不能被后续提交重新认证。已知且不重叠的 Slot 写入只失效自身证书；检测到无效启动 seal 时，先持久化清除所有旧证书，包括未打开的 Slot。大批次采用 Pebble 公开的 batch representation 校验分配的序列号。
- 已通过：1/12 个物理 Slot 连续重启、三节点整集群重启、旧产品写入后回退并认证新凭据、迁入第四节点后整集群重启及当前副本的 checkpoint 复用。
- 已通过对应数据库/Slot/集群包测试及针对证书、旧写入者、失效 epoch、大批次、流式恢复的集成与竞争检查。具体命令和日志在证据目录。
- 原有动态 onboarding/send 测试在迁移前以 `ReasonAuthFail` 失败，基线与候选相同；不能把该测试算作迁移通过。新增场景使用显式创建的凭据验证迁移后重启。
- 无可认证证书且没有快照的旧数据库保留原有 watermark 恢复语义，在真实 compaction 建立锚点之前不产生新证书。这里没有承诺修复任意无快照离线修改。

大规模故障测试在观察到 `snapshot_install` 后发送 SIGSTOP，确认尚未出现安装完成事件，再发送 SIGKILL，随后完整重启和核对。该事件在范围删除及 pending 标记持久化之后发出；记录数可能仍为 0，不应描述成已观察到某个非零数据批次完成。现有存储层崩溃测试另覆盖分批安装中断。

## 定位过程中发现的问题

第一版 checkpoint 的大规模测试主动失败：Pebble 将大批次接管为 flushable 后，会清空调用方的批次表示，提交后直接读取 `Batch.SeqNum()` 会误报序列号变化。小数据未触发此路径。先用大批次集成测试复现，再改为保留公开批次表示并验证真正分配的序列号，相关回归及 race 检查通过。原失败报告保留，不能与修复后的结果混为一组。

## Profile 和恢复日志

启动 CPU 归因使用完全相同的诊断专用 Go overlay，分别构建基线和候选：从程序 init 到驱动观察到 ready，最多两分钟，输出终止原因和耗时收据。插桩不进入产品源码。profile-only 用例不承担全量数据验收；常规测试另外采集的 ready 后 profile 不能当作启动归因。

基线启动 profile 共 3.76 秒 CPU 样本，`runtime.memmove` 占 flat 21.28%；Slot 恢复调用链和后台压缩均有明显占用。这与代码中的完整快照加载、复制、解码和重写路径一致。它不能单独量化生产环境收益。

checkpoint 复用的启动 profile 共 0.71 秒 CPU 样本，主要热点转为 CRC、SHA-256 和系统调用；两份 profile 均确认由观察到 ready 终止，而非触发两分钟上限。该诊断用例没有进行全量 inventory，不能替代上表的普通验收例。

INFO 事件为 `slot.recovery.progress`，阶段边界即时打印，同阶段限频五秒。字段包含 node/Slot、阶段、快照 index、字节/记录计数、可用时的百分比、累计耗时以及 checkpoint 回退原因。日志不含 UID、token 或记录内容。`complete` 表示启动时已提交日志恢复完成，不等同于整个服务已经 ready。

## 提交 PR 前的独立复审

规范与需求两个方向分别审核，并由主代理检查持久化和异常路径；详情见
[复审记录](2026-09-27-startup-recovery-review.md)。修复了多 Slot 首次升级／无快照
邻居造成的证书连锁失效，以及旧版本写入后未打开 Slot 的旧证书可能在后续
reseal 后恢复可用的边界。迁移维护、重叠 ownership 和未知写入继续全局失效。

上面的 2/4 GiB、profile 和写吞吐数值对应已记录哈希的 checkpoint-v2，不能
当作每次后续源码调整的重新测量。复审后的二进制、2 GiB 三百万用户复测、
十二 Slot 旧版升级及混合无快照场景记录在配套 JSON 的 `post_review` 字段。
前期并发编译下出现过十秒首次就绪超时；复跑还暴露 HTTP 就绪早于网关监听、
动态节点早于种子监听的测试时序问题。测试已显式等待相应协议入口和种子
就绪，失败输出保留，只有最终通过的执行计为通过证据。

最终交付二进制的 2 GiB 复测如下，三例均核对全部 300 万记录并通过 257 次认证：

| 路径 | ready | 恢复阶段 | RSS 峰值 |
| --- | ---: | ---: | ---: |
| 首次升级 | 28.30 秒 | 13.820 秒 | 465.8 MiB |
| 再次启动复用 | 5.70 秒 | 0.238 秒 | 144.2 MiB |
| 中断后重试 | 4.21 秒 | 1.690 秒 | 451.8 MiB |

首次升级这次观察到 28.30 秒 ready、13.82 秒恢复；该例与宿主 E2E 并发执行，
没有完成独立耗时归因，不据此宣称稳定的首次升级延迟。复用检查点仍跳过快照
安装，恢复阶段约 0.238 秒；全量重写的首次升级和中断重试继续保留。
