# 本地三节点归因与随机发送者修复 — 2026-09-21

本轮发现并修复了压测场景的一个实际执行错误：`random_online` 被接受，但群聊运行时缺少该分支，始终选择第一个在线成员。该问题改变发送者分布，必须修复后才能声称覆盖随机发送者；尚无证据证明它就是云上约 194ms SENDACK P99 的主因。

逐轮匿名指标、二进制与原始报告校验值、测量阶段内的剖析窗口和退出记录见 [机器可读证据](assets/benchmark-local-attribution-2026-09-21.json)。

## 修复与回归证据

基于 `725626f331d9438d81cca7ad36f70a36030d9628`，新增 worker 到真实 workload 的回归测试，分别以种子 42、42、43 连续发送 128 条消息。修复前所有消息均来自 `bench-u-0`，不同种子的序列完全相同，测试失败。

修复将既有 `run.random_seed` 传入群聊 workload，并由种子、逻辑群索引、全局消息索引生成每次发送的伪随机选择。调度器选择发送者键和实际 SEND 调用使用同一计算；没有共享随机状态、全局锁或随调用顺序推进的随机序列。给定相同顺序的候选在线成员，重复执行、并发乱序和流量分片保持选择一致。改变候选成员集合仍会改变结果。

修复后测试验证相同种子重放相同序列、不同种子改变序列、四个成员均被选中；并发分片测试覆盖倒序调度、不同群、空成员及单成员情况。既有 first-online、round-robin、weighted-80/20 行为仍由原有测试覆盖。该改动修复压测器执行口径，没有改变服务端分布式通信实现。

历史六轮云上场景虽写了 `random_online`，实际是每群固定一个发送者，共 100 个发送者，而非随机轮换 1,000 个在线成员。原始性能数值仍保留，但已更正覆盖范围；见 [跨 ECS 报告](2026-09-21-transport-cross-host-validation.md)。

## 本地实验方法

Apple M4、macOS arm64，Go 1.25.11，每个服务/压测进程设置 GOMAXPROCS=4。三个独立服务进程与一个 worker 同宿主运行，使用仓库静态三节点配置、独立新数据目录、loopback 链路，256 Hash Slots、12 个逻辑 Slot、三副本。服务端二进制在两轮中相同。

负载为 1,000 在线用户、100 个不重叠十人群、128B 消息、每群 5 SEND/s、总计 500 SEND/s、并发 64、seed 42、完整接收内容校验。每轮预热 10s、测量 60s、排空上限 30s。先执行修复前 worker 的探索轮；时间线复核发现其测量开始后的约 4s 与一组短回归测试重叠，因此不纳入下表性能对照。随后执行修复后的随机发送者轮次，再补跑完全隔离的显式 `first_online` 轮次。下表两轮使用同一修复版 worker 二进制，只改变发送者模式和运行 ID；群名哈希与领导者分布也可能不同，因此这不是统计上充分的性能改善对照。

每两秒采样 worker 状态和服务端指标；测量阶段开始至少 5s 后，同时采集四个进程各约 10s 的 CPU pprof，并保留前后 heap 样本。为观察 worker，仅在本地诊断构建中通过 Go overlay 给 CLI main 增加 loopback pprof 监听，未将诊断入口加入产品。两轮使用同一诊断入口；编译和测试没有与有效测量阶段重叠。

首次启动因证据目录过长而超过 Unix socket 路径限制，未进入压测；改用独立短 socket 目录。第二次在数据准备阶段超过 90s 轮询上限；后续把该协调器等待上限设为 180s，准备完成后再进入有效测量，没有改变服务端操作超时或业务门限。两次无效尝试单独保留，不能计入性能样本。

## 有效测量结果

| 指标 | 固定发送者（隔离补跑） | 随机发送者（修复后） |
|---|---:|---:|
| 计划 / 派发 / 成功发送 | 30,000 / 30,000 / 30,000 | 30,000 / 30,000 / 30,000 |
| 实际 SEND/s | 500 | 500 |
| 接收校验成功 | 270,000 | 270,000 |
| 连接、SENDACK、接收校验错误 | 0 | 0 |
| 原 SENDACK P99，ms | 100.672 | 100.793 |
| 调度滞后平均值，ms | 1.260 | 1.164 |
| SEND 提交平均值，ms | 0.00798 | 0.00736 |
| ACK 等待平均值，ms | 48.561 | 48.382 |
| 完整操作平均值，ms | 65.070 | 63.879 |

两轮新的固定桶 P99 上界相同：调度 20ms、提交 0.05ms、ACK 等待 100ms、完整操作 150ms。它们是诊断桶上界，不能与原精确 SENDACK 分位数直接相减，也不能相加得到完整路径。两轮没有窗口结束丢弃，busy-key 停顿计数为零。两种发送者模式的结果接近，本轮未观察到修复带来的业务性能改善。

## 验证与交付

- 回归测试先失败再修复，覆盖真实 worker 配置到发送路径，以及并发、重放和流量分片的一致性。
- `go test -race ./internal/bench/... ./pkg/bench/... ./cmd/wkcli/internal/bench ./cmd/wkcli/internal/benchmark -count=1` 全部通过，18 个包。
- `flow-doc-contracts` 命名检查通过，保留九项 FLOW 长度建议警告；索引已重新生成。
- 两轮真实进程、TCP 三节点实验均通过原有门限和完整接收校验；四进程 CPU profile 均在各自测量阶段内完成。探索轮证据另存，不用于下表比较。
- 停止所有压测进程后单独测量随机选择，三轮中位数约 21.68ns/op、16B/op、1 alloc/op。每消息调度与发送各选择一次，500 SEND/s 对应约 16KB/s 的选择器临时分配估算；该微基准不能替代整体容量评估。
- 所有本次启动的进程均已等待退出，独立临时 socket 目录和一次性节点数据库已清理；报告、日志、配置及剖析文件保留。前序阿里云租约保持已销毁状态，本轮没有采购。

前序分段计时报告曾把未加 `GOWORK=off` 的环境 Go 版本写成 1.25.0；实际测试命令由本模块 toolchain 选择 Go 1.25.11，现已更正。这不改变原测量数值。

## 结论边界与后续定位

本地有效基线达到全部计划发送量，未复现云上的发送缺口与约 194ms P99，因此不能宣称云上问题已经修复。同宿主、不同架构/存储、较短窗口和每种模式仅一轮，限制了外推。

探索轮与随机发送者轮次的 worker CPU 剖析均出现历史时延排序热点，`Registry.Collect` 分别占 CPU 样本的约 13.2% 和 15.8%（其中 `summarizeDurations` 分别约 11.7% 和 14.6%，不可与父项相加）。代码核对显示，`metrics.Registry.Collect` 在持有注册表互斥锁时调用 `summarizeDurations` 复制、排序旧 SLO 样本；快照请求可能阻塞同期指标写入。这是有证据的下一项排查对象，但尚未隔离其对 SENDACK P99 的贡献。新诊断直方图已使用固定桶，原 SLO 样本仍随运行增长。

服务端 CPU 样本主要落在系统调用及调度；三节点分配增量样本中，复制提议批次收集的直接分配约占 19%–21%，也保留为后续线索。CPU 剖析不测量全部阻塞时间，不能把 ACK 等待直接认定为服务端处理时间。探索轮 worker 前后 heap 分配差分没有可用增量，不能解释成零分配。

下一步应针对快照持锁排序构造并发写入的可复现阻塞测试，再比较排序移出锁区前后的写入延迟，并保留原有快照、精确分位数及并发安全语义；之后才适合做同条件长窗口与跨节点复测。本轮未购买云资源。

后续已完成 [指标快照锁竞争修复及 180 秒对照验证](2026-09-21-benchmark-snapshot-lock.md)。该改动缩短指标生产者的锁等待，保留原有精确分位数语义。
