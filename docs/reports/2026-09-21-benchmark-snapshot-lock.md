# 压测指标快照锁竞争修复 — 2026-09-21

本轮确认了压测器自身的可复现阻塞：`Registry.Collect` 在持有指标写入锁时排序全部旧 SLO 时延样本，快照请求会阻塞同期发送/接收指标写入。修复将一致性复制留在锁内，把昂贵聚合移到锁外；原精确分位数、样本保留方式和 SLO 判定不变。此前云上约 194ms P99 的归因仍需区分环境与压测器影响。

改动基于 `1141eb767d9e8a8055b14e129bcb3004770add24`。前序 CPU 剖析线索见 [本地三节点报告](2026-09-21-benchmark-local-attribution.md)。

原始微基准数值、业务统计、二进制与报告校验值、剖析窗口和退出记录见 [机器可读证据](assets/benchmark-snapshot-lock-2026-09-21.json)。

## 复现与设计

在保留原锁行为的内部聚合测试边界上，回归用例尝试在聚合期间写入指标，修复前立即失败：`snapshot aggregation blocks metric producers by holding the registry lock`。该用例不使用实际睡眠或依赖机器速度的时间门限；它验证聚合阶段生产者可以继续写入，且本次返回的计数、仪表、精确时延、诊断时延及错误样本仍属于写入前的同一次快照。

修复先在 `mu` 下复制所有指标族、复制原始时延到独立切片并汇总固定桶，再释放 `mu`，在私有切片上排序和聚合。原来聚合函数中的切片复制被移到捕获阶段，没有给每条历史时延额外复制两份。单独的 `collectMu` 保持快照收集串行，避免多个 HTTP 快照请求同时创建大工作副本；锁顺序固定为 `collectMu` 后 `mu`，生产者只获取 `mu`。

一次完整快照的工作副本大小仍与所有旧 SLO 样本总量相关；复制仍在短暂锁区，旧样本存储仍随运行时间增长。此修复不消除排序 CPU 成本，也不将全部旧时延改成固定桶近似统计。

并发回归还使用有剩余容量的原始切片，让两个收集者与一个写入者并发工作，核对所有快照的 count/sum 一致性、最终样本数和精确 P99，并断言注册表中的原始样本顺序没有被排序修改。

## 并发写入微基准

Apple M4 / macOS arm64，Go 1.25.11，GOMAXPROCS=4。固定伪随机时延历史，三种规模各执行 10 次快照、三轮；另一个 goroutine 每收到 1ms ticker 事件尝试一次计数器写入，只保留固定大小的统计。该基准使用 `integration` 标签，与真实业务测试分开执行。

下表为三轮中位数。“写入最大等待”是每轮所观测写入调用最大耗时的中位数，不是 P99，也不是所有计划 ticker 事件的延迟；基线长时间阻塞时 ticker 会合并事件，所以两版完成写入的样本数不同。

| 历史样本数 | 快照耗时，ms：前 → 后 | 写入最大等待，ms：前 → 后 |
|---|---:|---:|
| 30,000 | 2.166 → 2.231 | 4.869 → 0.00483 |
| 270,000 | 21.942 → 24.369 | 43.476 → 0.07033 |
| 810,000 | 71.616 → 74.904 | 145.026 → 0.349 |

81 万样本下，基线每轮最大写入等待范围为 143.2–147.6ms，修复后为 0.302–0.582ms。修复后三种规模的全部已观测写入均低于 1ms，但这不是对其他机器、更多指标族或更大样本量的保证。81 万样本每次快照仍分配约 6.49MB；新旧总量接近，修复版约 8 次分配。快照本身没有加速，生产者不再等整个排序完成是本轮确认的改善。

## 真实进程验证方法

沿用专用本地三节点实验，三个服务与一个 worker 同宿主、各设置 GOMAXPROCS=4，256 Hash Slots、12 个逻辑 Slot、三副本。两轮使用同一个服务端二进制，只替换 worker 的快照实现；显式指定 `first_online` 以复现此前云上版本的实际发送者策略。

每轮新进程、新数据目录、新运行 ID；1,000 在线用户、100 个互不重叠的十人群、128B 消息、500 SEND/s、并发 64、seed 42、完整接收校验。预热 10s、测量 180s、排空上限 30s。每两秒采集状态和服务指标；在测量开始至少 150s 后采集四个进程各 10s CPU profile，以覆盖历史样本已大量累积的阶段。worker 的 loopback pprof 入口只通过诊断构建 overlay 加入，不进入产品。

两轮的编译、单元测试和微基准均在真实测量开始前完成。不同运行 ID 会改变群名哈希及领导者分布，单轮前后对照不能排除机器波动；同宿主 macOS 数据也不能直接替代独立 Linux ECS 复测。

## 180 秒业务结果

| 指标 | 基线 | 修复后 |
|---|---:|---:|
| 计划 / 派发 / 成功发送 | 90,000 / 90,000 / 90,000 | 90,000 / 90,000 / 90,000 |
| 实际 SEND/s | 500 | 500 |
| 接收校验成功 | 810,000 | 810,000 |
| 连接、SENDACK、接收校验错误 | 0 | 0 |
| 原 SENDACK P99，ms | 125.121 | 104.915 |
| 原 SENDACK 均值，ms | 59.353 | 50.540 |
| 调度滞后均值，ms | 9.350 | 0.131 |
| ACK 等待均值，ms | 49.037 | 50.524 |
| 完整操作均值，ms | 74.988 | 65.795 |

两轮均通过既定门限，没有窗口结束丢弃；busy-key 停顿计数为 313 → 0，该计数不是等待时长。本轮精确 SENDACK P99 降低约 16.1%，平均调度滞后显著降低。诊断调度滞后 P99 桶上界为 50ms → 0.5ms，完整操作 P99 桶上界为 200ms → 150ms；这些桶上界不能与精确 SENDACK 分位数相减。

ACK 等待均值没有改善，仍在约 50ms；SEND 提交均值均约 7µs。结合确定性的锁行为回归、独立并发微基准和服务端二进制未改变，本轮证据支持改善来自压测器自身阻塞减少，不支持宣称网络或服务端处理变快。两轮均达到 500 SEND/s，也不能用于宣称更高容量。

末段 worker CPU profile：基线 10.15s 窗口中有 10.32 CPU 秒，`Collect` 累计 7.99 秒（77.4%）；修复版 10.12s 窗口中有 10.56 CPU 秒，`Collect` 累计 8.03 秒（76.0%），其中排序聚合 8.01 秒。父子累计项不可相加。排序仍然是 CPU 热点，修复并未降低这部分成本，符合预期。

## 验证与边界

- 聚合期间写入及快照一致性回归先失败、修复后通过；并发收集/追加测试验证切片归属、精确统计和原始顺序不变。
- `metrics`、`report`、`workload`、`worker` 四个直接相关包的 integration + race 全部通过。
- `flow-doc-contracts` 命名检查通过；FLOW 索引已更新，保留九项长度建议警告。
- 两轮真实 TCP 三节点实验均完成全部发送与接收校验；CPU profile 的开始/结束时刻均核对在测量阶段内。
- 本次所有进程已等待退出，临时 socket 目录和节点数据库已清理，报告、日志、配置及剖析证据保留。没有新增云资源。

已确认的是快照排序可制造百毫秒级指标写入停顿，以及本地对照中压测调度/记录耗时的改善。此前云上约 194ms P99 与发送缺口没有在本轮基线完整复现，不能认定它们已被全部解释或修复。后续应在使用修复版压测器的前提下复测跨 ECS；长时间、大样本运行仍需关注精确分位数排序 CPU 和旧样本保留内存。
