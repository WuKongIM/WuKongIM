# RPC 取消监听分配与锁范围实验

本轮保留一个窄优化：取消回调只捕获已有请求所有权对象，在 Go 1.25.11 Linux ARM64
隔离测量中，每次注册稳定减少 **32B**，分配次数不变。取消、队列和执行器规则不变。
**没有证明吞吐回退已修复，也不能断言完全没有小幅性能回退。**

另一个候选——出队后在锁外撤销监听——四对吞吐均下降，中位下降 **2.86%**，已撤回。
同时修复一个在未改动基线上也会失败的测试：版本化队列通知不能按到达顺序判断物理先后。

[机器可读证据](assets/rpc-cancel-watcher-local-2026-09-22.json)保存全部测量、源码、候选补丁、
构建哈希、测试失败与通过日志、前轮剖析表和清理回执。原始文件位于
`/Users/tt/.codex/visualizations/2026/09/22/rpc-cancel-detach`。
44个独立进程纯计时窗口共 **66,043,361次成功RPC**，错误与样本截断均为0。本轮未购买云资源。

## 证据与预测

沿用[前轮 pprof 与 trace](2026-09-22-rpc-small-local-queue-timer.md)：共享定时器版本中，
`watchQueue` 累计分配字节占33.79%，CPU占3.35%；`stopQueueWatch` CPU占1.45%；
`Enqueue` 累计归属78.00%的mutex等待剖析样本。它们是不同度量，嵌套占比不可相加，
mutex样本也不等于持锁耗时或总CPU占比，不能据此宣布根因。

依次检验三个预测：注册主要受分配影响；锁内撤销监听放大争用；其余工作/环境波动占主导。
首先测锁外撤销，再独立测试减少回调捕获。两项改动从未叠加计时。
标准库源码确认注册会创建回调取消对象，并按需初始化父上下文Done通道和子项表；
撤销会从父上下文移除子项。未添加服务循环、跳过取消、共享不同请求的预算或改写执行器。
本轮使用已有剖析与隔离分配测量，没有把剖析开销混入计时，也未新增服务端计时埋点。

## 方法与版本

- 基线 `a43ef2f99`，transport与 `5c293024c` 相同；复用前轮最终 shared-probe。
  固定旧客户端为 `68662c4c8`；预算开启验证使用前轮 current-probe（`5e159cd36`）。
  每个二进制哈希与共同探针源码均归档。根AGENTS源修订与SHA256已冻结，目标没有适用FLOW。
- Apple M4 Docker Desktop VM，Go1.25.11，Linux ARM64静态程序；Debian amd64仅提供rootfs，
  每窗输出确认程序架构arm64。构建使用 `GOWORK=off`、`-trimpath -buildvcs=false`。
- 客户端CPU0–3、服务端CPU4–7，各GOMAXPROCS=4、GOGC=100、3GiB上限；两个进程独立GC，
  同一网络命名空间loopback，不发布主机端口。Observer关闭，16预热连接、16调用者。
  服务并发64、队列4096项/64MiB、队列期限5s、执行期限30s、调用期限2s。
- 每窗10s，逐次校验完整响应，逐调用者保留样本计数和100万样本失败上限；
  RTT分位采用 `floor((n-1)*p)`。客户端B/call不能作为服务端分配。
- 构建、单元/竞态测试、隔离微基准均在纯RPC计时窗口之外运行。
  配对顺序交替；不同批次分别报告，不合并以抵消不利结果。这是本地工程验证，非云容量结论。

## 已拒绝：锁外撤销监听

候选只在 `nextRequest` 中先完成锁内FIFO移除，再解锁调用 `stopQueueWatch`。
注册、到期处理、Stop路径均保持原样。已经开始的回调通过 `queued=false` 放弃所有权。
该候选通过相关单元和集成竞态测试，但性能未达保留条件。

|服务端|吞吐中位 RPC/s|P99中位 ms|
|---|---:|---:|
|基线|212,574.23|0.451521|
|锁外撤销|206,495.98|0.456146|

四对吞吐变化 −3.64%、−2.08%、−1.65%、−0.55%；两组同二进制A/A变化 +0.14%、−0.46%。
候选P99中位变化 +1.02%。这些结果反对采用该改动，但不能精确解释其调度成本来源。

## 保留：只捕获请求所有权对象

原回调捕获请求对象、服务指针和原始上下文；后两者已经保存在请求对象中。
改为通过 `e.service`、`e.req.Context` 读取，注册与撤销位置完全不变。
请求对象不复用；这些字段在已启动回调可能访问期间保持不变。
此改动不在拒绝准入路径增加工作，不移除任何取消监听。

隔离基准实际调用 `watchQueue`/`stopQueueWatch`，复用请求对象等测试支架，区分
每次新建请求上下文与重复使用同一上下文。每种情况500ms，4轮，共24行前后测量。
原注册基准二进制包含已拒绝的出队候选，但被测方法与基线完全相同，基准不调用出队。
重复上下文仅用于区分首次初始化成本，不是合并请求上下文的实现建议。

|隔离场景|原 B/op → 新 B/op|分配次数/次|原 ns/op → 新 ns/op（中位）|
|---|---:|---:|---:|
|仅新建/取消请求上下文|96 → 96|2|98.66 → 96.34|
|新上下文并注册/撤销监听|640 → 608|8|405.05 → 391.75|
|已初始化上下文的注册/撤销|176 → 144|3|133.00 → 130.75|

四轮均复现32B节省。首次注册相对仅建上下文额外544B/6次分配，优化后512B/6次；
其中大部分仍是取消机制自身的初始化。此隔离差值不能直接当作完整RPC去掉监听能省的成本，
因为完整执行路径可能在其他位置触发同一个上下文的惰性初始化。

真实RPC结果如下，变化为各版本中位数之比；配对明细完整保留。

|场景|基线 RPC/s|仅捕获owner RPC/s|吞吐变化|P99变化|
|---|---:|---:|---:|---:|
|旧客户端64B，4对|216,995.38|216,052.67|-0.43%|-4.29%|
|预算开启64B，3对|214,266.01|212,493.51|-0.83%|-2.65%|
|预算开启65537B，首批3对|58,900.54|58,335.45|-0.96%|+0.42%|
|预算开启65537B，复测4对|55,503.88|56,024.20|+0.94%|-0.43%|

首批大载荷配对变化 +0.60%、−4.46%、−2.19%，触发额外复测；后续相反起始顺序的四对为
+2.91%、−0.16%、−1.46%、+2.66%，A/A为 +1.79%、−0.08%。初次下降没有稳定重现，
但不能忽略，也不能把各批次平均后宣称“没有回退”。小包配对同样混合正负。
只将此改动视为低复杂度、明确的分配字节优化，吞吐恢复仍未通过验收；原生x86跨主机性能未验证。

## 测试中发现的既有问题

`TestServiceObservesQueueAdmissionInflightAndTask` 原先按通知到达顺序检查队列修订号，
但Enqueue与pump在释放队列锁后发送通知，可以先收到出队通知。初次候选测试出现
`81..79`；未修改的main重复1000次也出现 `267..265` 等相同失败。
而且这个测试使用服务根上下文，本身不注册本轮修改的请求取消回调。

修正为依据载荷项数/字节识别入队与出队，检查恰好两个状态，并验证出队修订号高于入队。
仍能捕获错误物理顺序，不再把合法通知重排判成失败。修正后1000轮竞态重复通过。

最终候选验证（GOWORK=off、GOTOOLCHAIN=go1.25.11）：

- `go test ./pkg/transport/... -count=1 -timeout=2m` 通过。
- `go test -race -tags=integration ./pkg/transport/... -count=1 -timeout=4m` 通过。
- 通知测试 `-race -count=1000` 通过；修正前基线和候选的失败日志均保留。
- 网络预算/取消/断连语义 `TestNegotiated(Cancel|Deadline|ReadCanceled)`，集成竞态20轮通过。
- 队列期限 `TestQueue(Deadline|Expiry|Budget)`，集成竞态20轮通过。
- 24行隔离分配测量与44窗RPC的计数、错误、截断、哈希和正常清理状态均核验。

本轮没有增加永久吞吐阈值单测；本机变动不足以支撑可靠阈值。真实取消/所有权行为由已有
网络和队列测试覆盖，分配字节由归档基准验证。临时探针与微基准移出工作树，全部本轮容器清理。
已有buildkit及其他非本轮资源保持原样。

后续应优先检查首次注册触发的上下文初始化与完整入站请求生命周期的关系；
不要继续仅移动锁内外位置，也不要依据隔离基准就删除独立请求取消或预算语义。
