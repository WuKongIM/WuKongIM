本计划承接本地生命周期与准入隔离的负向结果，目标是在原生 x86 跨主机环境
复现 64B/16 并发回退，并区分客户端与服务端版本变化。当前只完成本地准备，
没有调用云厂商 API，没有新租约、报价或云测结果。

## 固定测试矩阵

| 客户端 | 服务端 | 用途 |
| --- | --- | --- |
| 原始 | 原始 | 同环境基线 |
| 当前 | 当前 | 复现整组变更后的差异 |
| 原始 | 当前 | 固定客户端，观察服务端变化 |
| 当前 | 原始 | 固定服务端，观察客户端变化与兼容回退 |

每组使用 64/4097/65537B、1/16 并发，五轮交错顺序，每项 10s，共 120 项，
纯计时窗口合计 20 分钟。实际执行还包含预热、进程重启、采样与证据归档。
使用 16 个预热连接、GOMAXPROCS=4、服务并发 64、队列 4096 项/64MiB、
执行超时 30s、当前服务排队预算 5s、调用超时 2s、Observer 关闭。
原始版本不支持的新限制不伪装成已启用。

探针的 `budgets=auto` 在支持的客户端启用协商；旧服务端走兼容回退。
输出中的 `request_budgets` 表示客户端配置，不能当作每次实际使用了 v2 帧的
证明。两种混合组合保留这一差异，不把它们解释成完全独立的加法成本。

逐次保存吞吐、平均 RTT、P50/P95/P99、错误和客户端分配，不只保存中位数。
保留原有 `floor((n-1)*p)` 分位数算法，避免混入统计方法变化。内容不一致、
错误、样本达到探针容量上限或进程提前终止会使该项失效；不可丢弃失败轮后
继续报告“全部通过”。正式计时关闭 profile 和其他工作负载。

## 双端诊断

正式矩阵后，对四种组合的 64B/65537B、16 并发另行采样，采样结果不参与
吞吐比较。CPU/allocs/mutex/block 与执行 trace 使用不同运行窗口：

- CPU 10s，mutex fraction 10，block rate 1ms；同时记录双端窗口和完成调用数。
- 执行 trace 3s，用于区分调度、同步和网络等待。记录双端时钟同步状态与
  采样起止时间，只比较可确认的重叠区间，不将不同进程的单调时钟直接相减。
- 每次诊断重启探针，保存准备阶段边界；累计分配/锁等待不能除以另一窗口
  的调用数。两端 P99 不能相减得到网络耗时，CPU/锁累计占比也不能直接当作
  吞吐损失比例。

采集 CPU 型号、架构、内核、Go 版本、实例规格、时钟偏差和进程 CPU/内存。
两台实测主机必须是相同 CPU 型号的原生 x86，使用同地域同可用区内网。
若时钟或主机不匹配，保留失败证据，不以本地模拟结果替代。
