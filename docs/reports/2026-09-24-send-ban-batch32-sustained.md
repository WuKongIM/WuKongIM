# 显式 batch32 配置的持续资格

状态：**失败**。四分钟诊断通过没有在本次 30 分钟目标中复现为持续稳定。
保持 5000 频道、4500 SEND/s、128 append workers，三个节点公开配置均
确认 128 gateway workers、131072 总队列、batch cap=32。默认配置未改。

## 观测与假设检验

- 节点 2 有一次、节点 3 有三次 `async_dispatch_queue_full` 关闭，均与
  相应 async_send admission full 计数一致；快照在测试清理之前获取。
- 权限 busy=0。追加路由峰值比例仅 0.4902，仍发生队列满关闭。因此
  “共享路由达到 512/512 是断连的必要条件”被本轮反证。
- 提前结束窗口 SENDACK/RECV P99=323/304ms，gateway dispatch wait
  P99.9 约 878ms、SEND handle P99.9 约 343ms；成功完成的分位数不能
  描述所有尚未完成的慢请求，也不能与其他提前失败窗口当成完整配对对照。
- 单节点堆峰值 356,924,360 bytes、compaction debt 峰值 468,896,842
  bytes、CPU 均值 415.34%。没有证明堆压力或 compaction 是直接根因。

较小批次降低了本轮观测到的并发峰值，却没有解决持续 EOF。不能据此
推荐该组合已满足 4500 SEND/s 的持续目标，也不能修改默认值或放宽
零拒绝、延迟、内存和持久化门槛。需要继续区分会话分片的突发预算、
最慢追加等待与当前同机三节点的存储尾延迟；目标机器信息已向用户询问。

功能证据保持有效：该完整配置的 gateway 禁令判定/完整历史、私聊与群聊
各 1200 条消息/ACK/接收顺序已通过。它们不替代本轮失败的持续资格。
后续三组同机对照单独比较固定 1200 SEND/s 下的 RPC、CPU 和延迟开销，
即使通过也不会自动清除这一 4500 SEND/s 持续失败。
