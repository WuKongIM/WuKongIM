# 30 分钟持续验证（调度延迟 / cgroup 限流观测版）：发送跑满，仅因权限读繁忙门槛失败

源码 `5939551d2`，harness `permission-soak-sched.test`。
负载 5000 频道、4500 SEND/s、cap32、30m，不注入故障。容器限制 8 CPU（`cpu.max 800000 100000`）。

## 结果

- 发送跑满 30 分钟：8100000 条消息全部送达；入口 4500.0/s，完成 4500.0/s。
- 没有 SENDACK 超时、没有 EOF、没有断连。
- SENDACK p50/p95/p99/max = 9 / 69 / 221 / 3947ms；RECV p99 = 199ms。
- `sendack_system_busy` = 12553（均已退避重试成功）。
- 失败断言：`permission admission busy = 16, want 0`（`permission_soak_test.go:830`）。
- 每分钟快照只有第 18 分钟（183）、第 23 分钟（29）有积压，下一分钟即归零。

## CPU 与调度

- 容器平均 CPU 约 590–665%（上限 800%）。整轮新增 cgroup 限流约 796 个周期、约 23.7s，
  每分钟 3–72 个周期；第 18 分钟积压时限流很少（5 个周期），第 23 分钟限流较多（72 个）。
- Go 调度延迟（`go_sched_latencies_seconds`，按直方图分桶精度）：

| 节点 | 调度次数 | 平均 | >0.92ms | >10.5ms | >117ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| node-1 | 83338407 | 6.9µs | 232712 | 5683 | 48 |
| node-2 | 88011498 | 7.5µs | 256404 | 9130 | 85 |
| node-3 | 81127855 | 6.4µs | 189390 | 6357 | 54 |

## 提交协调器

- 三节点请求耗时超过 1s 的一共 1 次（node-1 replica_foreground），没有超过 2.5s 的。
  前几轮的秒级协调器排队本轮没有出现。

## 结论

本轮 SENDACK 没有超时，协调器也没有秒级排队。调度延迟存在百毫秒级长尾，与 CPU 接近上限一致，
但本轮没有造成 5s 级卡顿。剩余失败是验收门槛：权限读准入繁忙 16 次，门槛要求 0 次。
SENDACK max 3.9s 的来源未确认；压测的 SENDACK 延迟从首次发送起算，包含 `ReasonSystemBusy`
退避重试的时间，可能来自重试链，尚未验证。

证据：`assets/send-ban-sched-20260929/`。

## 权限读准入繁忙分析（同一轮的失败诊断）

| 节点 | busy 次数 | busy 平均耗时 | 正常准入平均 | rpc 平均 | barrier 平均 | 调度延迟 >117ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| node-1 | 3 | 105.4ms | 0.014ms | 1.26ms | 0.64ms | 48 |
| node-2 | 9 | 120.0ms | 0.018ms | 1.23ms | 0.65ms | 85 |
| node-3 | 4 | 100.9ms | 0.010ms | 1.27ms | 0.60ms | 54 |

- 16 次 busy 的平均耗时都在 100–120ms，说明它们是排队等满 100ms 超时，而不是等待队列满后被立即拒绝。
- 正常情况下一个 envelope 只占许可约 1–2ms，16 个执行许可平均每秒可处理远超实际的约 3000 次。
  要让等待者 100ms 拿不到许可，16 个正在执行的 envelope 必须同时停住约 100ms。
- 调度延迟直方图分桶较粗（相邻边界 10.5ms、117ms），每节点有 48–85 次 goroutine 调度等待超过 117ms。
  busy 次数最多的 node-2，超过 117ms 的调度等待也最多。

推断（未验证）：busy 来自容器 CPU 接近上限时的秒级以下调度停顿，而不是权限读容量不足或代码缺陷。
现有数据是整轮累计值，没有时间戳，只有三个节点的排序一致，样本太少，不能确认因果。

## 降档对照：3000 SEND/s（同一二进制与 harness）

命令：`assets/send-ban-sched-20260929/sustained-30m-qps3000.command.json`，只把
`WK_E2E_MEDIUM_RECIPIENT_QPS` 从 4500 改为 3000，并去掉仅对旧 sync-window 二进制
有效的 `WK_SENDBAN_FLIGHT_DIR`。

| 指标 | 4500/s | 3000/s |
| --- | ---: | ---: |
| 结果 | FAIL（权限读繁忙 16，门槛 0） | PASS（1989.1s） |
| 消息 | 8100000 | 5400000 |
| 完成/s | 4500 | 3000.0 |
| SENDACK p50/p95/p99/max ms | 9 / 69 / 221 / 3947 | 6 / 14 / 31 / 998 |
| RECV p99 ms | - | 32 |
| 权限读繁忙 | 16 | 0 |
| `sendack_system_busy` | - | 0 |
| 容器平均 CPU（第 1→28 分钟，上限 800%） | 约 629% | 约 450% |
| cgroup 被限流周期 / 累计时长 | 732 / 18.8s | 68 / 1.4s |

每分钟快照 pending 全程为 0。通过的运行不输出 `ACCEPTANCE-RUNTIME`，所以本轮没有
各节点调度延迟分桶。

结论：负载降到 3000/s 后，CPU 余量约 350%，cgroup 限流减少约 93%，权限读繁忙、
系统繁忙和秒级 SENDACK 尾部同时消失。这支持"4500/s 下的剩余失败来自本机 8 CPU
容器饱和"，但仍是相关性证据；4500/s 在更大 CPU 环境下是否通过尚未验证。
