# Scope review — generation 1

**Conclusion: the two-asset external seal and composite offline plan design is reusable; do not implement a production-capable stable writer until the pre-write provenance boundary below is made explicit.** No code or external state was changed. The reviewed proposal copies and source hashes are frozen alongside this report; this is design review, not execution evidence.

## R1 — blocking scope ambiguity: local candidate facts cannot authorize a real stable seal

The proposal says the new stable writer first calls the #72 candidate audit/verifier and allows non-TEST-ONLY candidates, while deferring fresh source/control checks to later production wiring/activation. Those are different boundaries. `compose-package-site.py:1986–1988` validates production control_sha only as 40-hex; `:2021–2055` binds and structurally checks supplied resolution/metadata/attestation files; `:2078–2082` rebuilds the plan using its own declared SHA. The candidate audit's real package-signature checks (`package-audit-receipt.py:1089–1123`) do not authenticate the historical checkout or the source's current GitHub provenance. `docs/release-contract.md:649–659` explicitly states this limitation.

Existing `seal-audit-release.py:272–301,376–386` checks live *seal control* main/tag and immutable policy, but has no historical candidate control/source authentication. A self-consistent forged local control/source tree must not become trusted merely because it passes candidate verification and a real Publisher token seals it. Two distinct control labels are correct; they do not themselves prove the relationship.

Smallest resolution for this offline slice: stable writer mode remains loopback-only and fails before any request for real endpoints until the existing production source-preflight and actual historical-control byte checks are integrated. Alternatively identify and implement the concrete existing pre-write calls now, before any POST/PATCH; do not replace them with a local success JSON, caller boolean, seal-resolution hash, or a future activator promise. This is not a request for a new request/response ledger or general provenance framework. Legacy preview writer responsibility/behavior need not change.

Required added failure: production-shaped (test_only=false) locally self-consistent forged history/source, even with the expected seal SHA, must not reach any real-host write through the new stable CLI. Preserve the separate positive test in which historical candidate control differs from seal control and both are independently established.

## R2 — required TEST ONLY boundary detail: dual loopback bases do not bound redirects

`resolve-audit-release.py:193–207` accepts an initial asset redirect to any HTTPS host and then uses the ordinary urllib redirect-following opener; authorization is stripped, but requests can still leave loopback. Checking only api_base_url and download_base_url at startup is insufficient for the proposed TEST ONLY no-external-network guarantee. Existing writer upload handling already requires same-origin for loopback (`seal-audit-release.py:167–175`) and JSON writes disable redirects.

Smallest change: in the new TEST ONLY read/write path reject asset redirects entirely, or validate every hop remains the explicitly allowed loopback origins. Add a loopback 302→external fixture whose external-request sentinel stays untouched and whose partial output is cleaned. Do not expand production redirect or credential routing policy as a side project; retain legacy behavior outside the explicit new mode.

## Accepted scope and useful reductions

- Keep the candidate's original content-derived filenames, v3 receipt, signed APT/RPM bytes and null internal audit/package IDs unchanged (`package-audit-receipt.py:1079–1123`). Only the outer numeric Release/asset identity is new; exactly two assets is sufficient.
- Keep candidate history and seal control distinct. `CANDIDATE_PRODUCER_FILES` (`compose-package-site.py:1890–1897`) excludes the four planned helpers, so unchanged core bytes can verify current #72 candidates. First implementation should simply reject mismatching producer bytes using the existing guard; there is no need to add a historical-code executor, code import from control data or new registry.
- Composite planning may validate supplied seal observations and hashes, but cannot distinguish a fully self-consistent local forgery from authentic GitHub evidence offline. P01 must promise consistency rejection plus provenance/activation=false, not authentication of who produced the JSON. Any future activator needs a fresh numeric resolver and source gates.
- Preview owns /repo and other root metadata exclusively. Stable root copies stay only under the snapshot prefix. Stable mirrorlist points to the exact complete immutable RPM snapshot; generated bytes/hash/size are part of the plan, no-store, and no whole-site atomicity claim follows. No /repo-stable or new installer is needed in this slice.
- Stable remains enabled=false/object_storage_required; no manifests, keys, live site, production workflow, IAM, DNS, CDN or OSS writes. Native TEST ONLY validation must remain credential-free and must not read production Mac keys.
- v1 preview output/schema/default behavior remains intact; v2 total limit is 8 snapshots / 2 GiB across both channels and retention. Every retained generation is independently checked; conflicts never choose an input-order winner; deletion remains empty.

The failure matrix is otherwise appropriately focused: numeric-ID/state/asset fencing, original-byte equality, strict candidate opt-in, source/control confusion, bounded input, duplicate IDs/URI conflict, all-generation retention and default-consumer rejection. Its R03 already anticipates redirect rejection; make the TEST ONLY every-request constraint explicit rather than relying on inherited transport.
