# Candidate: bounded UID recovery flights

Status: **static proposal, not implemented or tested**. The separate tests-only branch has one intentional isolation RED and eight PASS. This proves coarse cold-lane HOL under the controlled boundary; independent cold-UID latency is a proposed contract, not an existing promise or a confirmed cloud root cause. Source remains 2ab3e1a8; the current diagnostic run is not touched.

Replace only AuthorityRecovery's I/O-spanning 32 lane ownership with a small private registry of in-flight UID proofs. Keep NewAuthorityRecovery, RecoveryDirectory, RecoveryBatchOwners, page packing, the production owner adapter and caller retry/deadline contracts. Do not add a generic singleflight module, per-UID goroutine, background worker, retry, larger owner gate, lane count or timeout.

The key is `(HashSlot, SlotID, LeaderNodeID, LeaderTerm, ConfigEpoch, UID)`. These are the five distributed identity fields in Directory.sameAuthorityIdentity (`directory.go:595–600`) and ValidatePresenceTarget (`presence_recovery.go:36–47`). RouteRevision and AuthorityEpoch are excluded from key equality as existing local revision/observation metadata, while each complete original RouteTarget is still forwarded unchanged. Directory and owner membership/boot/sequence validation remain authoritative; a matching flight key is never evidence of route validity.

On one existing <=512-UID / <=256-target page, check Directory first so proven positive/negative lookups bypass admission. Briefly lock the registry to find existing flights and atomically reserve **all** new keys, their owned UID bytes and one leader-cohort slot. Copy each newly retained UID's exact bytes (`strings.Clone` or equivalent), once, after reservation; reuse those owned strings in the bounded owner request. No registry mutex spans owner I/O, Directory calls or waiting. No partial new-key reservation is retained while waiting for quota. An existing-only follower takes no new cohort slot. Quota wake-up must recheck Directory, and an admitted leader rechecks missing proofs before owner I/O to close the completion/admission race. A quota notification channel needs no registry-owned waiter list; waits select the caller context. An individually oversized page returns typed ErrRouteNotReady immediately.

Execute newly owned work **before waiting for existing flights**. In A={u1}, B={u1,u2}, B first queries and installs only its u2 proof. Immediately after installation (or failure), resolve its owned entries, release their keys/UID-byte/cohort resources, and signal done; only then may B join A's u1. Done must not be deferred until the whole mixed page or earlier flight completes. This prevents owned resources and completion dependencies from forming a cycle. Batch current owners once for the newly owned subset; preserve successful sibling groups and original result alignment/UID multiplicity. Do not publish any partial owner evidence as negative proof.

After done, every caller rereads Directory under its own target. Store only completion status in transient flights, never cached routes or an offline marker. FIFO eviction or authority change between installation and a late waiter's read can legitimately return ErrRouteNotReady/ErrNotLeader; it cannot return fabricated offline, stale routes or silently query the owner again. Existing outer adapter retry remains the only retry. Close/remove/release exactly once on every error and cancellation path.

A canceled follower detaches without canceling owner work. With in-caller execution and no detached work lifetime, canceling the **leader's** context cancels its owner read and completes the cohort unsuccessfully. That leader returns its own context error; a still-live follower receives typed ErrRouteNotReady, while its own canceled/deadline context takes precedence. This intentionally avoids passing another caller's context.Canceled as its own cancellation. A stronger promise that owner work survives leader cancellation would require a separate bounded lifecycle and is outside this minimal proposal.

Three independently checked hard limits must exist: retained distinct keys, copied UID bytes, and active leader cohorts. A conservative proposed starting envelope is **4 cohorts**, **4×512=2048 keys**, and **4×1 MiB=4 MiB of owned UID bytes**, with <=1 MiB for any indivisible admitted page. Four follows the existing node-wide owner gate (`presence_recovery.go:22–33`); it is below the old 32-lane maximum and does not enlarge network concurrency. The key ceiling follows the existing 512-UID page. The 1 MiB page / 4 MiB byte values are **new internal memory-budget choices**, not an existing RPC maximum, UID-length guarantee or measured capacity claim. They permit a full 512-UID page to average 2 KiB per retained UID; larger pages must fail explicitly. Freeze/review these choices before implementation and validate compatibility/capacity; do not present them as already approved production defaults. Bytes cover registry-owned UID copies, not caller inputs, Directory's existing proof FIFO, transport buffers or all presence heap.

The change can increase effective parallelism and owner-query rate even with lower hard maxima, so performance improvement is not assumed. It cannot isolate B when all four owner reads or the explicit budgets are legitimately occupied. Implement only after the complete failure matrix has failed meaningfully on the old code; then use public-seam integration controls and the existing adapter/runtime proof contracts. A later process-level test must retain exact-source artifacts and check receipt delivery under the unmodified workload gates. That test would validate a candidate mechanism; matching the cloud incident still needs exact message-level evidence. If implemented, update the applicable FLOW, Unreleased note and project knowledge, and run the named flow documentation gate and independent review.
