## Smallest complete change proposed

Use the existing controller diagnostic stream and coordinator summary. Add no new diagnostic file, report schema, persistent state, retry, service, or universal error framework. Keep the report validators, fail-closed verdicts, exit-code mappings, cleanup bounds, and worker traffic unchanged.

A small chatlifecycle-specific failure record plus an unexported error wrapper is sufficient. The record contains only a closed finalization stage/reason and, when available and valid, the already-frozen `observed_outcome`, `observed_cause`, and `observed_terminal`. These fields are diagnostic observations, never an alternative report verdict. The wrapper's `Error()` is a fixed safe message; `Unwrap` preserves the internal sentinel/underlying error for `errors.Is/As`. Underlying errors, paths, worker identities, RPC bodies, and arbitrary strings must never be formatted into retained output. Retain both the broad existing sentinel and the inner cause (for example via joined causes internally); never classify by matching error text.

- In **CheckpointRecorder**, tag errors at the already-existing return sites with a fixed stage, retaining existing sentinels: `checkpoint_sequence`, `checkpoint_evidence`, `snapshot_aggregate`, `report_validation`, `write_json`, or `write_markdown`. Reasons can reuse the six existing snapshot classifications; evidence reasons need only `invalid_evidence`, `dataset_mismatch`, and `invalid_snapshot_cut`. Output reasons need only `invalid_paths` or `output_failed`; no filesystem error string is needed. This is a few explicit return-site annotations, not a refactor of validation or writing.
- In **ProductionEvidenceController.Finalize**, report `controller_guard`, `controller_continuity`, `live_diagnostic`, `dataset`, or `meta_checkpoint` at the existing rejection point. For the dataset helper, distinguish probe error and digest mismatch without a second probe. Retain the prior meta-product rule exactly: a later harness-only metadata error must still allow the existing product report. Forward an already-classified recorder failure rather than replacing it with a new generic error. Reuse the existing `wkbench.chat_lifecycle.controller_failure` JSON event, adding a closed `phase=finalize` discriminator and optional frozen observation fields. Best-effort logging failure never replaces the primary failure or changes verdict/control flow.
- In **Coordinator**, add one bounded finalization record to CoordinatorResult. At existing rejection sites mark `worker_stop`, the classified hook failure (or safe `controller_unknown` fallback), or `snapshot_aggregate`. Preserve the pre-finalization terminal decision as an observation, not as the coordinator outcome. Do not make a failed finalization return product success or a valid report. The continuous hook site must use the same classification. `stopAssignedSnapshots` can retain its existing ErrCoordinatorSnapshotCount while wrapping the original failed Stop cause privately; fixed reasons distinguish missing assignment, deadline/cancel, and control failure without serializing raw RPC errors.
- In the **CLI runner**, append the closed finalization fields to the existing summary only when a finalization failure exists. Preserve them on both report-unavailable and existing-report paths. Keep `chatLifecycleCoordinatorVerdict`, `ReadReport`, report preference, and exit mapping unchanged in this diagnostic-only change. Keep the original summary byte-for-byte when there is no finalization failure.

These four production files are the necessary scope to distinguish every top-level finalize branch and the requested checkpoint/write boundary. Tests live beside their existing files. Operator-visible diagnostics require CHANGELOG Unreleased and concise PROJECT_KNOWLEDGE; the applicable FLOW must be updated only if its description becomes inaccurate. No workflow/policy/skill changes are required.

## Important existing partial-output boundary

`CaptureAndWrite` writes JSON before Markdown, and commits recorder sequence only after both succeed. A Markdown failure can leave a readable JSON. `productionChatLifecycleRunner.Run` currently prefers ReadReport(final.json) even if the coordinator failed finalization. Therefore an absence of final.json cannot prove a filesystem failure, and a JSON-only failure fixture must not assert that both files are absent. This proposal exposes the failure alongside the existing output path; it does not change two-format transaction semantics or the report gate. Any later request to change that policy needs a separately specified/tested change.
