# Minimal diagnostic proposal; not implemented

Existing service-label metrics already separate owner admission, queue depth, wait, inflight, handler completion and end-to-end client totals. Reuse them on all three nodes; do not add UID/Channel/session/physical-Slot labels or duplicate global pool metrics. Durations are one-in32 samples and service14 mixes read and mutation operations, so the current data cannot place a particular owner-read timeout on a cross-node timeline. No dedicated reply-enqueue failure counter or owner registry lock/scan duration exists.

The smallest useful diagnostic is a bounded transport edge record for owner reads9/10 only, preserving existing wire bytes and behavior. Record monotonic times for caller start/send enqueue; receiver request admission/handler start; owner registry scan start/finish; handler completion/reply enqueue result; client response decode/caller terminal reason. Include the existing request ID and a run-private connection-generation identity sufficient to pair the exact endpoints. Request ID alone is only per connection; independent source IDs on opposite ends must not be declared equal. The process E2E harness can retain the normalized connection tuple privately and publish only a finite opaque correlation after proving an exact match. Do not expose addresses, UID strings, Channel IDs, payloads, error text or metric labels containing correlation IDs. No new wire nonce is needed for a controlled fresh local fixture, and no production protocol change is proposed.

Keep at most128 active owner-read entries per node, the latest128 slow completed records (threshold50ms), and the first64 failed records. Hard-cap128KiB per node, with explicit dropped/incomplete counters; use bounded synchronous in-memory recording without a goroutine, timer or file write per request. Flush after workload stop and preserve existing outcome/gates. A private harness sink may count reply enqueue results as the closed set ok/full/canceled/stopped/error; it must observe the existing error, not retry, close connections or alter the reply. Preserve instrumentation overhead in the run description. A permanently exposed new telemetry API is unnecessary for the first controlled reproduction.

For registry attribution, separately time lock acquisition versus indexed scan in a controlled fixture or bounded sink, rather than assume a whole owner-handler duration means lock contention. The real online Registry and transport must be in the path. First write controlled failure tests: (1) handler starts before client cancellation and continues under mixed-service semantics; (2) one held Registry writer blocks an unrelated UID scan until released, with cancellation recorded; (3) block response writes/fill its bounded scheduler after handler completion and show client timeout without blocking response demultiplexing or requiring an executor token; (4) gate first target of operation10 and observe later target serialization, preserving exact fences/alignment. Each uses latches and finite cleanup; realistic deadline/process tests belong to integration/E2E. Do not change mixed-service CancelRunning, shard layout, transport queues, timeouts, retries or owner gates to make a hypothesis pass.

Only after a red-capable exact-seam test and the per-request evidence agree should a repair be selected. Then repeat the unchanged original distribution locally and obtain a complete valid report. None of this proposal authorizes new cloud procurement or establishes the original cloud cause.
