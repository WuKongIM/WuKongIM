## Cancellation and Registry locks

PresenceOwner service14 contains both read operations9/10 and route mutations. It is absent from the read-only CancelRunning allowlist (pkg/cluster/net/transport.go:354-357). Once its request starts, Service.handle replaces the negotiated caller context with the service lifetime plus30-second handler context (service.go:334-350). Client's250 ms deadline still ends client waiting and receiver queued ownership, but it does not cancel an already-started owner handler. On expiry the response callback suppresses sending to the dead request context (server.go:284-286). A context deadline is cooperative; an RLock wait or long context-free scan is not forcibly interrupted at30 seconds either. This is a static lifetime mismatch, not evidence that one occurred in this run, and enabling cancellation on the mixed mutation service would be an unjustified semantic change.

All Registry writer critical sections (RegisterPending, MarkActive, unregister, touch/requeue, EnableMessageUpdates) use only memory maps/slices and dirty-index bookkeeping. No writer calls network/disk/session callbacks under its lock. DrainTouched's locked drainDirtyLocked scans/compresses the entire shard dirtyOrder even after its output limit is filled (registry.go:279-303), so work depends on that backlog. RangeLocalSessions invokes a visitor while holding a read lock (:132-146); its only production caller is Manager connection pagination, whose visitor performs context checks, projection and bounded heap operations (internal/usecase/management/connections.go:110-135), not I/O. Thus a writer-held RPC/disk wait is refuted by this code. Ordinary lock/scheduler contention remains unmeasured. SessionHandle write/close are not called inside these Registry critical sections.
