# Fresh classification with the c495 counting rules

This is a plan, with no profile opened or parser executed. The baseline decoder and classifier are reference algorithms only. Their hardcoded old paths and observed cohort-count assertions are not reusable for a fresh run. A small path-parameterized bounded adapter is a future approved action; no implementation is supplied or authorized here. Preserve all old files and original run artifacts. Stop on parser/type/limit uncertainty rather than rewriting the metric/profile parser or forcing expected counts.

For each available node goroutine profile, sum `sample.values[0]` only after its goroutine/count sample type is verified. Partition each delivery `runWorker` sample in the baseline priority order: idle plan dequeue; registry admission quota wait (`admitRecoveryPage:156`); owner recovery RPC; remote authority RPC; bounded parallel-leader WaitGroup join; owner PushBatch RPC; UID-flight join (`recoverPage:70`); unclassified. Every member contributes to exactly one category and the fresh categories must sum to that profile's observed delivery-worker total. Do not assert a historical fixed worker total.

Independently partition each `recoverPage` cohort: registry quota wait; executing cohort owner RPC; UID-flight join; unclassified. An actual owner-read-holder cohort requires both `executeRecoveryCohort` and `RecoverRoutesByTargets`, then independently partitions by caller context (delivery worker / inbound presence RPC / other) and operation (batch owner-route read / singleton / other). Preserve the baseline exact-symbol tests and priority. Unknown frames remain explicit. Source line interpretation is conditional on verifying those exact 56c files and lines; a mismatching line must not be reinterpreted as the old branch.

Count `Conn.Call` callers using the same nearest non-transport product frame rule; count delivery enqueue and Slot apply-task callers separately. These named cohorts overlap and must not be added together. The recovery symbol/line table is deliberately overlapping. For owner source-line tables, only call a partition disjoint if each holder has exactly one matching readOwnerPage line; otherwise label it overlapping/unclassified rather than double-counting holders. Preserve all invariant failures as finite diagnostic results.

CPU aggregates use the baseline sample count and nanosecond weighting only when sample types are verified. Publish sampled on-CPU total, elapsed profile duration, symbol flat top 20 and optionally the already bounded top 60 symbol projection. These are on-CPU samples, not disk latency, off-CPU waits, heap headroom or elapsed stack-cut wait durations. Fixed `-top` and `-traces` are at most one each per input; raw traces/labels/string tables/addresses/UID-like values stay private. Public output is a closed allowlist of counts/classes, immutable Go symbols/source lines and elapsed/windows/status only, with no raw stack records or errors.

Missing/partial data is not a zero count: record each path as missing, capture-partial, request-failed, unsafe/oversized, decode-failed or usable with its actual approved metadata. Do not assume all six profiles exist, succeeded, have equal durations, or cover active SEND. A missing goroutine profile still permits its independently valid CPU profile and vice versa; it does not permit a substituted node/file. The profile header time and duration, helper request/capture status, first-grant/terminal/drain evidence and launch times must be bound after cleanup and separate root approval. Nominal +5s and metadata phase labels cannot establish an independently observed active-send window or exact synchronized sampling across nodes.

Publish each node/cut separately. Optional totals of available cuts must carry completeness and sampling-time labels and cannot be called one simultaneous cluster state. No message identity joins, failed-message stack claim, cloud root-cause claim, c495/old-run latency comparison, causal performance comparison, Linux acceptance, successful message-loss regression or release-readiness conclusion follows from these six diagnostic profiles. No heap, DB, new profile/service request, network, install, build, test, workload or cloud operation is part of this offline plan.
