# RPC 连接请求取消父节点登记实验：未通过吞吐验收

本轮尝试由连接已有请求表统一负责断连取消，省去同一请求在 Go context 父子表中的重复登记。
候选在本地独立进程写 RPC 对照中**没有稳定收益，已撤回生产改动**。吞吐中位变化 **−0.06%**，
四对有正有负；同版本 A/A 吞吐变化为 +0.34%、−2.36%。不能据此认定原有写 RPC 回退得到修复。

本次只交付诊断报告、证据和知识记录，没有修改运行时行为，因此不新增产品 Changelog 条目。
未购买云服务器。12 个纯计时窗口共 **25,264,674 次成功 RPC**；2 个独立剖析窗口共
**6,888,548 次成功 RPC**，全部零错误、零样本截断。本轮临时容器均退出并销毁。

[完整证据](assets/rpc-inbound-parent-2026-09-22.json)保留全部测量、源码、候选补丁、构建命令及哈希、
测试日志、8 份原始 pprof、解析输出和清理回执。原始目录：
`/Users/tt/.codex/visualizations/2026/09/22/rpc-inbound-parent`。

## 假设与单变量候选

按顺序提出三个可验证预测：

1. 请求表与 context 子节点表重复登记可能造成明显成本；去掉后一份登记，应在保留取消语义后稳定提高吞吐。
2. 响应回调捕获整个入站对象可能增加分配；缩小捕获应降低分配，但仍须独立验证吞吐。
3. 若前两项只改善局部成本，主要限制可能位于队列和执行器的阶段同步，需要进一步区分持锁、唤醒与调度成本。

本轮只测试第一个假设，未混入回调、队列或执行器修改。第二、三个假设仍未确认。
源版本为 `caad6f290`；根 AGENTS 摘要已冻结，transport 无适用 FLOW。
实验在 `.worktrees/rpc-inbound-parent` 内进行。

`Conn.New` 使用没有值和截止时间的 Background 根上下文；`shutdown` 先取消连接根，再调用
`cancelInboundRequests`。后者已有独立请求表，会逐个取消仍登记的请求。候选仅将 `TrackInbound`
的 `WithCancel/WithTimeout` 父节点改为 Background，保留每请求自己的上下文、预算定时器、取消函数、
请求 ID 表、重复 ID 拒绝、结束时删除和取消，以及关闭连接时取消全部请求。

关闭与准入的协调仍是：先取消连接根，再在 `inboundMu` 下取走请求表；准入持同一锁检查根是否已取消，
成功登记的请求由取走的表负责取消。候选取消依赖该显式关闭流程，不能把单独取消根上下文当作完整关闭。
该生命周期依赖的变化没有获得吞吐收益支持，故未保留。

不能直接让无预算或 v1 请求共享连接根上下文：当前服务端会按请求 ID 处理有效取消帧，
需要独立请求取消能力；预算为零并不等于没有取消语义。队列监听、执行超时、已启动写操作独立完成、
FIFO 与容量边界均未作为实验变量移除。

## 本地独立进程对照

Go 1.25.11、GOWORK=off、CGO=0；Apple M4 的 Docker Linux ARM64 VM。
静态 ARM64 服务端与客户端运行在已有 Debian amd64 rootfs 中，程序输出确认 `arch=arm64`。
客户端 CPU0–3，服务端 CPU4–7，各 GOMAXPROCS=4、GOGC=100、3GiB 上限。
同一网络命名空间 loopback，无主机监听端口，两进程分别承担自身 GC。

固定本轮基线客户端，开启请求预算；16 个预热连接、16 个调用者，64B 完整回显校验。
服务并发64，队列4096项/64MiB，排队期限5s，执行期限30s，调用期限2s，CancelRunning=false。
每窗10s，四对交替 AB/BA，加两对同版本 A/A；每调用者最多100万样本，达到上限即失败。
所有计时窗口均关闭服务端剖析和 Observer；构建、测试、微基准、pprof 不与计时重叠。
客户端分配指标不代表服务端分配；本轮客户端不是原始 `68662c4c8` 客户端，不能跨轮比较绝对吞吐。

|指标|基线中位数|候选中位数|变化|
|---|---:|---:|---:|
|吞吐 RPC/s|209,897.26|209,763.90|−0.06%|
|P99 ms|0.491855|0.478938|−2.63%|

四对吞吐变化分别 +1.11%、+0.38%、−4.64%、+0.40%；P99 变化分别 −2.26%、−7.46%、
+21.76%、−2.98%。A/A 吞吐变化 +0.34%、−2.36%，P99 −4.11%、+17.61%。
不利配对完整保留；这些样本没有达到事先约定的稳定收益标准。

因此没有进入大包、旧线协议及完整服务回归验收，也没有把该候选合入。
这不是证明所有负载下都无收益；本轮只有每连接一个调用者，不能外推高并发复用单连接的场景。
也未重做原生 x86 跨主机回归。

## 分阶段与剖析证据

实际 `TrackInbound` 方法与真实 Service Enqueue/pump/executor/Finish 链路各测有/无预算两种情况，
每项500ms、基线和候选交替3轮，共36行。支架复用载荷和结束通知；不包括网络编解码。
每个登记周期访问 Done，纳入真实路径的惰性通道分配。下表为3次耗时中位数，分配值各轮一致。

|场景|基线→候选 ns/op|B/op，未变|allocs/op，未变|
|---|---:|---:|---:|
|无预算，仅登记|192.4 → 162.4|240|4|
|有预算，仅登记|353.9 → 311.9|416|6|
|无预算，写生命周期|1979 → 1953|1072|14|
|有预算，写生命周期|2204 → 2180|1248|16|
|无预算，读生命周期|2173 → 2157|1200|16|
|有预算，读生命周期|2195 → 2196|1200|16|

局部登记确实减少约30～42ns，但没有减少分配，也没有转化成稳定网络吞吐收益。
微基准不包含 socket、服务端响应编码等开销，不能替代网络验收。

两个独立18s诊断窗口各采8s CPU及累计 alloc_space、mutex、block，共8份原始 pprof。
诊断调用次数与纯计时分开保存，不将有剖析时的吞吐改善混入候选收益。

|累计调用栈采样占比|基线|候选|
|---|---:|---:|
|CPU：TrackInbound|4.80%|5.34%|
|CPU：context.removeChild|1.20%|0.37%|
|mutex：TrackInbound|0.027%|0.030%|
|mutex：Service.Enqueue|79.91%|81.01%|

`removeChild` 的 CPU 比例下降与减少父节点删除操作一致，但请求登记本身并非主要锁等待来源。
Enqueue 的 mutex 样本提示继续细分该路径，不等于其锁内 CPU 占比，也不能直接证明某条语句是回退根因。
不同进程的采样比例、累计分配量不可直接解释成每 RPC 绝对成本；嵌套累计值不能相加。

## 正确性检查、撤回与后续方向

候选前新增实验测试，调用实际 Conn 创建、TrackInbound、CancelInbound 和 Close：
覆盖重复 ID 不取消原请求、按 ID 取消不影响其他请求/连接、结束后 ID 复用、关闭后拒绝准入、
预算截止时间、关闭与16个并发准入竞态；每轮竞态执行20组。

运行 `GOWORK=off GOTOOLCHAIN=go1.25.11 go test -race -tags=integration ./pkg/transport/internal/conn
-run '^TestInboundTracking' -count=20`，未修改基线通过；候选 `-count=100` 通过。
这是有界语义验证，不是原吞吐回退的单元测试复现；性能判定使用上述真实网络配对窗口。
候选未通过性能门槛，因此没有宣称通过全套回归或证明全部取消时序等价。

生产补丁已恢复，实验测试和探针源码移至证据；只提交本文、证据和知识记录。
核验14个运行的载荷计数、零错误、样本上限、8份 profile 哈希、二进制哈希、正常退出与清理状态。
已有其他容器和未提交文件保留。本次文档交付不重跑未发生变化的产品全套测试。

后续应优先区分队列准入的持锁时间、唤醒频率和执行器交接成本，并补充单连接多并发对照。
此前移出队列分配、移出监听撤销均未获得稳定收益，不应仅凭 Enqueue 的累计 mutex 占比重复这些改动。
