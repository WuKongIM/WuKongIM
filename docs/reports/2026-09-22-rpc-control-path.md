# 无预算 RPC 尾延迟的测量边界复核

**确认了客户端 GC 对端到端 P99 的显著影响，尚未确认候选存在稳定的服务端 P99 回退。**
服务端完全不变时，仅把压测客户端 GOGC=100 改为400，两对P99分别下降38.57%和33.41%。
但最终低GC频率控制中，同一基线的A/A P99仍上升41.84%，说明客户端GC不是全部波动的解释。
本轮保持原运行时，仍不接受上一轮候选；这一决定表示收益/代价尚未可靠验证，不表示已经锁定某个服务端根因。

## 来源与问题

工作分支基线`dcba86e27`，上一轮报告为
[已准入写监听实验](2026-09-22-rpc-write-listener.md)。上一轮四对无预算单连接P99均上升是
当时真实观察，应保留；但它们是客户端测得的端到端延迟，不能直接当作服务端函数耗时或已确认根因。
本轮先复用同一对归档二进制，避免重建、链接布局或工具链变化成为新变量。
二进制来源仍是`1aebc05336f16ac422178ae523789fa3b729c9e2`及归档`candidate.patch`；
这两个提交之间的transport变化只有测试。原候选没有重新合入。
根AGENTS及依赖`pkg/goroutine/FLOW.md`摘要冻结于证据中的`source.json`；transport无适用FLOW。

预先列出三个可区分的假设：公共队列CPU/锁成本增加；执行器唤醒后的调度等待增加；
冷启动、客户端GC或环境漂移干扰测量。未能建立同版本稳定、跨版本稳定变红的性能断言，
因此采用有限证据诊断，不把某次吞吐或P99方向当作已验证修复。

## 环境与边界

Apple M4主机，本机Docker Linux ARM64进程、Go1.25.11。客户端CPU0–3，服务端4–7，
各3GiB、GOMAXPROCS=4；服务端GOGC始终100。沿用缓存Debian amd64 rootfs执行静态ARM64程序，
运行输出再次验证实际架构为arm64。虚拟CPU集合不等于证明物理CPU隔离。
单连接、16调用者、PoolSize16、64B完整回显、无预算协商、CancelRunning=false、Observer关闭。
客户端仍给每次调用2秒本地超时；服务并发64、队列4096项/64MiB、排队5秒、执行30秒。
客户端和服务端是不同进程，loopback同网络命名空间，无主机端口。
这些是最小transport闭环饱和负载，不能代表跨主机集群、生产观察器开销或固定到达率SLO。

纯计时40窗，每窗10秒；另有8窗15秒的采样负载。采样结果不混入计时验收。
CPU/trace分别在启动客户端约2秒后请求，CPU采8秒、trace采3秒；每版各两次并交换运行顺序。
开启pprof时还设置mutex采样比例10及block采样率1ms。CPU与trace不同时采集；
mutex/block快照是进程从启动到抓取的累计数据，包含初始化，不是纯CPU采样区间。
采样有扰动，且没有逐次RPC与profile起止的同步计数，不能把15秒调用数直接用于8秒CPU归一化。

## 独立进程采样

CPU的入队累计占比：基线4.07%/5.03%，候选4.36%/3.48%，两对方向不同。
队列timer累计占比：基线1.65%/1.68%，候选0.77%/0.90%。
这些是各自CPU样本份额，不能视为每RPC成本；没有证据将新增截止时间选择认定为集中CPU热点。
系统调用与计时函数占较大份额，两版都有，不能从共有热点推出新增回退原因。

mutex采样中，入队释放锁栈上的累计等待基线603.87/820.00ms，候选737.39/904.58ms，
两对均较高，作为未解决线索保留。总mutex等待分别为基线887.10/1256.94ms、
候选932.93/1020.05ms，并非一致增加。该采样将等待归因于释放锁的栈，
并不能直接证明该栈的持锁执行时间变长；调度和竞争者数量也会影响结果。

|trace|执行器唤醒栈事件数|该栈平均调度等待µs/事件|占总调度等待|
|---|---:|---:|---:|
|基线1|439,751|33.493|90.06%|
|候选1|451,668|32.153|89.94%|
|候选2|424,923|33.839|89.85%|
|基线2|451,102|33.132|90.10%|

这里是Go trace将“变为可运行后等待执行”的延迟归因到Executor.Submit/ants.Invoke唤醒栈，
不是说Submit执行占用90%CPU，也不是说它阻塞了这么久。按该栈事件数归一化后，一对下降、
一对上升；不能仅凭两版共有的90%占比继续重写执行器。

## 预热与每秒分布

旧探针只在计时前调用每个连接一次，不构成持续预热。新客户端增加可选3秒、16调用者并发预热，
并记录每秒调用数/P99、预热计数以及测量期间客户端GC次数和总暂停。
原有样本容量、逐次回显、连接/超时配置保持相同。所有模式继续在正式计时前执行一次客户端GC。
每秒窗口按调用开始时间分组；边界跨越调用仍计入开始窗口，十窗计数之和必须等于整窗完成数。
分秒统计在计时后排序；不能把十个P99平均成总体P99。

新客户端下无预热/3秒预热各三对，交错预热模式和版本顺序，每种模式内比较固定同一客户端。
新探针多了分秒记录，故旧探针和新探针的绝对结果不作单变量比较。

|预热|配对|候选吞吐变化|候选P99变化|
|---|---:|---:|---:|
|0秒|1|+0.30%|-25.63%|
|0秒|2|-0.21%|-5.94%|
|0秒|3|-1.79%|+8.16%|
|3秒|1|-1.84%|-1.45%|
|3秒|2|+1.38%|-26.79%|
|3秒|3|-2.63%|+11.97%|

3秒预热A/A：基线吞吐-0.55%、P99 +7.04%；候选吞吐-1.67%、P99 +3.41%。
一个无预热基线窗的前两秒P99为0.836/0.728ms，后续秒约0.203–0.401ms；
但预热后的另一个基线窗在第六秒仍升到0.642ms。首个无预热窗口启动附近还执行了约0.21秒
的pprof离线文本预览，是否与测量起点重叠未同步确认，故该窗口仅保留观察，不用于单独证明冷启动因果。
持续预热没有消除中途漂移，
也不能将全部历史差异归为冷启动。

## 仅改变客户端GC的对照

同一服务端基线、同一新客户端、3秒预热，服务端GOGC=100保持不变。
只改变客户端GOGC，按100→400、400→100运行两对。没有更改产品配置。

|窗口|客户端GC次数|客户端总暂停ms|RPC/s|端到端P99 ms|
|---|---:|---:|---:|---:|
|1，GOGC100|122|73.61|178,580.54|0.361042|
|1，GOGC400|30|20.39|182,843.85|0.221791|
|2，GOGC400|30|17.54|180,194.32|0.213708|
|2，GOGC100|123|59.50|181,715.96|0.320917|

P99分别下降38.57%/33.41%，吞吐+2.39%/-0.84%。这支持“端到端P99对客户端GC策略敏感”，
并不意味着GC400是产品调优建议，也不能证明上一轮每个不利窗口都由客户端GC造成。
客户端总暂停不等于每条RPC的GC附加延迟，本轮没有作逐请求相关性归因。

## 低GC频率下重比两版

固定新客户端GOGC400、3秒预热，服务端仍GOGC100。两对AB/BA和两版各一对A/A：

|比较|吞吐变化|P99变化|
|---|---:|---:|
|版本配对1|+2.64%|-42.47%|
|版本配对2|+1.74%|-6.26%|
|基线A/A|-1.59%|+41.84%|
|候选A/A|+1.02%|-0.06%|

两对候选看起来较好，但基线A/A的P99仍由0.213208升至0.302417ms。
因此这一批也不是验收通过，不能用更有利的结果推翻上一轮拒绝决定。
降低客户端GC频率仍不足以得到稳定的尾延迟判据，环境或其他执行因素尚未分离。
一次主机快照未报告热/性能警告，当时Docker未见本轮以外的压测容器，但这不证明全程无系统干扰。

## 决定、验证与后续边界

继续保留基线运行时。此次修正的是判断边界：测得的版本P99差异是真实端到端观察，
但尚不足以证明稳定的服务端回退或锁定定时器/执行器根因。候选也没有取得可靠的完整收益证明。
在同版本对照仍大幅波动时，不再迭代取消监听实现以追逐某个有利批次。
后续先建立稳定的原生Linux独立进程基准，对客户端与服务端分别记录资源和GC，
同时报告端到端指标；达到预先约定的A/A重复性后，再对单个服务端变化验收。
本轮不采购服务器、不更改生产GC策略。

共48窗，40窗纯计时、8窗采样，测量段校验91,764,407次成功回显（不含预热）。
无非预期错误、样本截断、OOM或异常服务端退出。所有运行保存原始结果、每秒计数、
客户端/服务端命令、profile抓取边界、架构、源码/二进制/输出摘要及清理回执。
新探针构建成功并通过真实运行和逐调用者/逐秒计数守恒校验；未修改产品代码，
未新增无法稳定捕获症状的性能断言，也不冒称新增产品修复或产品回归测试通过。
本轮临时探针源码和测试容器均已清理，没有购买云资源。

[结构化证据](assets/rpc-control-path-2026-09-22.json)嵌入探针源码、驱动、全部原始结果、
CPU/mutex/block及trace导出profile、采样汇总和验证记录。四个原始trace共约104MB，
与三个二进制保留为本机外部工件，清单记录绝对路径、长度和SHA256，不扩大Git仓库；
原始目录为`/Users/tt/.codex/visualizations/2026/09/22/rpc-control-path`。
`profile-summary.py`对pprof原始样本按调用栈去重归组；累计项不能相加当成总CPU。

复现入口依次为`replay.py`、`diagnostics.py`、`warm.py`、`gc-control.py`、`steady.py`，
每个脚本必须在前一个完成后运行，构建和profile离线分析也与纯计时分开。
前两步复用上一轮已校验的base/candidate二进制；新客户端源码为`warm-probe.go`，
