# 带预算 RPC 的队列取消监听实验

**不保留候选运行时代码。** 带预算写RPC减少约288B/1次分配，本机1/16连接吞吐中位提升约2.65%/2.58%，
P99下降约35.75%/43.13%；但读RPC吞吐中位下降1.74%/0.56%，单连接读损失明显大于其A/A波动，
且拒绝请求增加64B/2次分配。没有实际流量配比证明总体收益，暂不以增加截止时间索引的复杂度
换取这种跨路径代价。最终只提交实验记录与适用于原实现的回归测试。

## 来源与方法

基线 `7c2ece537082215592e7609e6f56237c984e3e8b`。本轮仅本地验证，没有购买云资源。
根 AGENTS 和依赖 `pkg/goroutine/FLOW.md` 的摘要已冻结；transport 没有适用 FLOW。
候选保留标准 Go budget context，只让现有服务队列定时器覆盖调用方截止时间，
从而让带预算入站请求也复用连接内显式取消入口。预算协商、FIFO、准入、共享执行器和
已运行 mutation 的独立执行策略保持原有语义。

预先拆分三种可能：预算 context/timer 本身的成本、通用队列取消监听的成本，以及
分配减少仍不足以改善执行/同步开销。先测分段分配及 CPU profile，随后只实现一个候选，
再对真实独立进程作交换运行顺序的对照。没有从微基准分配直接推断网络吞吐。

组件诊断使用 Darwin ARM64、Apple M4、Go1.25.11；基线和候选组件耗时不是交错计时，
只能作为机制线索，不能据此宣称稳定速度收益。真实进程验收使用本机 Docker Linux ARM64、
Go1.25.11、GOMAXPROCS=4、GOGC=100，服务端 CPU4–7、客户端 CPU0–3，各3GiB内存。
静态 ARM64 程序使用缓存 Debian amd64 rootfs，探针输出确认实际进程为 arm64。
双方共用一个容器网络命名空间的 loopback；没有主机端口，没有 Observer。

每组固定相同基线客户端，两版服务端和三类探针均由同一份对应源码重新构建，记录 SHA256。
16个调用者、连接池16、活动连接1/16、服务并发64、队列4096项/64MiB、排队5s、执行30s、
客户端2s预算。主组开启预算协商，所有窗口校验 `request_budgets=true`。
普通写 `CancelRunning=false`；读控制开启该选项。纯计时每窗10s，不采 profile 或 MemStats。
主组每拓扑4对AB/BA，随后基线和候选各1对A/A。每个控制负载每拓扑2对AB/BA。
完整回显检查、每调用者计数和样本上限检查均由探针及归档校验执行。

## 组件机制

合成阶段中，带预算 context 为384B/5次分配，增加通用队列监听后为784B/10次，
再进入写 handler 为1056B/14次，读 handler 为1008B/14次。
标准 context 与队列监听的约400B/5次增量包括取消树注册，不能逐项相加累计 profile 占比。
独立 CPU profile 中 `watchQueue` 累计19.8%，`context.AfterFunc` 累计14.36%，
`context.WithTimeout` 累计25.74%；这些仅是合成阶段 profile，并非网络服务端占比。
该合成探针直接创建标准 context，不能用其候选重跑结果衡量入站专用监听收益。

真正经过 `Conn.TrackInbound` 和 service/执行器的串行生命周期诊断为：

|路径|基线B/次|候选B/次|基线分配次数|候选分配次数|
|---|---:|---:|---:|---:|
|带预算跟踪|416|480|6|8|
|带预算写|1248|960|16|15|
|带预算读|1200|1168|16|17|
|无预算写|768|784|13|13|
|无预算读|1152|1168|17|17|

新增入站 wrapper 在准入前有64B/2次成本，增加队列索引还使 owner 分配增大16B。
写请求省去通用队列监听后净减少288B/1次；读执行本身仍连接标准 context 的取消树，
因此只有32B净减少，次数反而增加1。失败准入不能获得队列监听节省。

## 候选的并发与边界

`inboundQueueContext` 仍包装标准 `context.WithTimeout/WithCancel`，保留 Deadline、Done、Err、
Value、Cause 以及标准子context传播。显式cancel、连接关闭和finish仍调用同一取消入口；
异步回调仍归现有 transport RPC service goroutine 任务管理。
直接监听只覆盖显式取消；预算到期由原标准context定时器与队列的共用定时器分别承担职责。
通用context仍使用标准 `context.AfterFunc`。

新增的调用方截止时间最小堆只索引使用直接监听且仍在FIFO排队的请求，长度受准入上限约束；
插入/删除是O(log Q)，额外索引空间为O(Q)。FIFO保持执行顺序，堆仅决定谁先超时。
出队、取消、超时和Stop都移除索引并清空尾部引用，避免保留已完成请求。
服务仍只持有一个队列定时器，结合FIFO头的固定排队时限和所有已索引请求的最早调用方时限。
回调重新检查当前请求和时间，已开始的旧回调不能提前结束替换请求。
`Service.mu`继续仲裁终结所有权；不池化请求对象。

新回归用可控时间证明非队首提前到期、显式取消移除、空位复用、旧回调与Stop清理。
测试使用仅显式取消回调的预算context，模拟候选需要承担的新契约；在基线明确失败、候选通过，
证明直接扩展wrapper还必须补上队列截止时间处理，并不表示基线的标准context超时本身有错误。
实际连接集成测试覆盖有/无预算的取消、断连和运行中
读/写策略；标准子context的DeadlineExceeded、Cause和Value传播也有断言。

## 决定和交付

选择撤销候选，保留完整补丁、源码、二进制摘要和所有有利/不利窗口。
单连接读A/A吞吐仅约±0.026%，原两对读吞吐为−2.20%/−1.28%，
不能把这项损失直接归为环境噪声。16连接读A/A波动更大，证据不足以断言其小幅下降稳定，
但这不消除单连接读的负面结果，也不消除已证实的分配代价。
写路径改善是真实的本轮局部证据，尚不能证明混合负载或原始版本回退已经解决。

交付保留原运行时代码，扩展实际入站回归，覆盖有/无预算请求的排队取消、断连与运行中读/写策略，
以及预算context子节点的DeadlineExceeded、Cause、Value和标准AfterFunc传播。
候选专属的最小堆/人工deadline回归与诊断探针仅归档，不留在产品测试或运行时中。
此轮没有用户可见行为改变，因此没有新增Changelog条目。

若继续优化，应先找到让读请求和失败准入不承担额外所有者分配的边界，再复用队列取消入口。
不要直接重试这个全量包装预算context的候选，也不要据本机loopback推断原生x86跨主机或完整集群容量。

## 验证与复现

候选完整transport race集成测试通过；撤销后再次执行transport单元及race集成测试，
验证最终交付的回归测试与原运行时兼容。全部计时/分配窗口的配置、固定客户端、回显/Busy、
逐调用者计数、样本上限、源码/二进制/输出摘要、MemStats算术、进程正常退出及无OOM都由归档脚本核对。
共72窗，校验102,759,024次成功回显RPC及17,771,859次预期Busy响应，未出现非预期错误、样本截断或OOM。
Busy计数不代表成功执行业务。临时探针和本轮容器均已清理，没有新购云资源。
