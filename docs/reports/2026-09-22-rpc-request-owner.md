# RPC 队列与执行器共用请求所有权

本轮实现一个明确的分配优化：执行器复用队列项内嵌的任务，省去每次成功执行
请求的独立 `serviceTask` 分配。64B TCP 对照稳定少 **96B、1 次分配/RPC**，
但本地吞吐变化不稳定，不能宣布前轮云上 **8.24%** 的回退已修复。
没有新购云资源，前轮租约仍为 released。

源码基线为 `a689006cf`，承接
[原生 x86 双端交叉归因](2026-09-22-rpc-cross-host-results.md)。
[机器可读证据](assets/rpc-request-owner-2026-09-22.json)保存实现补丁、测试源码、
冻结的指令和二进制摘要、全部计时输出、复现驱动与验证日志。

## 假设与验证范围

实验前按以下顺序提出假设：

1. 队列项和执行任务重复保存请求，分配与复制增加成本；共用对象应减少分配，
   若它也是主要吞吐瓶颈，TCP 吞吐应稳定改善。
2. 取消监听的上下文注册更重要；若成立，仅减少执行任务对象不会明显改善吞吐。
3. FIFO 到共享执行器的调度交接更重要；若成立，分配下降后仍有调度成本。

本轮只改变第一项，未删除监听、时限或绕过执行器。原生 x86 的云上反馈环已在
上一轮关闭租约后不可运行，因此对原始吞吐问题采用已保留证据路线，不用 ARM
loopback 结果替代。新增的分配检查只判定所有权对象成本，不判定云上吞吐恢复。

## 实现与终结语义

之前，`Enqueue` 为 `requestEntry` 分配一次，`pump` 又复制请求到新分配的
`serviceTask`。现在 `requestEntry` 内嵌 `serviceTask`，入队时填好 `service`
和 `req`；从 FIFO 移除后，向同一共享执行器提交内嵌任务的地址。

取消监听、排队时限、执行时限、FIFO、服务并发令牌、共享执行器容量、保留
字节准入、回复和释放路径均沿用原实现。没有池化或提前复用：即使取消监听
停止失败、到期回调已启动，回调持有的队列项仍由 GC 保持可达，读到
`queued=false` 后返回。提交失败、排队取消、panic 和停机仍使用原有终结路径。

元数据存在一个明确权衡：本机 64 位布局中，旧队列项 152B，新队列项 168B，
旧独立任务 104B。这是 `unsafe.Sizeof` 布局，不是实际堆分配或 RSS。尚未执行
的队列项多 16B；默认 4096 项满队列对应约 64KiB 额外结构体元数据。执行阶段
省去独立任务后，实测小包端到端总分配净少 96B。已排队但直接取消的请求不会
享受执行对象节省；字节准入仍按载荷实际保留容量计算，元数据由队列项数约束。

## 分配回归

在实现前加入真实 `Enqueue → pump → executor → Finish` 回归检查，使用可复用
载荷和完成通知，不以结构体形状充当测试。命令：

```sh
GOWORK=off GOTOOLCHAIN=go1.25.11 go test ./pkg/transport/internal/rpc \
  -run '^TestServiceRequestOwnershipAllocations$' -count=1
```

旧实现失败：`allocated 2.00 objects/request, want at most 1`。新实现在 macOS
和原生 Linux ARM64 各连续 20 次通过。测试为 `!race`，避免把竞态插桩分配
作为产品成本；语义与并发回归另行完整启用 race。该测试不覆盖网络或完整预算
开销；TCP 对照覆盖了这部分。

## TCP 交错对照

同一 Apple M4、Docker Desktop Linux ARM64 VM，Go 1.25.11，静态 ARM64
测试二进制，GOMAXPROCS=4、CPU 0–3、内存上限 6GiB。复用已存在的 Debian
amd64 rootfs，只直接启动静态 ARM64 程序；输出确认 `goarch: arm64`。不是
x86 模拟吞吐，也不是与前轮 ECS 同环境复测。

使用未修改的 `BenchmarkTransportBudget`，64/65537B、1/16 调用者，16 个
预热连接、预算开启、Observer 关闭，队列 4096 项/64MiB、排队时限 5s、
执行时限 30s、调用时限 2s。两个版本交错 AB/BA/AB/BA/AB，共五轮、40 项，
每项 2s；计时期间没有构建、测试或 profile。计入 benchmark 输出的调用共
**9,234,001** 次，内容与零错误断言均通过，不含预热和基准自校准调用。

| 字节/并发 | 基线中位 ns/op | 候选中位 ns/op | 吞吐中位变化 | 基线 B/op | 候选 B/op | 分配次数 |
|---|---:|---:|---:|---:|---:|---:|
| 64/1 | 12,397 | 12,310 | +0.71% | 2,825 | 2,729 | 45→44 |
| 64/16 | 3,536 | 3,518 | +0.51% | 2,826 | 2,730 | 45→44 |
| 65537/1 | 67,646 | 67,656 | −0.01% | 156,305 | 155,910 | 45→44 |
| 65537/16 | 46,778 | 47,112 | −0.71% | 154,828 | 154,758 | 45→44 |

`ns/op` 为吞吐折算耗时，不是 RTT/P99；分配包含双端。小包分配下降在每个
样本一致，不能把大包不同轮次的池复用/GC 差异算成精确每请求节省。
64B/16 逐轮吞吐变化为 +9.63%、+11.57%、−8.87%、−1.64%、+1.26%，
方向反转且基线范围 3,485–3,925ns/op、候选 3,470–3,824ns/op 重叠。
其他场景同样有方向反转，未证明稳定吞吐收益或统计显著性。

保留此改动的依据是少一次分配与更少的请求副本，且现有语义未弱化；不是
凭 +0.51% 宣称性能问题解决。取消上下文与调度交接的相对因果贡献仍未确定，
不重复前续已无收益的简单拆锁或关闭监听实验。
