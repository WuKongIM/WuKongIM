# 持续失败的发送端时序诊断

**状态：原规模持续诊断失败，尚未修复断连。** 同一生产二进制在
5000 频道、4500 SEND/s 下，发送 179.16 秒、806,235 次调用后出现
sender_read EOF，pending=6561。总运行时间 411.10 秒，未触发磁盘保护。
三个节点的公开配置均确认 128 gateway workers、131072 总队列、
batch cap=32、128 Store append workers。没有修改产品默认配置、发送节奏、
超时或准入门槛，没有并行编译、其他测试、压力任务或 profile。

## 探针与验证

新增默认关闭的 `WK_E2E_MEDIUM_RECIPIENT_DRIVER_DIAGNOSTICS=1`，只改变
E2E 观察方式。它分别记录计划发送时刻的滞后、SendFrame 入队耗时和真实
socket Write 耗时；保留累计计数/最大值及固定 100 个 100ms 窗口。
数据在失败处理的 HTTP 采集之前冻结，不保存 payload 或 UID。

边界测试先于探针代码编写，未声称执行过 RED。五个普通测试及 race 均
通过，覆盖测量窗口隔离、冻结、环形覆盖、过期、并发计数和部分写入。
macOS 的 LC_DYSYMTAB 链接器警告保留在日志中。

25 频道、500 SEND/s、10 秒的真实进程正向对照通过：5000 次发送调用、
5000 次 socket Write、2,385,000 bytes，零发送/写入错误、零 pending。
该短跑只验证探针，不替代持续资格。源文件指纹、实际构建身份、二进制
摘要、普通/race 日志和完整正向对照均已保存。

## 失败窗口观察

| 指标 | 全窗口最大值 | 失败前最近十秒最大值 |
| --- | ---: | ---: |
| 发送调度滞后 | 49.09ms | 4.16ms |
| 客户端入队耗时 | 22.30ms | 3.96ms |
| socket Write 耗时 | 52.22ms | 6.03ms |

最近十秒每 100ms 最多 451 次发送调用，每个发送连接最多 19 次；相同
窗口内每个连接最多写入 9063 bytes。冻结前没有 SendFrame 或 socket
Write 错误。未观察到足以解释队列满的大规模客户端补发突发。

失败前清理尚未开始的公开指标记录：节点 2 有一次
`async_dispatch_queue_full` 关闭和一次 async_send admission full。
其余节点没有该关闭原因。permission busy=0，追加路由峰值为 55.47%，
因此既非权限 busy 拒绝，也不要求追加路由达到满载才会出现断连。

第 60、120 秒的 pending 分别为 109、145，失败时为 6561。SENDACK
P99=589ms、RECV P99=562ms。网关排队/批次处理 P99.9 分别为
946.59/456.28ms；按消息加权的追加路由 P99.9 为 429.80ms，Store
append 等待为 193.97ms，物理提交为 79.49ms。append worker 曾达到满载，
但这些累计分位数不能给仍未完成的请求确定等待阶段。

## 结论边界与下一步

本次证据不支持“大规模客户端补发突发造成断连”的解释，支持继续检查
服务端会话排队和共享追加路径。尚未确定存储、复制、调度或物理磁盘中的
哪一项导致停顿，不据此修改容量、放松强一致性或扩大发送队列。

socket Write 完成只证明本机 TCP 接受数据，不等于服务端收到消息或
SENDACK；字节统计包括控制帧。固定窗口不能重建窗口内到达顺序，
各节点累计直方图也不能证明某个具体会话的因果链。

下一步应捕获变慢会话中具体未完成请求的阶段，区分单个请求阻塞与共享
环节停顿；同时补齐独立的真实网络并行权限读取证据。原 30 分钟资格和
5% 同机对照门槛继续保持未通过/未验证。
