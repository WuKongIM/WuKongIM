**通信层跨 ECS 实测 — 2026-09-21**

本次使用临时购买的 3 台服务节点和 1 台压测节点，完成六轮业务对照、36 组 RPC 测量及短时网络抖动恢复检查。全部资源已销毁并取得经过认证的精确租约零残留证明。云上结果没有证明整体业务延迟或吞吐改善；候选版本存在分配增加及并发 RPC 吞吐下降，需要继续定位。

原始实现背景见 [前序报告](2026-09-21-transport-performance.md)，逐轮数据、指标口径、原始证据摘要及清理证明摘要见 [机器可读结果](assets/transport-cross-host-2026-09-21.json)。本次仅补充验证记录，没有修改产品代码。

**环境与方法**

基线 `68662c4c8fa7a447ac2864c7352789ae4a5021b7`；候选 `7bda37db546fc577dd6fe7cc56ed3b95e6cbeeda`，包含前序审查修正。两者使用 Go 1.25.11 编译为 Linux amd64。
阿里云杭州同一可用区，4 台 `ecs.u2a-c1m2.xlarge`，每台 4 vCPU / 8GiB，AMD EPYC，Ubuntu 24.04 / Linux 6.8.0-139；服务节点各有 500GiB ESSD PL0 数据盘，压测节点为 200GiB。使用独立 ECS 的内网链路，未验证底层物理宿主机分布。

三副本集群，256 Hash Slots、12 个逻辑 Slot。相同机器、配置及候选 wkcli 驱动两种服务版本，按基线/候选交错执行三轮；每轮重启进程、使用新数据目录并等待集群就绪。1000 在线用户、100 个互不重叠的十人群，128B 消息，每群计划 5 SEND/s，总计 500 SEND/s，并发 64，seed 42，完整接收内容校验。后续复核发现配置中的 `random_online` 在当时版本会回退到每群首个在线成员，实际是 100 个固定发送者，不构成随机发送者覆盖；见 [本地归因与修复](2026-09-21-benchmark-local-attribution.md)。预热 30s、测量 180s，排空上限 30s（可提前完成）。这些群聊结果不能与前序同宿主混合业务基准直接合并。

首次准备阶段超过压测器默认 10s 轮询等待上限，未进入有效测量；改为 `--phase-poll-timeout 90s` 后使用全新运行 ID 重测，未修改产品超时。初次失败证据单独保留。报告归档首次因旧临时文件权限失败，已改用新文件重新归档；六轮报告均成功取回并核对。

| baseline-2 | 87,080 | 483.78 | 192.73 | 2,920 |

所有轮次均连接成功 1000 人，连接、SENDACK 和接收校验错误率为零，既定报告门限通过。但实际只达到计划发送速率的约 96.8%–97.6%；未发送数量表示测量窗口内未完成的计划发送，不等同于网络丢包。此次不能宣称完整达成 500 SEND/s，更不能据此声称最大容量。

三轮中位数：SENDACK P99 **192.27 → 194.76ms（+1.29%）**；吞吐 **484.23 → 484.19 SEND/s**。样本只有三轮，不能据此推断显著的整体延迟退化，但没有看到整体收益。

每轮只选测量窗口内的 18 个资源快照，时间跨度 170–171s。以下为三节点合计后再取三轮中位数，分配表示累计分配速率，不是存活堆或 RSS。

| 资源 | 基线 | 候选 |
|---|---:|---:|
| CPU（核） | 1.394 | 1.386 |
| 平均 RSS（MiB） | 1195.2 | 1168.4 |
| 分配（MB/s，十进制） | 139.49 | 154.57 |
| 分配次数/s | 1,112,192 | 1,195,344 |

候选分配字节速率增加 **10.8%**。候选观测丢弃计数在采样窗口内增量为零；基线不存在该计数，记录为未知，不能把缺失指标视为零。

第二轮各版本另取约 20s 的应用及主机指标窗口。直方图估计的 channel runtime append P99：基线三节点约 22.9ms，候选约 16.6–18.4ms；storage commit P99 约 5ms，未见持续网关队列积压。这提示内部部分路径可能改善，但只是短窗口聚合，不能相减得到独立阶段耗时，也不能认定整体瓶颈已解决。

压测器 `internal/bench/workload/group.go` 的发送计时始于 `lockSendackOperation` 之前。后续核对本次压测器精确版本发现，实际使用的 `matchingPersonClient.lockSendackOperation` 是空操作，因此先前据此推测客户端锁等待的结论不成立。RECV 指标从收到 ACK 后等待匹配消息开始，也不是端到端投递延迟。约 194ms 的尾延迟与计划发送缺口仍需分段证据；本轮旧数据不能追溯拆分。新诊断指标、已复现的调度问题及证据边界见 [压测延迟归因后续](2026-09-21-benchmark-latency-attribution.md)。尚未证明压测器就是云上瓶颈。

**跨节点 RPC 与网络恢复**

业务服务停止后，在两台服务 ECS 间运行公开 transport 接口的 echo 探针。每项 3s、三轮，16 个预热连接，1/16 个并发调用，64/4097/65537B 载荷，逐次校验返回内容，36 组共 4,535,005 次成功调用，错误为零。Observer 关闭，两版库的默认 `WriteBatchMaxWait` 均为零；此探针没有重现前序应用默认凑批等待的比较。候选启用预算协商，基线没有该功能，因此比较的是两个功能集的整体代价，尚未隔离预算、服务调度、缓冲池各自影响。

| 字节 / 并发 | RPC/s：基线 → 候选 | 吞吐变化 | P99 ms：基线 → 候选 |
|---|---:|---:|---:|
| 64 / 1 | 14,170 → 13,570 | -4.2% | 0.087 → 0.091 |
| 64 / 16 | 142,977 → 115,868 | -19.0% | 0.253 → 0.610 |
| 4097 / 1 | 11,443 → 11,111 | -2.9% | 0.140 → 0.142 |
| 4097 / 16 | 78,525 → 74,335 | -5.3% | 0.849 → 0.860 |
| 65537 / 1 | 3,586 → 3,720 | +3.7% | 0.457 → 0.451 |
| 65537 / 16 | 20,331 → 14,511 | -28.6% | 2.552 → 3.068 |

以上均为三轮中位数，P99 为单请求 RTT。64B / 16 并发吞吐下降约 19%，65537B / 16 并发下降约 29%，应作为后续定位的回归线索。客户端稳态分配不包含服务端，也不同于前序同时保留 32 个缓冲区的内存探针；65537B 串行每调用分配约 179,919 → 152,855B，不能宣称所有云上内存指标降低 87%。本轮未采集云端 pprof，不能仅根据此前本地剖析就把云上回归全部归因于 context/timer。

在候选客户端出口临时施加 `netem delay 10ms 2ms`，设置 20s 自动撤销保护。抖动期间 4,771 次调用无错误，P99 12.06ms；撤销后 349,778 次调用无错误，约 116,588 RPC/s、P99 0.608ms。已核验队列恢复为 mq/fq_codel、没有 netem。该结果仅证明短时延迟注入及撤销后的 RPC 行为，不覆盖丢包、断网、节点故障或业务故障转移。

**后续行动与边界**

优先为同一候选版本加入预算开/关的隔离基准，分别采集服务端与客户端 CPU/alloc pprof、队列等待，定位并发 RPC 退化；再优化 context/timer 分配与调度路径，保留截止时间、取消和内存准入语义。同步拆分压测客户端计时并记录计划与实际发送差异，重跑相同跨节点场景后再判断收益。此次没有继续购买资源或未经验证地调整产品参数。

本轮没有验收十万成员群、WAN、最大容量或长时间稳定性，也未执行固定的 60 分钟 chat-lifecycle 稳定性流程。三轮短样本、同可用区环境及不完全达标的发送率限制了结论外推。
