## 等待与资源证据

O→D 的 list queued-worker P99 中位数分别从 **7.501 / 5.378 ms** 降至
**0.051 / 0.044 ms**；driver 匹配线程的 runqueue wait 两次都约减半。
节点合计等待及 leaf CPU PSI 同时下降，支持本次逻辑 CPU placement 干预确实影响了
列表排队和调度等待的解释。

| 轮次 | Driver matched wait 中位数，s | 三节点 matched wait 合计的中位数，s | 产品 CPU/完成请求，ms | leaf CPU PSI some 中位数，s |
| --- | ---: | ---: | ---: | ---: |
| 01-S | 29.166 | 158.059 | 10.8519 | 28.358 |
| 02-O | 26.430 | 211.338 | 9.6564 | 40.299 |
| 03-D | 13.669 | 190.270 | 9.6686 | 32.625 |
| 04-D | 13.970 | 190.174 | 10.1032 | 33.057 |
| 05-O | 26.805 | 212.167 | 9.6583 | 40.769 |
| 06-S | 30.770 | 161.097 | 11.0359 | 28.799 |

CPU/请求是三个产品节点前后 metrics CPU 计数差值之和，除以排空完成的
list+sync 请求数，再取窗口中位数；不包含 driver。metrics 跨度包括窗口开始前
约 100 ms 和窗外观测开销，不是精确 60 秒或纯业务计算 CPU。
请求混合比例固定，分配每窗约 36.65–36.71 GB。
产品 CPU/请求没有随着 O→D 同步下降，不能把观察到的改善说成产品计算工作量减少。
task wait 是匹配线程的累积 Linux runqueue wait，可能超过墙钟时间；
不是完整进程 off-CPU、goroutine 等待或请求等待。

O/D 四轮的 sync queued-worker P99 三窗中位数约 0.016–0.020 ms，其 driver 等待主要体现为
producer 延后；total 延迟改善主要体现在请求阶段。这削弱了“两个端点都通过
相同的 driver 排队机制改善”的先验判断。producer 的总体包括全部计划到达；
queued-worker、total、request、driver-wait 包括实际尝试的请求及错误，不含丢弃。
queued-worker 从 enqueue 尝试前计时，含少量 producer 记账。不同分位数不可相加，
也不能直接用分位数之差给单个请求分配因果贡献。

可见非根祖先的 `cpu.max=max 100000`，所有观察到的进程 cgroup membership、
CPU/cpuset/memory 静态控制均保持一致。18 窗的可见 `nr_throttled`、
`throttled_usec` 与 host steal 增量均为 0；根层缺失的控制仍为未知。
这只排除已观测层级的相应事件，不能排除隐藏宿主竞争。

### 01-S 第三窗：整体均值掩盖局部慢段

01-S 第三窗 list/sync P99 为 53.641/107.446 ms，约为前两窗的两倍。
但产品 CPU 为 168.40 s、分配 36.707 GB、三节点 GC pause 累积之和 0.114818 s，
整体 task wait 也没有同比翻倍，不能单凭这些整窗值指定 GC 或工作量为根因。

| 56 | 36.68 / 58.79 | 0.475 / 2.684 | 3.223 / 3.227 | 249 / 70 |
| 57 | 76.67 / 153.38 | 0.641 / 3.024 | 3.099 / 3.530 | 292 / 48 |
