# 500 QPS CI reliability repair

## Evidence and scope

Source baseline: `eff9b4d1ef0d072016796e9fa5d20849e93a0bdd`.

- [PR run 35451750533](https://github.com/WuKongIM/WuKongIM/actions/runs/35451750533)
  rejected mixed SEND P99 487.4ms against 400ms. Append passed at 210.5ms.
  The 3000-operation mixed window lasted 6.022 seconds. Linux I/O full pressure
  accumulated 11.9% of that interval. Storage-request P99 buckets reached
  500ms while physical-batch commit P99 was within the 10ms bucket. These are
  different populations: the evidence suggests waiting but does not establish
  slow fsync or host interference as the root cause.
- [Nightly run 35134673634](https://github.com/WuKongIM/WuKongIM/actions/runs/35134673634)
  ended with a confirmed `message_loss` verdict after 120504 successful SENDACKs.
  The local wrapper instead emitted `insufficient_evidence` because the product
  failure ended the 600-second measurement early. Replaying the retained
  artifact reproduced exit 6 before the repair, and product-failure exit 3
  afterwards. Full-duration evidence remains false; this is not a passing run.
- That nightly's first `actual_offered_ratio` diagnostic used 2043 ACK completions
  over five seconds, although 2500 SENDs were recorded. This historical field
  describes ACK throughput, not proof of inadequate load generation. Its
  compatibility semantics remain unchanged in this revision.

## Implemented checks

Correctness, unit/race, and three performance seams have independent jobs on
GitHub-hosted Ubuntu 24.04. Performance uses Go 1.25.11, four visible AMD64 CPUs,
60 seconds of sustained warmup and three consecutive 60-second measurement
windows at 500 QPS. The 400ms limit remains. All windows must have at least 95%
scheduled start throughput, no drops/errors and complete request accounting.
A bounded open-loop queue records planned-arrival-to-completion latency,
queue delay and service time separately. Per-second evidence and rejected
windows remain available. No automatic performance retry is introduced.

Early confirmed product failures have a separate closed-timeline proof path.
It requires exact report identity, terminal report, closed ordered boundaries,
matching terminal timestamp, process continuity and profile evidence. It
cannot grant a performance pass, hide mismatched identities, or manufacture
full-window throughput.

## Validation and remaining acceptance

- Unit tests cover hidden queue delay, underload, drops/errors/missing work,
  and a bad middle window that aggregate P99 would hide.
- Integration and race tests exercise bounded saturation of the actual arrival
  scheduler. Local short mixed SEND, append and TCP seams passed; these macOS
  runs verify the harness and are not Linux qualification evidence.
- The captured nightly classification was replayed through the actual wkcli
  command, not only a synthetic fixture.
- The local four-thread sustained mixed SEND profile also completed all 90,000
  measured requests after 30,000 warmup requests. The three scheduled P99s were
  171.97ms, 203.80ms and 150.85ms, with 500 starts/s and zero errors/drops in
  each window. This is still macOS harness evidence, not Linux qualification.
- Terminal worker evidence now preserves bounded redacted failure examples
  (including correlation sample indices) once, after traffic joins. Focused
  controller/diagnostic tests pass with race detection; maximum retention stays
  below its 1 MiB cap.
- GitHub sustained runs, repeated baseline stability, and performance-regression
  injection acceptance are pending. GitHub host model/disk variation remains
  recorded; dedicated hardware is not claimed or required for this first run.
- The retained nightly message-loss verdict and the original mixed SEND waiting
  spike remain product/harness diagnosis work. No speculative runtime change or
  relaxed correctness threshold has been made.
- Scope-based baseline reuse is deferred until the qualification evidence is
  trustworthy; all PRs continue to execute the gates.

- PR run 35455793746 passed all independent jobs. The three scheduled-arrival
  P99 windows were 153.73/317.57/373.48 ms (append), 11.95/12.01/11.82 ms
  (mixed SEND), and 178.08/178.10/178.11 ms (TCP SENDACK). Every window started
  500 requests/s and completed all 30,000 requests with zero errors or drops.
- The pre-merge ten-minute run 35455833764 still failed: worker 2 retained one
  ten-second correlation expiry for sample 2305851805306903227. All 195,506
  SENDs were acknowledged; 2,232 of 2,233 sampled deliveries were observed.
  The run ended after 391 seconds including warmup, so it is not qualification.
- Read-only export of the retained node-1 database found that exact payload
  marker at message sequence 84. Its person Channel and the 100,000-member
  canary both mapped to delivery worker 19 of 320. Node 1 logged five-second
  presence timeouts on 512-recipient group pages; the terminal metric cut had
  173 queued plans and only one active worker. These facts identify the shared
  queue as a concrete head-of-line blocking mechanism, not failed persistence.
- A runtime regression using those exact Channel identities failed before the
  fix: the person plan could not progress while group lookup was blocked.
  It passes after replacing fixed hash-to-worker routing with exact-Channel
  FIFOs and a shared bounded worker pool. Same-Channel execution stays serial;
  queued continuations rotate behind ready siblings. Empty Channel state is
  removed, with retained keys bounded by queued plus executing plans.
- Runtime/app/config race tests pass. Queue tests cover Channel-type separation,
  continuation fairness, no concurrent same-Channel execution and drained state.
  The resumed 500-QPS injection test rejects all three 450-ms service windows
  despite maintaining the offered rate. Full Linux acceptance remains pending.
