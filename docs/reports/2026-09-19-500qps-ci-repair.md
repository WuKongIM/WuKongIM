# 500 QPS CI reliability repair

## Evidence and scope

Source baseline: `eff9b4d1ef0d072016796e9fa5d20849e93a0bdd`.

- [PR run 35451750533](https://github.com/WuKongIM/WuKongIM/actions/runs/35451750533)
  rejected mixed SEND P99 487.4ms against 400ms. Append passed at 210.5ms.
  The 3000-operation mixed window lasted 6.022 seconds. Linux I/O full pressure
  accumulated 11.9% of that interval. Storage-request P99 buckets reached
  500ms while physical-batch commit P99 was within the 10ms bucket. These are
  different populations: the evidence suggests waiting but does not establish
  slow fsync or host interference as the root cause.
- [Nightly run 35134673634](https://github.com/WuKongIM/WuKongIM/actions/runs/35134673634)
  ended with a confirmed `message_loss` verdict after 120504 successful SENDACKs.
  The local wrapper instead emitted `insufficient_evidence` because the product
  failure ended the 600-second measurement early. Replaying the retained
  artifact reproduced exit 6 before the repair, and product-failure exit 3
  afterwards. Full-duration evidence remains false; this is not a passing run.
- That nightly's first `actual_offered_ratio` diagnostic used 2043 ACK completions
  over five seconds, although 2500 SENDs were recorded. This historical field
  describes ACK throughput, not proof of inadequate load generation. Its
  compatibility semantics remain unchanged in this revision.

## Implemented checks

Correctness, unit/race, and three performance seams have independent jobs on
GitHub-hosted Ubuntu 24.04. Performance uses Go 1.25.11, four visible AMD64 CPUs,
60 seconds of sustained warmup and three consecutive 60-second measurement
windows at 500 QPS. The 400ms limit remains. All windows must have at least 95%
scheduled start throughput, no drops/errors and complete request accounting.
A bounded open-loop queue records planned-arrival-to-completion latency,
queue delay and service time separately. Per-second evidence and rejected
windows remain available. No automatic performance retry is introduced.

Early confirmed product failures have a separate closed-timeline proof path.
It requires exact report identity, terminal report, closed ordered boundaries,
matching terminal timestamp, process continuity and profile evidence. It
cannot grant a performance pass, hide mismatched identities, or manufacture
full-window throughput.

## Follow-up warmup evidence gap

Manual workflow run 35485100291 on `8cba8d327` rejected mixed SEND before
measurement: the retained benchmark log said only `sustained warmup did not
complete`. No warmup request/queue counters survived, so the historical cause
cannot be classified as host interference, request error, or queue saturation.
PR run 35485705590 independently rejected append warmup with the same missing
accounting. Both failures remain visible and are not replaced by retries.

All three seams now write a separate non-qualifying warmup report before
asserting, with full per-window/per-second accounting and at most eight
anonymous failed-arrival examples. Errors use closed deadline/canceled/operation
categories; raw error text is never retained. Append and mixed SEND also record separate
warmup pressure/storage snapshots; mixed SEND includes bounded SENDACK reasons
on failure.
The warmup failure rule, measured 400-ms budget, offered rate and queue bounds
remain unchanged. This closes the evidence gap without claiming a root cause
that the earlier artifact cannot prove.

The independent ten-minute job in 35485100291 passed on `8cba8d327`: 600
measured seconds, 300,010 SENDs/ACKs, 3,916/3,916 sampled deliveries, zero
correctness errors/retries and converged queues. The workflow as a whole is
still failed because its mixed-SEND warmup failed; this successful job cannot
serve as a reusable main baseline.
