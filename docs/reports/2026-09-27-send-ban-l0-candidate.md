# 较大 L0 输出文件候选：拒绝并撤回

**仅增大 Darwin L0 文件目标没有解决持续失败，候选已撤回。** 在
相同 5000 频道、4500 SEND/s、30 分钟目标下，发送 110.966 秒、
499,349 次调用后仍出现 sender_read EOF。候选生产代码没有保留；
完整补丁、二进制摘要、失败日志和观测产物可复核。

## 假设与受控变量

核对精确依赖 Pebble v2.1.4 源码：L0 默认目标 2 MiB，flush 分割目标
4 MiB；每个输出 SST 的 Finish 会同步文件，完整 flush 随后同步目录。
因此提出可检验假设：如果大量小 SST 的文件结束同步主导 flush 时间，
适度增大 L0 输出可缓解积压；如果其他共享资源占主导，停顿仍会出现；
更大的 L0 键范围也可能加重后续 compaction，需要运行证据决定取舍。

候选仅在 Darwin 设置 L0 目标 8 MiB、flush 分割目标 16 MiB，显式保持
非 L0 文件目标为上游原值。WAL、文件最终同步、目录同步、memtable
停写阈值、队列、复制配置及权限逻辑均不变。没有关闭同步或提高队列
来换取通过。当前生产源码已精确反向应用保存的 candidate.patch.json 中的补丁，
并验证恢复到本轮基点 `0976b4d11` 的 engine 文件。

之前关于 Levels 可能为空的疑问也已排除：这个依赖版本使用定长数组，
现有 Bloom filter 契约在候选修改前通过，不存在该初始化缺陷。

## 验证

- 存储引擎全部现有测试通过，耗时 1.097 秒；候选生产二进制构建通过。
- 相同预编译 E2E harness 的真实三节点正向对照通过：25 频道、
  500 SEND/s、10 秒测量，5000 条消息，总耗时 38.11 秒。
- 完整规模失败：cold prime 177.297 秒，发送 110.966 秒后 EOF，
  总耗时 355.525 秒。配置核对通过，无资源保护终止。
- 运行期间没有本任务并行编译、其他负载、测试或 CPU/heap profile；
  使用与前一轮相同的 driver、最早未确认消息、存储历史和主机 iostat。

完整规模仍为 3 进程、256 Hash Slots、10 物理 Slots、3 副本，gateway
128 workers/131072 队列/batch32，append workers128。失败时
SENDACK P99=200ms、pending=6517、permission busy=0。仅节点1有
一次 async_dispatch_queue_full，各节点另有一次 peer_closed。
小规模通过及较低 P99 都不能替代原持续资格。

## 结果与限制

最后 180 个存储快照每节点 60 个，零采集错误。结束时三个节点均为
4 个 memtable、分配 256 MiB、一个 flush 在进行。整个窗口观测到的
最大 compaction debt 约 5.4 MB，仍然发生停顿；所以较高的 compaction
债务不是本次故障发生的必要条件。但与上一轮失败时刻、存量不同，
不能把两个终点债务直接作为候选改善比例。

失败前最后三轮，25 条最早未确认消息均在节点3，序号未前进。失败后
节点3 coordinator 仍位于 memtable 写停顿分支，后台可见文件写入。
三节点 profile 输入为103962/105601/117932字节，HTTP均200，无输入
或过滤输出截断。主机重叠区间 disk0 平均吞吐69.68 MB/s、峰值
260.52 MB/s，仍不能据此证明设备饱和或测得单次 fsync 时长。

这是一次受控失败实验，说明该参数候选不足以解决问题；不是严格多轮
随机对照，不能据一次更早断连宣称统计意义上的性能退化，也不能据
较低 P99 宣称改善。候选不进入产品 CHANGELOG 或默认配置。
