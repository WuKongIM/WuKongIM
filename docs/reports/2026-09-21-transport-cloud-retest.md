## 环境与比较口径

使用一个精确租约中的 3 台服务 ECS 和 1 台压测 ECS，阿里云杭州 B 可用区、`ecs.u2a-c1m2.xlarge`、4 vCPU / 8 GiB、AMD EPYC、Ubuntu 24.04。服务数据盘各 500 GiB，压测数据盘 200 GiB，均为 ESSD PL0；系统盘 40 GiB。服务节点通过内网通信。不同 ECS 不等于已证明位于不同物理宿主机。

Go 1.25.11、Linux amd64、CGO 关闭、`GOWORK=off`、`-trimpath`，服务和压测进程均为 `GOMAXPROCS=4`。三副本集群、256 Hash Slots、12 个逻辑 Slot。两种服务版本使用相同机器、配置和共同的候选版 wkcli；压测端仅通过构建 overlay 增加回环地址 pprof 监听，业务逻辑不变。API 及网关仅在测试内网使用，Manager 绑定回环地址。

按基线、候选顺序交错运行，每轮重启服务并使用新数据目录。1000 在线用户，100 个互不重叠的十人群，128B 消息，计划 500 SEND/s，并发 64、seed 42，完整接收校验。明确使用 `first_online`，与旧压测器把 `random_online` 回退为首个在线成员的实际行为一致。预热 30 秒，正式测量 180 秒，排空上限 30 秒；每轮计划 90,000 次发送和 810,000 次接收校验。

这是一组固定负载的短时诊断，不是最大容量、十万成员群、WAN、故障转移或长时间稳定性验收，也没有执行固定的 60 分钟 chat-lifecycle 工作负载。旧云测与本次使用不同租约，未证明所有配置和运行条件完全一致；不能把跨轮延迟差异全部归因于压测器修复。

## 构建与采集校验

首次候选构建意外包含工作区忽略目录中的大体积嵌入资源，已在任何有效业务测量之前废弃，并从干净的候选提交重建。实测候选大小为 88,586,065 字节，部署后逐节点核验 SHA-256。原始错误产物的校验值与排除原因单独保存。

基线二进制的内嵌 VCS 标记显示外层仓库的候选提交。本环境中，从基线提交建立新的干净嵌套 worktree 后重建，仍复现此标记，但二进制与实测基线逐字节相同；RPC 基线探针也通过相同的重建校验。因此源码身份依靠干净 checkout、构建参数和字节一致性证明，不能单独依靠内嵌版本标记。

第一次启动因诊断监听环境变量被验证子进程继承而在正式负载前失败，已修正为仅传给 worker。第一组基线/候选完成业务测量，但服务端 pprof 请求缺少 bench Bearer 认证；业务数据保留为补充观察。修正认证并验证 HTTP 200 和有效 profile 后，增加第四组配对，主结论使用第 2、3、4 组三组完整样本。没有为补测新增机器，未按结果优劣挑选样本。

正式测量期间每两秒读取 worker 状态和三节点指标，在接近测量第 150 秒时同时采集三节点及 worker 的 10 秒 CPU、heap、allocs、mutex 和 block profile。采样成功与采样时间均单独校验，不能把“已尝试四次采集”当作“四次采集成功”。CPU profile 只描述短窗口；业务 mutex/block 采样率未专门开启，空结果不能证明没有锁等待。allocs profile 为进程启动后的累计采样，不能直接作为该 10 秒窗口的分配速率。

## 业务结果

主样本为第 2、3、4 组。每轮均达到 500 SEND/s，完成 90,000 次发送和 810,000 次接收校验，1000 用户连接成功，连接、SENDACK、接收校验错误率均为零。六轮主样本合计 540,000 次成功发送；连同补充样本共八轮、720,000 次成功发送。没有计划发送缺口。

| 配对 | 基线 SENDACK P99，ms | 候选 SENDACK P99，ms |
|---|---:|---:|
| 2 | 37.340 | 34.767 |
| 3 | 40.699 | 38.140 |
| 4 | 37.489 | 35.000 |
| 三轮中位数 | **37.489** | **35.000** |

本轮候选 P99 中位数降低 **6.64%**，三组方向一致；各轮均值的中位数从 **10.193 降至 7.862ms（-22.87%）**。P99 范围分别为 37.340–40.699ms 和 34.767–38.140ms。仅三组短样本，且配对内始终先基线后候选，没有随机化顺序，因此这是当前条件下的观察结果，不能作为统计显著性或一般性性能保证。

补充的第 1 组 P99 为基线 44.094ms、候选 35.726ms，两者也达到完整发送率和零校验错误；因缺少服务端 profile，不纳入主统计。

| 分段均值的三轮中位数，ms | 基线 | 候选 |
|---|---:|---:|
| 计划时间到调度 | 0.386 | 0.396 |
| 客户端 SEND 提交 | 0.00946 | 0.00946 |
| 等待匹配 SENDACK | 10.173 | 7.843 |
| 含接收校验的完整操作 | 12.193 | 8.928 |

差异主要出现在等待 SENDACK 和完整操作阶段，不能仅凭这些客户端计时继续拆分为网络、存储或服务端排队。诊断分段的分位数是桶上界，不能与精确 SENDACK P99 混用或相减；RECV 指标仍表示 ACK 后等待匹配接收的时间，不是端到端投递延迟。

## 服务资源与归因

只采用正式测量窗口内、三节点均有数据的共同时间点，每轮跨度 176–178 秒。先按轮合计三节点，再取三轮中位数：

| 资源 | 基线 | 候选 | 变化 |
|---|---:|---:|---:|
| CPU，核 | 1.669 | 1.573 | -5.76% |
| 分配速率，MB/s（十进制） | 201.58 | 172.07 | -14.64% |
| 分配次数/s | 1,411,023 | 1,393,838 | -1.22% |
| 平均 RSS，MiB | 1252.5 | 1192.3 | -4.80% |

分配是累计分配的增速，不是存活堆。候选各节点 observer dropped 在共同采样窗口内增量均为零；基线没有该序列，记录为未知。固定负载下 CPU 下降不等于峰值吞吐提高。

第 2 组节点 1 的累计分配 profile 中，`pressureTaskP99MS` 的累计占比从 21.73% 降至 1.38%，与候选减少压力指标持续汇总样本的实现方向一致。候选 `ObserverDrain.drainAggregates` 仍占 5.29%；其批次切片和 duration 样本副本值得继续做隔离分配测试。候选 `context.WithDeadlineCause` 的累计占比为 2.12%，基线为 0.51%。这些是包含准备和预热的进程累计采样，父子累计项不可相加，也不能把整体分配差异全部归因于某一个函数。

共同压测器的六个正式 CPU profile 中，`summarizeDurations` 累计占 77.43%–78.64%，调用链来自状态请求 `LifecycleStatus → MetricsSnapshot → Collect`。源代码中的 `trafficStatusFromMetrics` 只投影计数器和 gauge，却触发完整时延历史排序。这是可定位的额外 CPU 开销；在本轮已达到 500 SEND/s 的条件下，尚不能认定它限制了当前业务吞吐。

## 跨 ECS RPC 与预算开关隔离

业务服务停止后，在两台服务 ECS 之间执行相同源码的 echo 探针。每个进程预热 16 个分片连接，载荷为 64、4097、65537B，并发为 1 或 16；每项测量 5 秒、重复三轮，共 36 组。返回内容逐次校验，单次调用截止时间 2 秒。两版 Observer 均关闭，默认凑批等待均为零；候选默认开启预算协商，基线不具备该功能。

再对同一候选版本执行预算开启/关闭的隔离比较：64/65537B、16 并发、三轮，共 12 组。关闭预算同时改变协商和每请求预算处理，不能仅称为“一次握手成本”。计时样本不启用锁采样；另外四组 20 秒运行分别采集基线/候选、小/大载荷的客户端与服务端 CPU、allocs、mutex、block profile，采样开销不混入吞吐比较。

RPC 延迟为单次调用 RTT；分位数保持探针原有的 `floor((n-1)*p)` 取样规则。客户端分配指标不包含服务端，也不是整机分配速率。此次没有重复网络延迟注入；前次恢复验证不能扩展为本轮已验收丢包或节点故障。

48 组非采样测量累计 **12,046,345 次成功 RPC，错误为零**。下表为三轮中位数：

| 字节 / 并发 | RPC/s：基线 → 候选 | 吞吐变化 | P99 ms：基线 → 候选 |
|---|---:|---:|---:|
| 64 / 1 | 11,681 → 11,389 | -2.50% | 0.100 → 0.103 |
| 64 / 16 | 136,751 → 129,494 | -5.31% | 0.228 → 0.333 |
| 4097 / 1 | 9,796 → 9,631 | -1.69% | 0.173 → 0.163 |
| 4097 / 16 | 82,394 → 82,112 | -0.34% | 0.611 → 0.615 |
| 65537 / 1 | 2,962 → 3,079 | +3.94% | 0.604 → 0.505 |
| 65537 / 16 | 17,553 → 16,002 | -8.84% | 2.950 → 2.751 |

64B / 16 并发和 65537B / 16 并发吞吐分别回退 **5.31% 和 8.84%**，因此不能宣布通信层性能问题全部解决。大载荷并发 P99 虽降低，平均吞吐仍下降；不要把延迟和吞吐混为同一结论。相比首次云测观察到的更大回退，本轮数字较小，但没有在同一环境直接对比旧候选 `7bda37d` 与当前候选，不能把差值当作后续优化的独立因果收益。

客户端分配方面，64B 两版均约 928B/调用；65537B 串行由约 183,811 降至 154,110B/调用，并发由约 155,446 降至 149,865B/调用。分配减少没有在所有并发场景转化为吞吐提高。

同一候选的预算开关隔离：

| 载荷 / 并发 | 开启 RPC/s | 关闭 RPC/s | 关闭相对开启 |
|---|---:|---:|---:|
| 64 / 16 | 129,288 | 129,092 | -0.15% |
| 65537 / 16 | 16,126 | 16,002 | -0.77% |

关闭预算没有恢复吞吐，两种载荷变化都低于 1%。本组数据不支持把回退归因于预算协商开关，更不支持以关闭预算作为修复。它没有隔离候选所有内部服务调度、执行截止时间和内存所有权实现。

四组独立诊断取得全部 32 份客户端/服务端 profile，诊断调用也均无错误。候选 64B 服务端 mutex profile 中，`Service.Enqueue` 所在释放锁调用栈占累计等待采样的 **63.18%**；候选采样总等待约 3.112 秒，基线约 0.441 秒。这里是自启用以来跨 goroutine 累计的抽样等待，包含采样开销和不同调用数，不能当作单 RPC 延迟或直接声称锁性能退化七倍。

同一候选小包服务端 allocs profile 中，`requestEntry.watchQueue` 累计占 **27.63%**，`context.WithDeadlineCause` 占 **26.97%**，`context.AfterFunc` 占 **19.65%**，这些调用栈部分重叠，不能相加。大包候选客户端 CPU profile 中 `runtime.memmove` 的 flat 占比为 **23.06%**。读写系统调用也占较大比例。证据支持优先隔离入队锁、取消监听注册及大载荷复制路径，但尚没有证明某单一热点就是全部吞吐回退的原因。

## 后续行动

1. **先处理 RPC 入队路径。** 在本地 Linux 复用相同探针，分别测量 `Service.Enqueue` 锁区、`watchQueue` 的取消监听注册和执行截止时间处理；每次只改一个因素。保留 FIFO、排队取消及时释放、执行中变更操作的独立时限、保留内存准入及停止/取消竞态测试。预算开关不是本轮验证有效的修复手段。
2. **让状态查询只读取所需的进度数据。** 为生命周期状态提供一致的计数器/gauge 快照，避免为了 `TrafficStatus` 重复复制并排序完整时延历史；最终报告和 SLO 继续使用原有精确分位数。需验证阶段边界、跨工作负载汇总、原子快照及终态封存语义。
3. **分别验证观测批次与大包复制。** 先以分配微基准验证 `drainAggregates` 的批次和样本副本，再以大包探针验证复制路径；缓冲复用必须保持数据所有权、精确计数与采样/丢弃语义。不要把减少分配直接等同于提高吞吐。

本轮保留当前提交作为可复现候选，没有在测试中途修改产品或扩大云资源规模。下一次付费测试应等本地隔离修改产生明确证据后，再确定新的单因素对照。
