# 已准入写 RPC 的队列取消监听实验

**原候选与定时器快路径修订均不合入运行时。** 专用监听延后到成功写准入后，
预算写每RPC减少约304B/1次分配，读和失败准入分配恢复基线；但原候选的无预算单连接
四对原始/补测P99全部上升。修订未相对原候选表现出一致改善，且其批次基线明显变慢，
不足以证明回退消失。最终只交付基线兼容的请求跟踪前进性回归测试、报告和完整证据。

## 来源与假设

基线 `1aebc0533`。此前全量包装预算context的候选因读吞吐和失败准入分配代价被拒绝，
见[上一轮报告](2026-09-22-rpc-budget-lifecycle.md)。本轮只验证一个更窄的候选：
专用监听延后到写请求通过服务准入之后，截止时间索引从公共请求对象移到服务侧。
测试前提出三项预测：读/拒绝分配恢复基线；公共owner不增大；新增同步和索引操作仍可能抵消写吞吐收益。
所有结果都保留，不能只以分配减少决定合入。

根AGENTS和依赖`pkg/goroutine/FLOW.md`摘要已冻结，transport无适用FLOW。本轮没有新购云资源。
组件诊断是本机Darwin ARM64、Apple M4、Go1.25.11；两版组件计时未交错，不能据此断言稳定耗时收益。
双进程验收在同机Docker Linux ARM64，Go1.25.11、GOMAXPROCS=4、GOGC=100；
客户端CPU0–3，服务端CPU4–7，各3GiB内存，loopback同网络命名空间，无主机端口和Observer。
静态ARM64程序使用缓存Debian amd64 rootfs；探针确认实际进程架构arm64。

固定基线客户端比较两版服务端，三类探针分别共用相同源码重新构建并记录SHA256。
16调用者、池16、活动连接1/16，服务并发64，队列4096项/64MiB，排队5s、执行30s、调用方2s。
写请求CancelRunning=false，读控制=true。主组64B预算写，每拓扑4对AB/BA和两版各1对A/A，
纯计时每窗10s，不采profile或MemStats。大包65537B、读64B、无预算64B各两对AB/BA、两种拓扑。

## 候选边界与并发

`Server`仅将带预算帧送入`EnqueueInbound`。服务通过原有payload、stopped、context、
队列及保留字节准入检查后，才为CancelRunning=false的请求安装专用监听。
读请求继续使用原监听；失败准入不调用监听源；无预算服务入口不变。
Request和requestEntry布局没有新增字段，原标准Context没有被替换，
Deadline、Done、Err、Value、Cause及运行中读/写策略沿用原实现。

连接只为已准入请求创建一个队列监听owner，并替换该请求表中的取消入口。
取消与安装使用单独的读写同步门：多个取消可并行，安装排他；
取消context子树时不持请求表锁，其他请求的TrackInbound/Finish仍可前进。
安装发现请求已取消或已退出跟踪时退回标准AfterFunc，防止漏掉先到的终结事件。
队列必须先撤销监听再调用Finish；原完成函数不因这个候选而修改。
连接关闭仍先取消父context，再逐个调用请求表内的取消入口。回调使用已有受管理RPC service任务。

专用监听覆盖显式取消，标准预算timer继续负责Context截止语义；队列的单个共享timer覆盖
已索引请求的最早调用方截止时间以及原FIFO排队时限。
截止时间堆和位置map都在Service.mu下操作，只容纳已准入预算写请求，O(log Q)更新、O(Q)空间。
出队、取消、超时和Stop均移除索引并清除引用；公共FIFO仍决定执行顺序。
旧timer回调重新核对当前owner及时间，不能提前结束替换请求。

## 回归证据

在仍使用旧CancelInbound顺序的安装原型中，固定“取消已取出旧函数、安装随后完成”的交错，
测试明确失败：`in-flight cancellation missed installed queue hook: calls=0`。
这证明候选必须处理新引入的安装竞争，并不表示原基线已有这个监听缺陷。
最终测试再次在不协调安装的原型上失败，在候选上通过。

测试覆盖安装前后取消/断连、Finish先到、监听撤销、其他请求跟踪的前进性、
成功写/读/无预算及各失败准入分支、非队首先到期、取消后复用、旧回调和Stop索引清理。
已有真实连接协议集成覆盖预算协商、排队容量回收、读中断及写独立完成。
完整transport race集成测试通过。最初测试夹具曾将mutex阻塞误当作synctest可判定的静止事件，
两次运行被主动停止；修正夹具后重验red/green，原日志和说明仍归档，未将夹具卡住归因于产品死锁。

## 一次定时器快路径修订

仅当调用方截止时间堆为空时，直接执行原基线排队timer逻辑，跳过新增的组合截止时间选择。
其余字段、同步和算法不变。目的在于区分公共timer分支是否解释控制负载代价。
对预算读/无预算写各运行两组三版本窗口：base→candidate→fast，再fast→candidate→base；
共12窗，每窗10秒。该批采用三版本组内比较，不伪装成此前两版本AB/BA。

|负载|版本|吞吐中位RPC/s|P99中位ms|
|---|---|---:|---:|
|预算读1连接|base|161,459.06|0.811250|
|预算读1连接|candidate|166,284.65|0.749833|
|预算读1连接|fast|167,573.75|0.750875|
|无预算写1连接|base|173,279.39|0.474917|

本批基线预算读有一窗约157,248 RPC/s，无预算写有一窗约168,220 RPC/s，明显低于此前窗口。
原候选在本批也随之显得有利；不能选择本批较好相对值覆盖先前四对无预算尾延迟退化。
fast相对原候选的无预算吞吐/P99没有一致改善；第二组fast相对base的P99仍增加0.59%。
观测未发现cgroup节流，CPU pressure和loadavg有变化，尚未证明基线变慢的原因。
全部窗口保留，既不删除不利样本，也不宣称修订已解决公共路径问题。
修订未重复整套主负载验收，因此不能引用原候选主组成绩充当修订版成绩。

## 决定与最终交付

成功准入边界解决了上一轮的读/拒绝额外分配，但增加专用取消同步与截止时间索引仍有公共路径风险。
两版运行时均撤销，候选特有的索引/安装回归仅存证据包；标准预算context和原监听保持原样。
最终新增 `TestInboundCancelAllowsUnrelatedTracking`，用受控慢取消验证同一连接上无关请求
的TrackInbound与Finish仍可完成。该测试在请求表锁包围cancel的错误实现上明确失败：
`unrelated tracking stalled behind cancellation`，在原运行时通过。
这个失败证明新回归能防止未来扩大锁范围，并非声称基线已有此缺陷。

后续若继续，应先用独立进程的CPU/阻塞证据区分公共排队路径和同步成本，缩小可验证的单点假设，
再讨论实现；不要直接继续扩展本轮候选或以分配收益替代其他负载的性能门槛。
本轮只测试本机loopback，不能据此推断原生x86跨主机或完整集群容量。
最终只有测试/文档变化，没有用户可见行为改变，不新增Changelog。

## 验证与复现

原候选最终完整transport race集成通过（`gate-race.log`）。修订的`fast-race.log`中
transport包通过，但临时writeprobe包因与构建脚本改写导入并发而编译失败，不能记为整套通过；
探针删除后，最终基线交付串行运行以下两项，均通过：

```sh
GOWORK=off GOTOOLCHAIN=go1.25.11 go test ./pkg/transport/... -count=1
GOWORK=off GOTOOLCHAIN=go1.25.11 go test -race -tags=integration ./pkg/transport/... -count=1 -timeout=4m
```

校验逐调用者计数、实际架构/工具链、固定客户端、负载参数、服务选项、MemStats算术、
