# 十万成员发送禁令场景：建群瓶颈

基线 `c9b5793b1`。原 E2E 保持 100,000 成员、256 Hash Slots、12 物理
Slots 与五分钟工作预算。诊断期间仅开启本机 debug API，采集 15 秒 CPU profile。

## 证据与假设

- 每 1000 个成员分成约 256 个 UID Hash Slot 提案；只允许两个同时提交。
- 采样时成员投影只有 5000 行，Slot 提案约 1520 次；平均 apply 数十毫秒。
- 15.13 秒 profile 只采到 1.64 秒 CPU（10.84% 单核），没有主要全量扫描热点。
- 请求栈等待 membership proposal future；Slot 栈等待 Raft 日志 durable write。

因此优先减少同物理 Slot 的重复提案与持久化往返，不增加并发或改为弱持久化。
这不是证明所有耗时都来自磁盘，最终收益必须由相同原 E2E 重跑验证。

## 修改前固定失败场景

1. 同物理 Slot 的不同 Hash Slot 成员合并，物理 Slot 不同的绝不混合。
2. 每个提案最多 128 条、编码最多 256 KiB、UID 总字节最多 64 KiB；超出
   拆分，不能扩大既有提案并发上限。重复 UID 保持幂等。
3. 新批量 FSM 必须是 upsert 的版本/重新加入语义，不能偷换成 person ensure。
   不回退个人 read/hidden/activation 状态，不用过期 SourceVersion 复活成员。
4. 命令里的任意 Hash Slot 不归当前物理 Slot 所有时整批拒绝，不部分写入。
   迁移只 apply 对应 Hash Slot；其他 Hash Slot 的成员不能被带入目标。
5. 编解码规范化、重复身份、截断/恶意 payload、超量与超字节都要有拒绝证据；
   新命令进入 operator inspection 注册表。匹配版本集群，不支持旧新混部。
6. 原十万成员 E2E 必须从全新数据目录跑完成功 fanout、两种禁令和解禁后完整
   历史；保留之前失败证据，不通过加长预算或减少成员数改判通过。

## 修复与结果

`Node.UpsertUserChannelMemberships` 按同一不可变路由快照解析去重 UID，
将同物理 Slot 的成员索引合并为命令 69。每个命令最多 128 行、256 KiB、
64 KiB UID 字节；先完成全部分块，再用原有两个 worker 提交。正常的 1000
成员片段不再为每个逻辑 Hash Slot 单独提交。没有改变订阅者写入顺序、
持久化承诺或发送权限读取强度。

FSM 校验所有嵌入的 Hash Slot，原子拒绝包含外部所有权的批次；迁移增量
回放只写目标 Hash Slot。沿用 `UpsertUserChannelMembership` 的版本、个人
进度保留和重新入群规则，没有使用 create-only 的 person ensure 命令。
编解码、检查工具和注册目录均覆盖新命令；须匹配版本，不新增旧数据迁移。

| 检查 | 结果 |
| --- | --- |
| 原十万成员 E2E（修复前） | 305.93 秒失败，`POST /channel` 截止时间到，禁令断言未执行 |
| 原十万成员 E2E（修复后） | 26.01 秒通过；原成员数、拓扑、五分钟预算均未变 |
| 用户禁言拒绝 | reason 25，6 个权限事实，0 个处理的接收者，无 ID/序号 |

| 正向对照 | 禁言前成功投递处理满十万成员；解禁后成功；完整历史只有两条获准消息 |
| 单/三节点禁令、非副本接入 | 通过，主禁令 69.12 秒，非副本 15.72 秒 |
| 会话目录与成员状态 | 单节点 3 项、多节点 3 项通过，覆盖隐藏、移除/重新入群、故障恢复及非副本接入；独立目录性能门禁未启用 |
| FSM/Node 完整单元包 | 通过 |
| 定向 race、vet | 通过；Mac 链接器既有 LC_DYSYMTAB 警告保留 |
| `flow-doc-contracts` | 81 compliant，0 invalid，10 个建议行数警告 |

JSON 中成功 SEND 的 `recipient_rows` 是 ACK 前后即时采样，异步 fanout 可在
采样之后完成；十万正向投递条件由独立 `RequireMetricAtLeastEventually`
断言证明，不能将该即时差值解释成最终投递总数。拒绝期间不存在前一成功
发送的未完成 fanout；场景先等待十万处理完成再设置禁令。

这些耗时是本机单次功能回归记录，不能据此宣称 SEND P99/CPU 性能门槛
通过。5000 活跃频道、4500 SEND/s、三组同等一致性对照及剩余故障矩阵
仍见[完整验收核对](2026-09-24-send-ban-acceptance-audit.md)。
