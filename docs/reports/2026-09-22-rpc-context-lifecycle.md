# RPC 完整取消生命周期归因与读执行上下文复用

本轮找到并实施一项可取消读RPC的冗余初始化优化：复用执行上下文的取消函数响应服务停机，
避免再套一层取消上下文。Linux ARM64隔离生命周期测量稳定减少 **464B、5次分配/读请求**。
独立进程64B读RPC吞吐中位提升 **3.99%**，P99下降 **32.92%**，四对均同向，
同场景A/A吞吐变化约±0.53%。本轮候选通过本地验收后合入。

收益针对 `CancelRunning=true` 且配置执行超时的请求。默认写请求路径保留独立执行，
**原先默认写请求的跨主机吞吐回退仍未解决**，本轮不是其恢复证明。
复测未发现稳定的大包或写请求回退信号，但不能由有限样本保证任意场景零回退。

[完整证据](assets/rpc-context-lifecycle-2026-09-22.json)包含基准源码、驱动、补丁、构建哈希、
全部输出、失败/通过日志、8份原始pprof及解析、清理回执。原始目录：
`/Users/tt/.codex/visualizations/2026/09/22/rpc-context-lifecycle`。
54个纯计时窗口共 **76,754,191次成功RPC**，两个独立剖析窗口共 **7,080,789次成功RPC**；
全部零错误、零样本截断。本轮未购买云服务器。

## 链路、假设与实现

`TrackInbound` 创建独立请求预算/取消上下文并登记请求ID；`watchQueue` 注册队列取消监听；
`handle` 创建执行超时。原实现对可取消读请求又创建一个子上下文，用来接收服务Stop。
前一个执行上下文已经提供独立取消函数，因此后一个上下文及其惰性初始化属于冗余。

三个预测分别是：队列首次注册具有初始化成本；读执行存在重复子上下文；优化仅影响特定读路径。
通过分阶段测量、真实服务生命周期、独立进程读写对照依次验证，没有跳过取消、超时或请求去重。
`pkg/cluster/net` 将 ChannelLastVisible、ChannelConversationHeads、ChannelCommittedReads、
SlotStatus 四类服务配置为可取消读请求；未改变这些服务的配置或Cluster语义。

候选只修改 `Service.handle`：有执行超时则将其返回的cancel函数交给 `context.AfterFunc(s.ctx, cancel)`；
没有执行超时、且请求上下文来自服务外部时，仍先派生自己的可取消上下文。
退出时先解除服务监听，再取消执行上下文；不能取消调用者父上下文。
队列FIFO、所有权、准入、去重、断连、已启动写操作的完成语义均保持。

源版本 `6426acc06`。根AGENTS与只读参考的 `pkg/cluster/FLOW.md` 摘要已冻结；transport没有适用FLOW。
候选在隔离worktree内实施，先完成验收，才合入目标分支。

## 分阶段测量

Go1.25.11，GOWORK=off，CGO关闭，Linux ARM64静态测试程序，CPU4–7、GOMAXPROCS=4、
GOGC=100、容器3GiB。使用已有Debian amd64 rootfs，程序确认arm64；不是在仿真运行amd64程序。
两套基准每项500ms、各3轮、前后共84行。基线先测，候选后测；其耗时属于隔离观察，
不拿该顺序下的微小ns差异作网络性能验收。

RPC阶段基准依次执行真实上下文创建、监听注册/撤销、handle，不运行pump/编码；
在终结前访问Done，模拟真实响应路径的惰性初始化。因此队列监听的增量不同于前轮只调用Err的基准。
Conn生命周期基准调用真实TrackInbound、Enqueue、pump、executor与Finish，复用测试支架/载荷，
不运行TCP编解码。两套结果不能作为实际网络RPC的完整分配总量。

|累计阶段|无调用预算：基线→候选 B/次数|有调用预算：基线→候选 B/次数|
|---|---:|---:|
|上下文与Done|208/3 → 208/3|384/5 → 384/5|
|加队列监听|608/8 → 608/8|784/10 → 784/10|
|加写执行超时|880/12 → 880/12|1056/14 → 1056/14|

包含真实请求登记与服务调度后，读生命周期从1664B/21次降到1200B/16次，两种调用预算配置相同。
写生命周期分别保持1072B/14次、1248B/16次；单独登记保持240B/4次、416B/6次。
这验证了冗余来自读执行层，并没有优化或删除请求表、队列监听。

## 独立进程验收

Apple M4 Docker VM；客户端CPU0–3，服务端CPU4–7，各GOMAXPROCS=4、GOGC=100、3GiB上限；
两进程独立GC、同一网络命名空间loopback、无主机端口。固定基线客户端、预算开启，16预热连接、
16调用者；服务并发64、队列4096项/64MiB、队列期限5s、执行期限30s、调用期限2s。
共同探针只增加read开关，显式映射到CancelRunning；其他参数与前轮一致。

每窗10s，逐响应校验完整载荷、保存每调用者样本数，100万样本/调用者即失败。
分位数采用 `floor((n-1)*p)`。构建、测试、隔离基准、pprof均不与纯计时重叠。
Observer关闭，客户端分配不等于服务端分配；配对顺序交替，不跨批次拼接均值。

该场景达到预先约定的稳定收益标准。

首批写64B的P99三对均升高，中位+7.85%，因此没有直接合入。交换起始顺序的复测P99中位−0.32%，

本地验收依据是明确且稳定的读小包收益，以及复测未显示稳定的大包/写请求回退。
单个不利配对仍完整保留；有限工程对照不构成正式统计显著性或所有负载下零回退保证。
本轮没有重做原生x86跨主机基线，因此不能外推云上容量。

## 单独服务端剖析

另起两个读64B运行，各18s；分别取8s CPU、alloc_space、mutex、block共8份原始pprof。
只在服务端开启剖析，诊断窗口不计入上表。CPU为各自窗口的采样比例，分配为进程累计采样，
包含初始化且不与完整18s客户端计数严格对齐，不据其绝对量计算每RPC成本，也不相加嵌套累计比例。

|调用栈|CPU累计占比：基线→候选|分配字节累计占比：基线→候选|
|---|---:|---:|
|TrackInbound|4.89% → 5.68%|13.77% → 18.10%|
|watchQueue|2.41% → 2.73%|23.61% → 28.90%|
|handle|13.51% → 11.28%|39.13% → 23.15%|
|context.WithCancel|3.11% → 0.96%|25.88% → 5.62%|

这一分布与消除读执行冗余上下文的预测一致，精确分配节省由前述隔离测量确认。
