# RPC 新旧版本与连接拓扑对照

固定旧版客户端后，新版服务端在1连接、16连接下的吞吐中位分别下降 **19.78%、17.77%**，
八对新旧比较全部下降。旧版单连接也有约90%的执行器唤醒栈调度等待占比，因此上一轮的
高占比本身不能解释版本回退。独立分配诊断在两种拓扑、两轮交换顺序中都观察到新版
**每次RPC多约689B、8次分配**。下一步优先隔离请求跟踪和排队取消的新增分配成本。

这是一轮因果方向筛选，未实现或验证新的运行时修复。分配增长已测得，但尚未证明它解释
全部吞吐回退；不能仅凭profile热点删除取消、截止时间或资源回收保证。
本次仅保存报告和证据，没有产品行为变化，因此不新增Changelog条目。

## 版本、假设和复现边界

旧版：`68662c4c8fa7a447ac2864c7352789ae4a5021b7`。
当前版：`e5fe7eb74c18a10f2735d5f4ce4130d54795edae`。
当前transport、go.mod/go.sum与上一轮`4226b8cc1`一致；两版本依赖文件也一致。
两份根AGENTS的SHA256相同，摘要保存于证据包；transport无适用FLOW。
两版在独立worktree构建，产品源码没有修改。

预先提出三个预测：单连接高调度等待在旧版已存在；新版新增等待伴随回退；等待变化较小，
而新增分配/CPU/同步工作是更值得定位的方向。本轮通过旧/新×1/16连接交叉比较区分这些预测，
没有关闭当前版本已有的正确性机制来模拟旧版。

Apple M4、Linux ARM64 Docker VM（10 vCPU）、Go1.25.11、GOWORK=off、CGO=0。
静态ARM64程序在已有Debian amd64 rootfs中运行，双方程序输出均确认arm64。
客户端CPU0–3、服务端CPU4–7，各GOMAXPROCS=4、GOGC=100、内存上限3GiB。
两端是独立进程，使用同一网络命名空间的loopback，不映射主机端口。

固定64B写RPC、16调用者、PoolSize=16，以固定shard选择1/16个活动连接槽并预热。
客户端始终是旧版，RequestBudgets关闭，调用期限2s；完整校验回显字节和调用者计数。
服务并发64、队列4096项/64MiB、执行期限30s。当前版排队期限5s、CancelRunning=false；
旧版没有后两项字段，共同探针通过JSON配置兼容，实际支持情况和最终选项逐窗保存。
**相同输入不代表两版生命周期语义相同**，这些新增机制的成本正是比较对象。

每种拓扑4对AB/BA纯计时，每窗10s，再分别加入旧版/新版各一对A/A，共24窗。
profile、trace、分配诊断各用独立窗口，不混入纯计时结论。只验证了这个本机小包写负载，
不是完整集群容量测试；也不能把此处ARM64 loopback回退幅度当作此前原生x86跨主机结果。

## 纯计时结果

下表中位仅使用四对AB/BA，A/A另列，不混入版本中位。

|活动连接|旧版RPC/s|新版RPC/s|变化|旧版P99 ms|新版P99 ms|
|---|---:|---:|---:|---:|---:|
|1|213,266.88|171,073.39|−19.78%|0.182980|0.630229|
|16|254,670.29|209,402.70|−17.77%|0.194605|0.454021|

1连接四对吞吐变化：−18.58%、−20.60%、−20.51%、−21.29%。
16连接：−19.77%、−12.17%、−16.73%、−19.19%。P99八对均上升。
A/A吞吐变化：1连接旧版−5.15%、新版+2.30%；16连接旧版+5.98%、新版−0.10%。
所有版本配对的下降幅度均超过本批观测到的A/A幅度，构成本机稳定回退信号。
A/A样本少，不能将其当作严格置信区间。延迟受噪声影响更大，1连接旧版A/A P99曾上升66.84%。

纯计时窗口前后服务端cgroup累计CPU用量之差，除以完成RPC数，中位如下：

|活动连接|旧版CPU µs/RPC|新版CPU µs/RPC|变化|
|---|---:|---:|---:|
|1|4.788|5.762|+20.34%|
|16|6.926|8.574|+23.78%|

这是服务端容器观测区间的CPU成本近似，包含预热、前后采集及少量后台工作，
并非精确handler CPU时间。未将profile窗口的cgroup值用于此表，因为那里还包含profile
下载辅助进程。运行前后CPU状态无quota throttling；loadavg和CPU pressure原文一并保存，
但不能排除宿主机干扰。

## 调度等待：旧版已有热点，16连接复测方向不一致

每个版本/拓扑单独采集3s trace，另在16连接交换为新版先运行，复测一对。
使用Go1.25.11 `go tool trace -pprof=sched`，分别导出delay和contentions两个样本维度。
该profile表示goroutine进入Runnable后等待被调度的时间，并归因到唤醒/启动栈。
这里的contentions是调度事件数，**不是mutex争用次数**。

|窗口|版本|Executor.Submit累计等待占比|平均等待 µs/事件|
|---|---|---:|---:|
|1连接|旧|90.52%|27.056|
|1连接|新|89.23%|33.019|
|16连接首轮，旧先|旧|68.72%|7.885|
|16连接首轮，旧先|新|45.58%|7.833|
|16连接复测，新先|旧|68.16%|7.507|
|16连接复测，新先|新|46.41%|8.216|

旧版单连接已经有高等待占比，支持“原有拓扑特征”的预测。当前单连接平均等待增加约22%，
可能是新增CPU工作的后果，也可能参与回退，尚未隔离其因果关系。
16连接两轮平均等待变化为−0.66%和+9.45%，方向不一致；不能选取首轮就宣称调度等待不变，
也不能用较低的累计占比宣称调度更快。比例受其他栈的等待量影响。
这些数值也不能与吞吐变化直接相减来计算各因素贡献。

Submit唤醒栈的累计等待不是Submit自身CPU耗时，更不是ants缺陷的证明。
本轮证据不足以支持继续将“固定批次Gosched”作为主要修复方向；上一轮该候选已因收益不稳定撤回。

## 服务端分配：跨拓扑重复的新增成本

另构建相同的分配诊断探针，固定旧版诊断客户端；每种拓扑做两轮新旧比较，第二轮交换顺序。
每窗5s，预热后通过loopback HTTP触发服务端GC并读取MemStats，所有调用结束后再读一次，
用TotalAlloc/Mallocs增量除以客户端成功数。没有给每次RPC增加计数器或诊断回调。

|活动连接|旧版B/RPC|新版B/RPC|新增B/RPC|旧版分配次数/RPC|新版分配次数/RPC|
|---|---:|---:|---:|---:|---:|
|1|887.98|1,577.25|689.27|17.950|25.977|
|16|888.95|1,577.74|688.79|18.007|26.013|

服务端分配字节增加约77.5%～77.6%，次数增加约8次。前后HTTP和少量后台工作包含在增量中，
终点也可能仍有少量请求所有者收尾，所以是每RPC成本近似。起点强制GC可能清空池，
这些诊断窗口的吞吐不参与性能验收。客户端自身的分配输出也不能当作服务端数据。

独立CPU/alloc_space/mutex/block诊断各取旧/新×1/16连接，共16份原始pprof。
16连接新版alloc_space累计样本中，`watchQueue`占32.95%，`TrackInbound`占7.81%；
嵌套的`context.AfterFunc`占24.99%，不能与watchQueue相加。
CPU累计样本中，`Service.Enqueue`从旧版3.61%升至新版9.52%，新版watchQueue为2.77%，
TrackInbound为2.10%。CPU百分比不是每次RPC的绝对耗时，不能仅凭份额量化回退贡献。

旧版没有这些新增请求跟踪/排队取消路径，当前采样表明它们承担可观分配成本。
结合独立MemStats和CPU区间数据，这比单独观察执行器等待占比更能指导下一项实验。
累计alloc_space包含启动且取样时点不同，未将其总字节除以18s客户端调用数冒充精确B/RPC，
也没有声称已将约689B精确分解到各个结构体。

## 验证、归档与下一项实验

46窗共 **87,110,531次成功RPC**：4窗冒烟825,909次，24窗纯计时50,951,393次，
4窗profile 14,462,174次，6窗trace 12,301,631次，8窗分配诊断8,569,424次。
全部零错误、零样本截断，16调用者计数与总数一致；服务端全部正常退出、无OOM。
构建源码/二进制、窗口输出及profile/trace哈希均已核对，分配归一化公式逐窗校验通过。
本轮没有产品代码或永久测试改动，因此没有重复全量Go测试；这些真实进程窗口验证本轮探针。
原始回退的自动性能回归门槛和修复仍未完成。
