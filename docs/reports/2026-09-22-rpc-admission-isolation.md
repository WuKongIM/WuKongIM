# RPC 请求登记、保留内存与队列通知隔离

本轮完成四组单变量诊断，没有找到足以采用的通信层优化。保留请求登记、
保留内存准入和状态版本号，未修改生产代码。此前云上 64B/16 并发相对原始
基线的 7.71% 吞吐回退仍未解决。本轮没有购买或启动云资源。

源码基线为 `ae68a044c`，接续
[上一轮生命周期隔离与状态轮询优化](2026-09-22-rpc-lifecycle-and-status-polling.md)。
[机器可读证据](assets/rpc-admission-isolation-2026-09-22.json)包含源文件摘要、
全部输出、诊断补丁、构建/运行脚本、统计和 profile 摘要。

## 方法与假设

同一 Apple M4 的 Docker Desktop Linux ARM64 VM，Go 1.25.11，
GOMAXPROCS=4，绑定 CPU 0–3、内存上限 6GiB。复用已有 Debian amd64
rootfs，仅直接执行静态 ARM64 测试程序；输出确认 `goarch: arm64`。
它不等价于先前的 x86 跨 ECS 环境。

采用原有 `BenchmarkTransportBudget`：64B echo，16 个预热连接，1/16 个调用者，
服务并发 64，队列 4096 项/64MiB，队列预算 5s，执行预算 30s，单次调用
超时 2s，请求预算开启、Observer 关闭。每个调用校验完整响应内容。

每个诊断版本只改变一个机制，通过仓库外的 Go overlay 构建固定二进制，
不更改测试夹具。五个版本顺序轮换三轮，每个用例 2s，计时与编译、测试及
profile 采样完全分开。共 30 个计时用例、12,725,553 次计时 RPC，均无错误。
预热及基准自校准调用未计入该总数。

预先提出并分别测试的假设：

1. **请求表登记成本**：保留请求超时上下文，绕过连接内请求表及其锁。
   若该表是主要瓶颈，吞吐应明显改善。此探针会失去请求 ID 去重和远端显式
   取消，不能用于生产；连接父上下文和预算计时器仍保留。
2. **保留内存记账成本**：绕过 retained 字节/数量记账、对应观测及终结时的
   服务锁。若这段记账是主要瓶颈，应改善并发吞吐。此探针保留队列限制，
   但移除 queued + executing 的总保留内存限制，不能用于生产。
3. **重复队列通知成本**：仅在 FIFO 从空变为非空时发送唤醒通知，其他
   排队和执行行为保持不变。若重复通知是瓶颈，应获得吞吐收益。
4. **状态版本号争用**：将服务排队、保留内存及 inflight 的版本更新替换为零，
   隔离全局原子操作。该探针破坏观测顺序语义，只能用于 Observer 关闭的诊断。

## 结果

`ns/op` 是吞吐折算耗时，不是单次 RTT。变化按同轮组的中位耗时倒数计算，
不能把不同轮次或租约的绝对数字拼接为优化收益。

| 版本 | 串行中位 ns/op | 并发中位 ns/op | 并发范围 ns/op | 并发吞吐变化 | 并发 B/op | 分配次数/op |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 当前基线 | 12,356 | 3,569 | 3,541–3,579 | — | 2,826 | 45 |
| 绕过请求表 | 11,675 | 3,521 | 3,516–3,712 | +1.36% | 2,794 | 44 |
| 绕过保留内存记账 | 12,289 | 3,624 | 3,499–3,780 | −1.52% | 2,826 | 45 |
| 仅空队列唤醒 | 12,931 | 3,544 | 3,488–3,559 | +0.71% | 2,826 | 45 |
| 禁用服务状态版本号 | 12,208 | 3,650 | 3,547–3,664 | −2.22% | 2,826 | 45 |

绕过请求表减少约 32B 和一次分配。串行中位吞吐提高 5.83%，但首轮串行方向
相反；并发第三轮也方向反转。三个样本不足以证明稳定收益，更不足以支持
牺牲取消或去重。取消保留内存记账未改善并发中位吞吐。

仅空队列唤醒的并发吞吐三轮均略好，幅度只有约 0.6%–1.5%；串行三轮均
变慢，中位吞吐下降 4.45%。这个交换不值得引入当前实现。禁用版本号的
并发中位结果也更差。没有将任一探针升级为生产候选。

这些结果不证明相应机制“没有成本”，也不排除多种机制叠加、负载差异和
架构差异。结论仅是本轮单变量证据不足以支持改写或削弱它们。

## 独立 profile

计时矩阵结束后，使用基线二进制对 64B/16 并发另行采样。基准窗口配置为
5s；包含准备和自校准的 CPU profile 实际持续约 10.53s。采集 CPU、累计
alloc_space、mutex（fraction 10）与 block（rate 1ms），四份均成功解析。
profile 同时包含客户端和服务端，其计时结果不纳入上表。

- CPU flat：系统调用约 30.87%，`runtime.nanotime` 约 16.10%。虚拟机时钟与
  系统调用占比不能直接外推到云上 x86，也不能为了减少采样热点而省略预算检查。
- `Service.Enqueue` 调用栈占 mutex 累计等待约 60.25%；这表示被采样的
  锁等待分布，不是整体 CPU 或吞吐损失比例。绕过记账和减少通知没有带来
  相应吞吐改善，因此不能仅按该热点比例决定拆锁。
- `context.WithDeadlineCause`、`context.AfterFunc` 累计分配分别约 28.74%、
  13.25%，调用栈可能重叠，不相加。生命周期分配仍存在；上一轮删除监听
  已证明减少分配并不自动改善此微基准吞吐。
- block profile 包含空闲 writer、连接终止监听和基准等待，不能把所有阻塞
  时间都视作排队故障。

## 交付与后续边界

仅提交报告与证据。所有不安全探针保留在工作区之外的 `debug` 目录，未加入
Go 包，也未部署。生产代码和现有取消、FIFO、内存上限、写操作完成语义均保持。
无需为文档变更重跑全仓库测试；诊断二进制成功构建，30 个用例均通过内容及
错误校验，证据输出哈希和样本数已校验。

下一次归因应先建立与云上回退相匹配的原始版本/当前版本对照，并对双端的
CPU 时间、调度等待、锁持有区间及网络等待做时间对齐。当前本地 loopback
fixture 没有复现跨 ECS 网络和 x86 架构，不能继续凭其亚百分比差异选择修复。
如果需要新增云测，应是明确范围的一次受控对照；本报告不构成购买请求。
任何后续实现仍需通过取消/停止/内存归属回归，再检查小包吞吐、P99 和大包
回退场景。此前云测结果与未完成项继续以
[三版本云测报告](2026-09-21-transport-response-cloud-validation.md)为准。
