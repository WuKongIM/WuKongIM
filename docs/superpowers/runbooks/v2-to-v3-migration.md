# v2 → v3 离线迁移操作手册

适用于未经修改的 `v2.2.5-20260422`（提交
`a888f89533d0e7d1b2030e06504ca97f1ad891d4`），迁入全新的 v3 集群。
不要求升级现有 v2。迁移工具和目标 v3 服务必须使用包含本迁移实现的同一代码版本构建。

## 已验收交付版本

2026-09-08 测试集群最终候选为 HA78；源码提交、构建参数和二进制摘要由交付包的
`manifest.json` 固定。先在解压目录运行 `sha256sum -c SHA256SUMS`，再使用包内
配套的 `wkcli migrate` 与 `wukongim`。不要把本次测试数据或私有计划用于其他部署。

实际三节点迁移测试、故障恢复、Demo 全历史分页和重新同步结果，以及本次回退路径，
见 [最终分页验收报告](../reports/2026-09-08-v2-migration-history-pagination.md)。
原始 v2 未升级。100 GiB／四小时性能项及后置插件验收仍按各自条件完成。

普通历史 API 的 `more` 按可见消息判断；每页应以前一页最早序号减一继续向前，
直到 `more=0`。超长隐藏记录区间可能触发有界扫描错误，遇到错误保留当前游标并
报告失败，不能作为历史结束。Demo 还可用“加载更早消息”读取未产生滚动条的首屏
之前的历史。清除旧消息缓存和游标，保留凭据，重新同步后再验证新消息递增。

## 流程与边界

正式消息副本仅缺少尾部时，可在新计划中显式配置
`"history": {"leader_quorum_prefixes": true}`。它要求当前 Leader 与正式副本
多数拥有完全一致的完整历史，其他副本是严格前缀，并核对源 Slot、当前配置和
完整保留配置命令。源行全部留档，归档重建重新核验；元数据仍严格比较。
当前 Leader 缺失历史、同任期换主、成员变更、删除、内容冲突或中间缺洞均不能
通过这个选项。它证明持久历史一致性，不证明历史客户端 ACK。详细条件见
[CLI 说明](../../../cmd/wkcli/internal/migrate/README.md#正式消息副本的严格前缀差异)。

已确认恢复的空 Leader 频道使用单独的 `history.recoveries`，不能仅开启前缀选项。
每个决定必须填写 `owner_hash`、`identity_sha256`、`capture_digest`、`proof_digest`、
`source_node`、`messages`、`history_sha256`。`owner_hash` 和 `source_node` 按字符串编码，消息条数为 JSON 数字。
摘要和条数来自原始捕获诊断，指定节点必须属于保存完全相同历史的正式多数；
当前 Leader 必须无消息且无尾记录。prepare 和归档重建都重新计算证据；未使用的
决定、摘要漂移、删除、内容冲突、中间缺洞及未知异常均拒绝。选择报告中的
`history_prefixes.recovered` 单列恢复频道数，原诊断不被改写成历史 ACK 证明。
修改计划后使用新的工作空间，不沿用旧计划的准备状态。

插件问题可以暂缓排查，但不能在最终 `prepare` 中跳过。活动插件不会提前遮挡
后续源业务副本比较；失败命令仍以退出码 1 返回，stdout 可包含 `status=blocked`
及已完成的检查。`replica_comparison_complete=true` 仅证明原业务副本比较完成，
不证明转换或插件兼容通过。插件未解决时 selection digest 为空且不生成 PREPARED。继续处理消息时可用
`dedupe-plan` 报告 v5 的 `protocol_impact`，核对已批准排除 CMD、去重后仍然
保留的协议字段。其数量按节点物理行分别统计，不相加为逻辑消息总数。
2026-09-08 最新范围：本次暂不迁移流消息，设置 `messages.exclude_streams=true`，
包含旧 15 条流主消息及其他带流标志的消息。保留消息从 1 连续编号，原生新消息
接续新尾部；普通读删位置同步映射。RedDot 对保留消息直接映射到 v3 既有字段。
目标 v3 必须全部使用带 RedDot 通用修复的版本（Channel RPC v8 / Exchange v4），
不能混用旧节点；这不要求修改或升级源 v2。
详见 [消息字段影响报告](../reports/2026-09-07-v2-migration-message-protocol-impact.md)。

遇到 `plugin.business_mapping` 时，诊断 JSONL 和样本的 `plugin` 字段提供
插件身份、配置 JSON、模板、方法及完整原记录的 SHA-256，不输出配置值。
用 `no_sha256` 对应同一插件，再比较各 `node_id` 的 `config_json_sha256`。
该配置指纹忽略 JSON 对象键顺序及空白，保留数值写法；指纹不同需要核对，
不能直接认定副本损坏。插件配置属于各节点，不能用 Slot Leader 或更新时间
自行覆盖其他节点的配置。改变节点数时必须明确目标配置分配，并完成插件
启动、用户绑定、实际钩子与回复行为验证后，才可解除兼容阻断。

保留各节点不同插件配置时，在计划顶层显式填写：

```json
"plugin_nodes": [
  {"source_node": 1001, "target_node": 1},
  {"source_node": 1002, "target_node": 2},
  {"source_node": 1003, "target_node": 3}
]
```

每个目标节点必须且只能指定一个配置来源；同一源节点可以供多个目标使用。
例如单节点来源扩容时可把源 1001 分配给目标 1、2、3；三节点来源缩容时，
必须显式选择保留哪个节点的有效设置，不能按更新时间自行合并。全部原节点及
原配置仍完整捕获、归档，未用于目标分配的来源也不会丢弃。配置来源不等于
业务数据的权威副本。prepare 与归档重建保持选定来源的启用状态和时间戳。
本次已批准 `wk.plugin.ai-example` 在全部目标节点使用源 1001 的有效配置，
在同一计划顶层增加（其他插件继续按节点映射）：

```json
"plugin_configs": [
  {"plugin_no": "wk.plugin.ai-example", "source_node": 1001}
]
```

该项只替换配置，不替换所映射来源的启用状态和时间戳。配置来源及每个被映射
的源节点必须已有该插件；统一配置可取自未分配给目标的原节点。找不到指定源、
重复指定或映射来源缺少注册时拒绝。三份原配置及选中源行
的指纹仍完整留存。策略改变后需使用新工作空间与新归档，不能沿用旧计划产物。
导入经原生 Store 写入 `<data_dir>/plugin-state`，随后才封存目标文件指纹。
重复导入必须精确匹配，已有配置改变时拒绝覆盖。`verify` 从原始归档重新推导
配置，逐节点核对内容、启用状态、时间戳以及缺失/多余文件，并输出独立的
`plugin_settings` 校验摘要。这些步骤不部署程序，也不解除业务插件兼容阻断。
工作空间中的分配记录包含原配置，须按源库一样保护。

`PluginUser` 绑定已有独立的数据迁移路径：先按源 Slot 0 确认正式副本及
两个业务索引一致，再按 UID 分配到目标的原生 `plugin_binding` 表。
绑定保留 UID 和插件编号，目标时间戳沿用 v3 的毫秒精度，原物理 ID 与完整
纳秒时间保留在归档。`verify` 从源记录重新计算期望值，检查用户查询、插件
反向分页查询、副本数及启动快照；只迁移绑定不等于插件业务兼容通过。

还必须核对插件实际在哪个节点执行。原版 v2 的离线插件调用跟随接收用户的
UID Slot Leader；v3 的投递任务可在不同节点触发插件。现场示例插件把节点配置
中的名字写入回复，即使三份配置按原映射完整保留，同一用户的回复也可能变化。
本次三节点及重启演练已复现这种差异；三个目标统一采用源 1001 有效配置的
候选也已通过演练，并已获批准；上述 `plugin_configs` 将该选择固定到计划。
插件程序使用原字节与 SHA-256，以 `<plugin_no>.wkp` 命名供原生扫描器识别。

当前工具已为这个具体程序实现显式兼容规则。新计划的 `plugin_artifacts` 必须
列出全部源节点的原文件：`source_node`、`plugin_no`、绝对 `path`、
`bytes: 11856443`、上述已审计 SHA256，以及
`profile: "wk-ai-example-receive-linux-amd64-v1"`。每节点只允许该版本 0.0.1、
Receive 方法、优先级 1 和 name-only 配置；仍需 `plugin_nodes` 完整分配及
已批准的 `plugin_configs` 统一配置。其他程序和竞争绑定不自动放行。
程序完整分块归档；移除原数据库及原程序访问后仍可重建、安装、验证。
目标通过原生目录扫描 `plugins/<plugin_no>.wkp`，不修改 v3 存储或运行逻辑。
目标运行环境必须与该 Linux/amd64 程序一致。离线 verify 将检查完整 SHA256、
大小、0500 权限、目标数量和多余文件；随后仍执行真实登录、收发及重启验收。
详细测试边界见[程序迁移报告](../reports/2026-09-08-v2-migration-plugin-artifacts.md)。

**本次批准范围的开发与隔离功能验收已完成，尚未生产切换。**
真实源全量离线校验、Web SDK 缓存重置、原插件及重启/拓扑测试见
[最终验收报告](../reports/2026-09-08-v2-migration-final-acceptance.md)。
实际业务 App 缓存适配及运维切流需按下文落实；100 GiB 性能测试按约定延后。
当前候选遵守原有 v3 消息格式，迁移专用的
摘要版本和历史前缀恢复扩展已撤回。RedDot 使用原生字段，通用冷历史恢复和空历史
API 已分别通过对照复现/修复测试。历史失败报告保留作诊断过程证据，不能把其
已解决问题继续当作当前阻断，也不能把早期候选的通过结论套用到当前候选。
真实源 prepare、归档导出、独立导入/重试/校验及隔离运行均已完成，证据见
[阻断项台账](../reports/2026-09-08-v2-migration-blockers.md)及
[归档演练](../reports/2026-09-08-v2-migration-archive-rehearsal.md)。

停止业务写入 → 原版 v2 收敛并排空通知 → 正常停止全部 v2 节点 →
保存完整停机备份 → `diagnose`（列出兼容缺口）→ `prepare` → `export` → `import` → 停机 `verify` →
隔离启动 v3 并做业务验收 → 切换流量。

导入前先创建目标 `data_dir` 的父目录，目标目录本身保持不存在。
例如 `data_dir=/srv/migration-targets/node1` 时，只创建 `/srv/migration-targets`；
工具排他创建 `node1` 并写入导入身份，不能预建一个无迁移身份的空目录。

单节点集群和多节点集群使用相同流程。可以改变节点数，但第一版不向已有业务数据的
v3 集群合并，不做在线增量追赶。`prepare` 是离线扫描，不是运行在 v2 内的准备接口。

源基线是原版 v2 权威节点停机后的可恢复持久化业务状态。旧版本没有提供的历史
ACK、历史多数派确认或外部 Webhook 送达证据，工具不会补造。源 Raft 状态用于
判断源是否可迁移；目标使用新的原生 Controller / Slot / Channel 初始化状态。

## 全量诊断与报告边界

原 v2 已停机时，可先运行：

```sh
/srv/tools/wkcli migrate diagnose --plan /srv/wkmigrate/plan.json \
  --workspace /srv/wkmigrate/diagnostic-workspace > /srv/wkmigrate/diagnostic.json
```

`diagnose` 对每个可完整读取的节点扫描全部行，逐项记录身份、业务字段、插件、
源索引、消息唯一性、历史序号、会话可见性和事件游标问题；磁盘排序统计重复项总数。
不会在第一个业务冲突处退出。单个节点无法读取或校验不变性时，继续检查其他节点，
但报告标记 `incomplete`，其计数不包含失败节点的未完成捕获。

摘要每类最多保留 5 个样例，`findings_file` 指向完整 JSONL，`findings_sha256`
校验该文件。节点 ID、原行 ID 和 owner hash 使用 JSON 字符串，避免大整数精度丢失；
不打印用户标识、凭据、原始键及消息内容。每类记录影响、节点分布和数量。
`duplicate.*` 统计重复组，`duplicate_member.*` 记录第一行之外的每个参与者；
`index.expected_collision` 统计冲突索引键。不同问题可能落在同一记录上，不能将
所有类别相加当作需删除的消息数；各节点物理计数也不能当作去重后的业务数据量。

退出码 1 表示发现阻塞或扫描不完整，仍输出完整报告；参数/工作空间/输出 I/O 失败
可能无法生成最终报告。退出码 0 仅表示 `checks` 所列检查未发现问题。
`scan_complete` 表示源扫描完成，不表示权威业务副本已经选定，`not_certified`
明确列出后续未验收项。权威配置检查失败只给出状态项，不冒充全部权威冲突计数。

该命令不会建立目标目录，也不会生成 `PREPARED` 或转换完成标记。
诊断工作空间使用独立身份，不能拿来执行 `prepare/export/import`。处理兼容缺口后，
仍必须在另一个工作空间通过完整 `prepare`、导入、独立校验及业务/恢复验收。
仅开启旧表排除时仍检查主消息；本次额外开启 `messages.exclude_streams`，流主消息不导入。

## 带迁移标记频道的专项核验

对于已停机且无法升级的 v2，可独立核验当前 `MigrateFrom/MigrateTo` 非零的频道：

```sh
/srv/tools/wkcli migrate authority --plan /srv/wkmigrate/plan.json \
  --workspace /srv/wkmigrate/authority-workspace > /srv/wkmigrate/authority.json
```

工具两轮加锁读取原库，要求两轮文件校验和相同。第一轮读取频道配置及保留的 Slot
配置命令，核对原版应用位置；第二轮只为这些频道保存消息摘要，按原序号比较全部
持久化字段。输出的 `details_file` 包括配置日志、每个不同序号的副本摘要、每频道
统计及分类，`details_sha256` 绑定完整 JSONL。消息内容和凭据不写入该报告。

- `consistent_formal_replicas`：配置证据满足本核验规则，正式副本完全一致。
- `learner_lag_only`：满足相同配置证据，正式副本一致，差异仅为学习者连续前缀落后。
- `conflict`：配置互相矛盾、同序号内容不同，或存在不能解释的额外消息。
- `insufficient_evidence`：缺少配置日志、来源节点、连续历史或明确转换依据等。

`candidate_node` 仅是有证据支持的备份候选来源；不写入迁移选择清单、不清除原库
标记，也不生成 PREPARED。`prepare` 使用原始捕获记录独立重建证据；不能直接使用该报告放行。保留日志缺失时，即使副本
一致，也不能冒充已经核实完整配置变更链。该命令不覆盖未标记频道、业务元数据及
事件投影，也不证明历史客户端 ACK；原 v2 重启会用消息尾部初始化频道应用进度。

退出码 1 仍可输出完成但未解决的报告；扫描失败为 `incomplete`。退出码 0 只说明
本次限定范围的检查通过。工作空间必须与其他命令分开，不能用该报告直接切换。

真实备份的逐频道分类与剩余历史配置问题见
[专项核验报告](../reports/2026-09-07-v2-migration-source-authority.md)。

## 1. 准备二进制、配置与源备份

迁移工具当前支持 Linux 和 macOS 的文件锁。在本实现所在的仓库工作目录构建：

```sh
GOWORK=off go build -o /srv/tools/wkcli ./cmd/wkcli
GOWORK=off go build -o /srv/tools/wukongim-v3 ./cmd/wukongim
/srv/tools/wkcli migrate --help
```

停机前记录原部署的版本凭据、所有节点 ID、数据目录、业务 DB 分片数和有效配置
（包括环境变量）；二进制部署者无需查找源码提交。新工具允许省略 `source_commit`，
使用内置的原版 v2 读取规则，仍逐项检查实际格式与业务兼容性。报告及归档中的提交号
标识读取规则，不代表自动鉴定了旧二进制。已知其他版本或自定义修改仍需单独评估。
旧版工具（包括 v3.0.0-beta.12）仍需显式字段；下方示例保留该兼容写法。
新工具在计算计划摘要前补齐省略值，保持旧计划及归档的身份；显式不同提交仍会报错。

阻断所有业务写入口，等待原版集群应用完日志、完成正在进行的拓扑变更并排空通知；
通过原有 API 留存代表性历史消息、权限、会话、CMD 和事件同步响应。然后正常停机，
关闭自动拉起，再复制每个节点的完整数据目录。不能复制仍在写入的 Pebble 目录。

收集所有节点目录到迁移机或可靠的本地挂载路径。文件锁用于拒绝仍被进程打开的
源库；工具还会在扫描前后校验文件清单。不要修改原数据来绕过检查。

**迁移归档不是完整文件系统备份。** 它保存原始数据库行、索引、管理记录、权威
选择与文件校验清单，不包含原始全部 WAL 文件字节。回滚必须保留完整停机备份。

目标运行配置需要另行核对。数据库转换不会自动验证或搬运 TLS、监听/公布地址、
网关鉴权开关、Webhook 地址/网络保护、插件程序、推送配置及业务方服务配置。原生 Webhook 不提供签名；外部签名代理需要单独迁移和验证。

## 2. 固定迁移计划

示例 `/srv/wkmigrate/plan.json`（地址、路径、分片数按实际部署填写）：

```json
{
  "version": 1,
  "source_commit": "a888f89533d0e7d1b2030e06504ca97f1ad891d4",
  "sources": [
    {"node_id": 1, "data_dir": "/srv/v2-snapshots/node1", "shard_count": 8},

```

- 源 `shard_count` 是原业务 DB 的实际分片数；工具单独盘点 Slot 日志分片。
- `created_at` 是这次新集群的固定创建时间，重试时保持不变。
- 目标节点 ID 为 1–1023；端口为 1–65535；所有目标节点同时是 Controller voter 和 data node。
- `hash_slot_count` 固定 256；物理 `slot_count` 为 1–256；两类副本数均不能超过节点数。

- 第一版在迁移机上安装全部目标目录。复制到对应目标主机时必须保留计划中的
  **同一绝对数据路径**，包括完整 `controller`、`slotraft-snapshots` 和迁移标记。
  Controller 原生快照清单包含路径，不能只移动消息库或随意改目录。

计划内容、源目录内容和工作空间绑定。要改变计划，使用新的工作空间、归档和
全新的目标目录重新执行；不要删除完成标记来复用已有目标。

### 明确排除旧流存储

长期升级的 v2 数据目录可能残留 2026-03-07 移除的 `Stream`（`0x1101`）和
`StreamMeta`（`0x1201`）表。默认拒绝这类业务数据。只有操作方明确决定不迁入
旧流分片和元数据时，才在计划顶层加入：

```json
"exclusions": {"legacy_stream_storage": true}
```

这条规则**仅排除两张旧流表**，不删除 `Message` 表中的主消息、ID、序号、
`StreamNo` 或起始正文，也不排除新版消息事件状态、游标和插件。主消息仍必须通过现有 v3 的兼容检查；
非空 `StreamNo` 等无法完整保留的字段会阻止完成，不允许清空字段来通过。
本次用户已明确整条流消息暂不迁移，必须同时启用 `messages.exclude_streams=true`。
该策略按 Setting 流标志或旧 StreamNo 排除主消息，关联事件投影/游标随之排除；
与保留消息共享事件身份时阻止完成。排除的源行仍完整归档，不改写流字段来通过检查。

排除记录仍完整保存在迁移归档的原始源行中。`prepare`、归档 manifest 的
`selection.excluded_from_target` 和 `verify` 的 `excluded_from_target` 报告规则、
按表计算的各源副本物理行数量及包含源节点身份的原始行 SHA-256。数量不能按
三个副本相加解释为三倍业务消息。报告成功只证明约定范围内的迁移通过。

规则参与计划和源选择摘要；变更规则必须使用新工作空间、归档和空目标目录。
排除不会放宽旧格式、键值身份、原分片或未知表检查，也不会绕过插件兼容检查。

## 3. prepare：离线检查并生成转换清单

```sh
mkdir -p /srv/wkmigrate/reports
/srv/tools/wkcli migrate prepare \
  --plan /srv/wkmigrate/plan.json \
  --workspace /srv/wkmigrate/scratch \
  > /srv/wkmigrate/reports/prepare.json
```

命令执行以下检查：

1. 检查节点目录、文件锁、原始表格式、业务读取所需索引、分片清单和文件校验和。
2. 对照持久化集群配置、Slot 日志及应用位置，确定源权威副本。
3. 解析所有业务身份，比较当前副本组的业务记录；冲突或无法确定权威时停止。
4. 合并原版可恢复的会话尾部意图，只补原本不存在的记录。
5. 校验消息 ID、序号、保留前缀、事件游标等映射，并在磁盘工作空间生成原生目标记录。

原版恢复时跳过的空用户 ID 会话缓存，会完整保存在源归档中，并在
`preserved_physical_rows_by_reason.originally_ignored_empty_uid_conversation`
记录数量；不为它创建目标会话。其他会话格式和已读位置检查继续生效。

原版黑名单等接口可独立写入频道成员计数，不要求存在频道属性。仅包含计数列的
`ChannelInfo` 行完整归档，在 `preserved_physical_rows_by_reason.derived_channel_counters`
记录数量，不凭它创建频道属性。个人权限的频道身份可从原用户或设备 UID 确定；
身份目录中的个人频道只是关联线索，不表示创建了频道或授予权限。实际成员仍须
完成身份、原业务索引、分片及权威副本核对。空身份、只有部分身份或策略列的
频道记录不会被当成计数跳过。采用新工具重新准备时使用新的工作空间及归档，
避免复用旧工具生成的身份目录和选择摘要。

原版 `Conversation` 的 UID/频道 ID 以及 `ChannelClusterConfig` 的频道 ID
可以包含非 UTF-8 字节。迁移工具按原字节保留它们，内部关联键、目标记录及独立
比较使用带版本的无损编码，避免 JSON 替换字符改变身份或合并不同记录。原索引、
分片与副本核对仍须通过；未证明兼容的空 ID、零类型业务记录及其他字段继续报错。
已覆盖归档导入、原生库重新打开和快照恢复；不代表这些标识的 API/SDK 行为已验收。
旧工具的工作空间和归档不能混用，必须重新 `prepare` / `export`。

原版 `ChannelClusterConfig` 可以持久化零配置版本，也可以保存非空 ID 的类型 0
配置。工具保留这些原值，依据所属 Slot 与配置副本逐字段比较确定来源，不把版本
改成 1，也不将旧配置直接作为 v3 拓扑。配置副本不一致、缺少完整版本字段、无效
Leader 或零任期仍拒绝。这个源控制配置规则不适用于消息、会话或频道策略。

迁移工具必须遵守现有 v3 存储格式、消息 ID 唯一性、序号与恢复约束。不能为了
v2 数据增加特殊目标记录或放宽校验。空 ID、重复 ID 等无法等价导入的记录必须
报告为兼容缺口；不能擅自改写 ID、序号或额外排除数据。本次授权范围包括旧 `Stream` 分片和
`StreamMeta`、CMD/流消息，以及按原序号判定的旧重复项；其他业务数据不在排除范围。

成功时退出码为 0，JSON `status` 为 `prepared`，包含源清单、选中/归档记录数量和
转换摘要。`cutover_ready` 仍为 `false`。此阶段不创建目标集群，不操作原 v2 服务，
也不会自动替你证明停写或外部通知送达。

当前明确阻止完成的业务边界包括：空 ID、重复消息 ID、非 1 起始的保留历史、
现有 v3 无法完整保留的非零 `sync_once` / `expire`、非空
`StreamNo` / `topic` 等消息字段、非正数消息时间戳，以及旧 `User.PluginNo`、插件全局方法或非空有效配置缺少兼容映射、独立非零 unread
计数未证明等价、CMD 删除边界、已有历史但缺少原会话的成员可见性歧义、无状态投影
的事件游标、不能被原生接口等价表达的记录。错误必须解决后重做，不能把业务记录
改为管理归档来“通过”。普通空群、普通会话、CMD 已读位置和删除位置已有样本覆盖。

预检和后续归档重建都会核对设备、成员、会话、消息的业务读取索引及原分片，
拒绝缺失、错误指向、跨分片消息 ID 遮蔽及未知格式。原版截断留下且不改变查询结果
的消息索引可以完整归档；时间、计数等管理索引只核对格式，不宣称其历史值准确。

纯插件名称、版本、配置模板等描述可以归档；注册方法或有效配置不能归档代替迁移。
原版持久化的插件禁用标记不足以证明全局钩子不影响业务，也不能绕过预检。

通知 DB 非空或磁盘通知队列未排空会阻止迁移。即使队列深度为零，也不能据此断言
外部系统已经接收全部通知；迁移不会重放旧通知。

## 4. export：封存源归档

```sh
/srv/tools/wkcli migrate export \
  --plan /srv/wkmigrate/plan.json \
  --workspace /srv/wkmigrate/scratch \
  --archive /srv/wkmigrate/archive \
  > /srv/wkmigrate/reports/export.json
```

必须沿用成功 `prepare` 的工作空间。再次检查源未改变后，发布有校验和的分块归档、
清单和完成标记。缺块、损坏、冲突或缺完成标记的归档不能导入。

归档含设备凭据、消息正文等业务数据，应按数据库备份管理访问权限。导出后可以
卸载源目录；`import` / `verify` 只从归档重建源事实，不要求源目录在线。

## 5. import：生成全新 v3 数据目录

```sh
/srv/tools/wkcli migrate import \
  --plan /srv/wkmigrate/plan.json \
  --workspace /srv/wkmigrate/scratch \
  --archive /srv/wkmigrate/archive \
  > /srv/wkmigrate/reports/import.json
```

迁移机变化时，可以使用新的工作空间，从完整归档重建输入；计划保持不变。
导入按目标原生分片和副本布局写入业务数据、Controller / Slot 启动快照以及原生
消息日志。每个节点完成持久化后才发布完成标记；不完整标记的节点拒绝启动。

中断后，在目标服务始终未启动、计划和归档未变的条件下，重跑同一命令。
已完成节点会校验文件指纹后跳过，部分节点按相同记录重试。已经启动或被修改的
完成目录拒绝被覆盖。若目录创建后、身份标记落盘前发生断电，工具会保守拒绝无身份
目录；保留现场，另选全新输出目录和计划重做。

导入期间不要启动任何目标节点，也不要让自动部署系统拉起服务。

## 6. verify：独立核对全部业务数据与启动产物

**在首次启动 v3 之前**执行：

```sh
/srv/tools/wkcli migrate verify \
  --plan /srv/wkmigrate/plan.json \
  --workspace /srv/wkmigrate/scratch \
  --archive /srv/wkmigrate/archive \
  > /srv/wkmigrate/reports/verify.json
```

校验器重新解码归档中的权威源记录，不使用转换器的目标行或成功计数作为预期值。
逐字段核对所有目标副本：凭据、成员/权限、会话/CMD 状态、事件投影和消息完整内容；
检查 message ID 与幂等索引、消息尾部和提交边界、完整 proposal 摘要链和成对索引、
频道运行元数据及多余/缺失记录。
同时核对 Controller WAL/快照、Slot 快照与已核对的业务元数据、整套发布文件指纹。

成功为退出码 0、`status: "offline_verified"`，报告给出源摘要、校验摘要、节点数、
消息副本数和各表副本数。逻辑消息数与所有副本之和不同，例如三副本会计三次。
任何差异都不能视为成功。启动过的库不再是这份初始生成状态，不能拿它重新执行
离线初始化校验；保留首次报告与验收前的目标副本。

`cutover_ready: false` 是有意保留的边界：离线数据相等不等于服务已通过业务验收。

## 7. 隔离启动并验收后切流

为每个节点准备 `wukongim.toml`，确保以下值与计划一致：`node.id`、`node.data_dir`、
`cluster.id`、`cluster.nodes`、`cluster.initial_slot_count`、`cluster.hash_slot_count`、
`cluster.slot_replica_n`、`cluster.channel_replica_n`。这些启动参数受迁移标记校验。
保留初始 bootstrap 配置；后续拓扑调整遵循 v3 原生集群流程。

在不接生产流量的环境执行，至少保存这些证据：

| 验收项 | 通过标准 |
| --- | --- |
| 集群健康 | 所有节点就绪，Controller 与每个 Slot 有实际 Leader，副本/任务收敛 |
| 原凭据 | 用原 token 和相同 device_flag 登录成功，错误 token 拒绝 |
| 历史数据 | API 分页读取首尾和跨页消息，ID/seq/正文/协议字段与源基线一致 |
| 权限和会话 | 成员/黑白名单/禁言行为正确；空群、删除会话、已读和 CMD ACK 符合基线 |
| 事件 | `/message/eventsync` 的投影、顺序、游标、私有过滤符合源基线 |
| 新写入 | 新消息 ID 不与旧记录冲突，seq 超过原尾部；同幂等键重试不重复 |
| 重启与故障 | 重启后结果不变；多节点集群丢失一个 Leader 后恢复读写且历史不丢 |

自动黑盒矩阵使用未经修改原版 v2 的停机 fixture，实际运行四个 CLI 命令、v3 进程、
HTTP 和仓库 Go WKProto 客户端，覆盖 1→1、1→3、3→1、3→3、3→5。它不能代替你的 SDK
版本、插件、Webhook 和生产配置验收。测试写入应使用隔离演练副本或明确的测试账号。

切流由运维在所有报告与业务验收通过后执行。切流前源备份完整、v3 无新业务写入时
可恢复原 v2；v3 已接受业务写入后，不能直接切回旧 v2，否则会丢失新写入。
第一版不提供反向增量迁移。

## 资源与未验证项

转换使用磁盘工作空间和有界批处理；仍需要同时容纳源备份、归档、工作空间及目标
全部副本。原生 Slot Raft 快照桥接当前上限为每个物理 Slot **256 MiB 元数据**，超出
会停止而非无限扩张内存。事件同步每页保留投影上限为 8 MiB。
迁入消息按原生恢复预算分批，每个不可拆分 proposal 的原生编码与传输计费均不超过
1 MiB；单条消息若超过该预算，会在预检拒绝，不能仅凭 payload 大小判断是否可迁。

100 GiB 源业务数据、停写至完成校验 ≤4 小时是约定的性能验收目标，**尚未执行**。
在测试环境提供前，本机小样本测试只证明对应功能，不构成该吞吐或停机时长承诺。

### 重复消息的删除与序号影响

已授权的业务策略是 MessageID 或频道、发送者、非空 ClientMsgNo 重复时保留最新一条，最新按同频道原 MessageSeq 判断。先以独立工作空间运行 `wkcli migrate dedupe-plan --plan /absolute/plan.json --workspace /absolute/dedupe-workspace`，核对候选删除清单、保留摘要、流主消息影响及 `survivors_requiring_renumbering`。物理副本逐节点核对，数量不可直接当作去重后的业务总数。明细有 SHA-256，源文件摘要由停机读取器前后核对；不能以该报告代替源权威性确认。

dedupe-plan 不会删源数据、改写序号或导入目标。用户随后已授权重排及 CMD 排除，prepare/import 的新显式策略见下文。跨频道 MessageID、保留候选相互淘汰和原序号缺口仍阻止完成。

本次真实备份核对结果见 [消息去重规划报告](../reports/2026-09-07-v2-migration-message-dedupe.md)。

### 已批准的 CMD 排除与序号迁移

在新计划中设置 `messages.keep_latest_duplicates=true`、`messages.exclude_cmd=true`、`messages.exclude_streams=true`、`messages.compact_sequences=true`，并保持 `exclusions.legacy_stream_storage=true`。使用全新工作空间重跑诊断和准备。源索引及权威性门槛不变；读取固定原版 CMD 标记/路由，不按正文推断。

转换先省略 CMD 历史，再保留剩余重复消息的最新记录，连续编号。普通已读和删除位置按“旧位置之前（含）仍保留的消息数量”映射；旧 CMD 会话及同步位置省略。所有原记录都留在归档，保留消息 ID、正文和事件投影不作额外删改，源本来存在的缺口仍拒绝。

prepare 输出带校验和的 `sequence_mapping`。从归档可运行 `wkcli migrate export-map --plan /absolute/plan.json --workspace /absolute/map-workspace --archive /absolute/archive` 重建同一映射。本次已批准按迁移代次清空旧消息缓存和序号游标，保留登录凭据，再从 v3 重新同步。清理只作用于客户端消息副本与派生同步位置，不删除服务端历史或凭据；不能只迁移服务端数据库便宣布客户端旧序号问题已处理。在落实客户端方式之前，不切换业务。本次先按 docs-site 固定的 Web SDK 1.3.5 验收；它自身不持久化消息，会话也保存在内存，业务 Provider 的历史翻页、会话同步和外部缓存仍须处理迁移代次。

客户端执行顺序已确定：先停止发送并关闭旧连接，记录本次计划/选择摘要作为新的
迁移代次；保留 UID、token、设备标识和业务登录状态，删除旧消息缓存、会话列表
派生缓存、历史翻页位置和消息同步序号。Web 客户端随后重新加载页面，确保原 SDK
单例及内存中的去重、会话状态被重建，再使用原凭据连接 v3。

第一次同步不得提交旧 `message_seq`、历史翻页位置、已读/删除序号或旧的待发送
更新请求。重新获取 v3 会话与服务端已读状态，历史从无旧游标的请求开始，后续
只沿用 v3 返回的位置；全部首次同步成功后才标记该账号完成新迁移代次。中途失败
仍保留“尚未同步完成”状态，重新同步，不能退回旧游标。未发送草稿与附件队列不
属于历史消息缓存，须保留并在恢复发送前确认其业务状态，避免重放已发送消息。

清理范围由业务客户端存储结构决定，不能对整个 origin 调用 `localStorage.clear()`
或删除整个账号目录来代替按表/键清理；那样可能同时删除登录凭据。当前验收用的
Web SDK 自身没有持久化消息库，演练里的缓存来自原始源消息构建的私有测试存储，
不是对未知业务 App 数据库结构的认证。实际客户端发布时应按本规则绑定其消息
缓存和游标存储，并确认旧版本客户端不会携带旧游标重新连接。


verify 使用独立工作空间命名空间从选出的原始记录重建映射，核对保留消息、原 ID、正文、新连续序号、普通已读/删除边界及目标 CMD/重复记录缺失性；不会使用转换侧映射作为唯一正确性依据。

新策略及真实备份结果见 [CMD 排除与序号转换报告](../reports/2026-09-07-v2-migration-cmd-and-sequences.md)。

## 从捕获记录重建来源证明

新版本 prepare 在同一源库锁和文件摘要检查范围内捕获原始 Slot 配置命令，
把节点身份、原分片数、命令数量和有序摘要纳入 capture/归档。
对带标记频道，在选择业务行之前重新核验前后配置命令及完整消息历史。
只支持证据完整的补充副本场景，以及满足完整前序证明的历史 Leader 自指标记。
结果的 `selection.authority_digest` 绑定此次完整 capture；不接受外部候选清单替代证明。

使用新的 prepare 工作目录。旧归档若没有命令证据，不能放行带标记的频道。
源目录卸载后，归档重建仍重做相同核验；命令缺失、内容变化或位置错误会在选择业务行之前失败。
原始配置和标记保留归档，v3 放置仍由目标计划生成。此检查通过不代表凭据、会话、消息协议
或在线 API/恢复验收通过，不能提前切换真实集群。


### 原元数据读取规则

现场已同意采用 v2 冷启动凭据。需要处理重复会话和已证明的空频道管理记录时，
在新计划中加入：

```json
"metadata": {
  "device_lookup": "v2_cold_start",
  "conversation_lookup": "v2_active_slot",
  "conversation_list_limit": 1000,
  "archive_empty_channels": true,
  "archive_user_timestamps": true
}
```

先从旧部署环境及配置确认 `conversation.userMaxCount`。本次停止的三个旧容器
没有相关环境覆盖，备份挂载目录没有 wk.yaml，固定 v2 源码默认值为 1000。
会话的原唯一索引必须有效；正式副本的已读、删除、类型、未读等业务状态必须
一致；当前 Leader 普通列表版本必须与该状态兼容。原列表先限数量后去重，
工具拒绝超限用户，不通过增大计划上限掩盖被旧列表截断的数据。待恢复的新普通
会话也计入上限。原记录保持归档，目标边界应用已批准的消息序号映射。

空频道证明要求信息/配置成对、无业务属性和引用、正式副本及原命令完整一致；
最后保留的已应用配置必须解释现存完整记录。只归档通过证明的管理记录，不
吞掉真实权限、业务插件或其他身份异常；流主消息只能按独立的显式消息策略排除。新计划使用新的工作空间和
归档；先完成 prepare，再 export，目标仍须独立 verify 及启动/API/SDK 验收。
服务器空间不足时可对源文件的完整镜像在隔离机器预检，但必须逐文件校验，并
记录镜像摘要与原停止备份完全一致；这不会代替现场目标的验收。

`archive_user_timestamps` 对应已批准的旧管理数据归档范围：原 User 的创建、
更新时间在 v3 原生用户表没有对应字段，各节点原值完整留档，不挑选或改写时间。
仅这两个字段不参加用户业务副本比较；身份、用户插件字段、设备凭据仍严格校验。
查看 `selection.archived_user_timestamps` 的用户物理行数、时间字段数和摘要，
并要求脱离源库后的归档重建报告相同。该摘要覆盖各节点完整原用户行；不证明
原时间副本一致，也不解除活动插件或其他业务冲突。现场证据见
[用户时间字段报告](../reports/2026-09-08-v2-migration-user-timestamps.md)。

### 流消息排除后的连续序号验收

逐频道以原序号排序保留消息，核对目标序号严格为 `1…N`、消息 ID/正文等保留字段一致，并核对已读/删除边界的保留前缀映射。全部消息被排除的频道目标尾部为 0。启动目标后首次追加必须为 `N+1`；完整重启后再次追加必须接续最新尾部。单节点集群与三节点集群均验证，不能用只检查最大序号代替全范围比较。

本次范围和本机结果见 [流消息排除与连续序号报告](../reports/2026-09-08-v2-migration-stream-exclusion.md)。其后已在用户指定测试服务器完成迁移及 Chat Demo 验收，见本手册开头的最终报告；实际业务 App 缓存适配仍按本手册执行。

### 全流频道的空历史 API

迁移候选包含 main 提交 `065317e0b` 已有的空会话兼容修复。授权成员查询无消息频道时，单条和批量历史同步应返回 `messages: []`，批量项不带错误；非成员仍被拒绝，真实路由/存储故障不能变成空结果。首次发送由原生路径建立消息运行状态，分配序号 1；导入工具不预写占位消息。

本机已对实际导入的全流频道验证 HTTP 历史、旧会话同步、未读清零、正常发送和两次完整重启，覆盖单节点集群与三节点集群。见 [验收报告](../reports/2026-09-08-v2-migration-empty-history-api.md)。这不代替真实源全量 prepare、现场集群或业务 SDK 的验收。


### 限定补齐缺失会话

用户已批准真实捕获中唯一一个有 100 条保留历史却无原会话／待恢复意图的成员，
补齐一条全部历史已读的原生会话。使用 `metadata.missing_conversations` 绑定
完整捕获、用户／频道 SHA256 和 `retained_tail=100`。保留历史读取范围及成员
权限；会话新增到列表，初始未读为 0。原始时间和会话 ID 不虚构。
所有原副本重新检查，证据变化或任何其他未批准缺失会话仍阻断；归档重建和独立
校验重新计算原始事实。原生存储及运行模型无须修改。
详见 [缺失会话核对报告](../reports/2026-09-08-v2-migration-missing-conversation.md)。


### 原独立未读计数、替代链及只隐藏列表的缺失会话

经明确业务决定可启用 `messages.resolve_duplicate_chains`，要求同频道递增替代链
最终只指向一条实际保留消息；原直接替代关系、最终项与所有原记录均保留。
`sequence_mapping.duplicate_chain_proof` 提供链证据旁文件，读／删除边界仍按
旧位置之前的保留消息数量映射，不前移到替代消息。

`metadata.derive_unread_from_boundaries` 使用 v3 未读规则，并在源归档保留旧独立
计数；`archived_unread` 绑定原行数量与摘要，不能报告为旧计数完全等价。

上述 `missing_conversations` 还支持 `visibility: "hidden_until_new_message"`。
它保留历史访问和成员关系，在新的业务消息到来前仅隐藏会话列表，内部恢复屏障不计为新消息，显式激活可显示；
不会把历史标为已读或已删除。缺少原已读位置时保持默认 0，新消息后的未读按原生
规则计算。原副本会话被仅归档时，须同时匹配精确副本归档决定；待恢复意图仍拒绝。
省略 visibility 仍表示旧的全部历史已读恢复，不可混淆。新隐藏标记扩展成员存储及
RPC 编码，必须全节点配套部署；回退使用整组迁移前数据与程序。
