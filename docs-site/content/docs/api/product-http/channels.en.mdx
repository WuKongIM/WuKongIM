## Goal and completion criteria

This page publishes 10 Channel-management operations calibrated against current source and entry tests. The trusted product backend should be able to distinguish mutations to Channel metadata, durable subscribers, temporary subscribers, and derived allow or deny lists, while keeping browsers away from Product HTTP.

## Trust and compatibility boundary

These routes have no business-authentication middleware of their own. `security: []` in OpenAPI records that runtime fact; it is **not permission for anonymous public access**. Put the listener behind a trusted network or authenticated proxy and let the product backend validate tenant, operator, Channel, and UID authority.

The compatibility paths retain `blacklist` for the domain denylist and `whitelist` for the allowlist. Integer flags mean true only when exactly `1`. `ChannelSubscriberAddRequest.subscribers` and `ChannelAllowlistMutationRequest.uids` use `NonBlankUID`; its `\S` pattern matches the runtime rule that rejects whitespace-only members.

Successful mutations return `{"status":200}`. Validation, routing, and storage failures use `CompatibilityError`, normally `400 {"msg","status":400}`. The restore-maintenance fence uses `MaintenanceError`: `503 {"error":"maintenance","message":"restore maintenance is active"}`.

## High-scale semantics

- `/channel/subscriber_add` can replace a snapshot with `reset=1`, but a product backend should bound and retry input batches for a 100,000-member group instead of relying on one unbounded JSON request;
- remove-all operations use bounded internal traversal and never return the full member set;
- ordinary durable subscribers and `/tmpchannel/subscriber_set` temporary members occupy different namespaces;
- allowlists and denylists are separate member sets derived from the Channel key;
- a person Channel (Type 1) does not accept ordinary subscriber management.

## Existing routes intentionally deferred

The following routes exist, but their current behavior is not strong enough for this Beta contract:

| Path | Why it is deferred |
| --- | --- |
| `POST /channel/info` | It validates no fields and performs a full replacement, not the partial patch its name can suggest. |
| `POST /channel/delete` | Key validation is weak; the behavior is terminal disband rather than physical deletion, and its error text is inaccurate. |
| `POST /channel/subscriber_remove` | An omitted `channel_type` reaches type 0, unlike add's compatibility default to group. |
| `POST /channel/blacklist_set` | It validates only `channel_id`, allowing type 0 and an empty list into the replace path. |
| `POST /channel/whitelist_set` | It has the same issue as blacklist set and lacks a consistent strong-validation contract. |
| `GET /channel/whitelist` | Query fields are not validated and it aggregates the complete list into an unbounded response, unsuitable for 100,000-member scale. |

Source-code existence does not imply public support. Do not fill these gaps from the legacy `resources/api/openapi.json`; that file contains removed routes and obsolete response shapes.

## Errors and troubleshooting

- **A 400 carries unstable text:** branch on the HTTP status and record only redacted `msg`; do not enumerate or parse the current Chinese or English message text.
- **A subscriber operation fails for Channel Type 1:** person-Channel membership belongs to person relationships and messaging paths, not group-style subscription mutation.
- **subscriber_add rejects a temporary member:** use `/tmpchannel/subscriber_set`; do not send `temp_subscriber=1`.
- **503 maintenance:** back off within a bound and observe `/readyz`; never bypass into a node-local path.
