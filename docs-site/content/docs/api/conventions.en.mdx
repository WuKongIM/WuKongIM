This page applies only to the Product HTTP subset used by the Phase 12 golden sample. It records the real compatible surface without promoting other internal or historical routes to a stable public API.

## Goal and completion criteria

When finished, you should call `/user/token`, `/route`, and `/channel/messagesync` correctly from a trusted backend, parse each endpoint's own response, and avoid conflating HTTP success, protocol Reason Code, and durable message commit.

## Prerequisites

- The Product HTTP base URL points to a WuKongIM HTTP listener inside a trusted network; the local sample uses `http://127.0.0.1:5001`.
- The caller is the sample localhost BFF or a product backend with authenticated service identity.
- JSON POST requests set `Content-Type: application/json`.
- Production uses TLS and access control at a reverse proxy, API Gateway, or service mesh.

## Addressing and format

| Convention | Golden-path behavior |
| --- | --- |
| Base URL | Local development uses `http://127.0.0.1:5001`; all paths start at `/` |
| Request format | POST endpoints use UTF-8 JSON; `/route` uses a GET query |
| Response format | JSON, but the three compatible endpoints have no universal envelope |
| UID / Channel ID | Product-owned strings; a person-Channel query uses the peer UID |
| Channel type | The golden-path direct chat uses numeric value `1` |
| Message sequence | Ordered only inside one Channel, never globally |

Do not force compatible responses into one `{ data, error }` type. `/user/token` returns `status`, `/route` returns address fields, and `/channel/messagesync` returns a synchronization window and message array. Error bodies can also differ by entry stage.

## Identifiers and numbers

- `uid` is a product identity, not a nickname, connection ID, or device ID.
- `channel_id` plus `channel_type` identifies a Channel; the client view of a person Channel uses the peer UID.
- `message_seq` is a per-Channel cursor.
- A synchronized message has both `message_id` and decimal string `message_idstr`; JavaScript should preserve the string form to avoid large-integer precision loss.
- HTTP JSON represents message Payload through the compatible Go `[]byte` encoding. The golden-sample adapter decodes it; that transport encoding is not your product schema.

## Retry rules

| Operation | Retry condition |
| --- | --- |
| `GET /route` | Back off and retry network failures or temporary `5xx`; success is not product authorization |
| `POST /user/token` | Retry the same identity intent only from a trusted caller; do not mint a fresh token in a loop |
| `POST /channel/messagesync` | Retry a read failure with the same cursor; tolerate overlap with realtime delivery |

This subset declares no universal Idempotency-Key request header. Message sending uses the SDK, whose logical message identity must be retained by the sender; these three HTTP routes do not replace that behavior.

## Expected result

The caller checks HTTP status first, then parses endpoint-specific JSON. A `2xx` means only that the HTTP operation completed. It does not turn CONNECT into production-grade authentication or prove that a message reached a realtime recipient or was read.

## Troubleshooting

- **JSON parsing fails:** retain HTTP status, `Content-Type`, and a bounded redacted response tail; do not assume every error has an `error` field.
- **`400`:** correct the request fields, UID, Channel, or cursor instead of retrying unchanged forever.
- **`503 maintenance`:** the cluster is behind the restore-maintenance fence. Back off and observe `/readyz`; do not bypass into a node-local path.
- **Synchronization contains duplicates:** overlap with online delivery is allowed; merge by message identity and Channel sequence.

## Security and responsibility boundary

Browsers and mobile apps must never access Product HTTP directly. CORS compatibility is not authentication. The product backend owns accounts, authorization, rate limits, audit, and token lifecycle and must not log plaintext tokens or message bodies.
