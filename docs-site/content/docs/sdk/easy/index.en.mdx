WuKongEasySDK is for applications that need realtime communication while keeping their own UI and product state. It connects to the WuKongIM Gateway over WebSocket JSON-RPC and reduces a first integration to four jobs: obtain connection material, initialize the SDK, subscribe to events, and send one message.

<Callout type="warn" title="Source alignment is not runtime verification">
  These tutorials were checked against exact release tags and source revisions in the four official repositories and against the current server JSON-RPC shape. This site has not issued an executable compatibility receipt for these EasySDK versions. The only client path with the site's complete scenario evidence remains the WuKongIMJSSDK Web golden path recorded under [Versions & Compatibility](/en/sdk/compatibility).
</Callout>

<Callout type="error" title="Current v3 cannot run this path directly">
  The Product Gateway does not currently support EasySDK's JSON-RPC CONNECT as a client integration path. This group therefore remains planned and stays out of search, the sitemap, and compatibility receipts. The material below explains the pinned source; it is not an availability promise for the current server.
</Callout>

“5 minutes” describes the shape of the path: install, initialize, listen, connect, and send. It is not a completion-time promise and does not include product accounts, authorization, group membership, offline synchronization, push, capacity, or release acceptance.

## What EasySDK owns

| Current EasySDK source provides | Your application still owns |
| --- | --- |
| WebSocket setup and JSON-RPC CONNECT | Product login, UID allocation, token issuance, and revocation |
| Sends to person or group Channels | Contacts, membership, permissions, content policy, and product receipts |
| Connect, disconnect, message, error, and related events | View state, rendering, persistence, and unknown-payload fallback |
| Send results and realtime receive | Offline sync, conversations, unread counts, push, and multi-device policy |
| Bounded automatic reconnect behavior | TLS/WSS, rate limits, capacity, observability, upgrade, and rollback evidence |

EasySDK is neither a chat UI nor a complete product backend. A successful `send` result means the server returned a result for that send. It does not prove that the peer received, displayed, or processed the message. Continue with [Messaging](/en/sdk/common-guides/messaging) and model send acknowledgement, realtime receipt, and product completion separately.

## One flow, different lifecycle owners

| Task | iOS | Android | Flutter | Web |
| --- | --- | --- | --- | --- |
| Create and initialize | Application-owned `WuKongEasySDK` instance | Process singleton via `getInstance()` + `init` | Application-owned singleton + `init` | One `WKIM` instance per identity/browser context |
| Listener ownership | Retain each `EventListener` token | Retain the same listener object | Retain the same callback reference | Pass the same function reference to `on` and `off` |
| Connection readiness | Enable send only after `onConnect` | Enable send only after `CONNECT` | Enable send only after the `connect` event | Enable send only after the `Connect` event |
| Account exit | Remove tokens and `disconnect` | Process/account owner removes listeners and disconnects | Remove listeners, `disconnect`, then `dispose` | `off`, then `destroy` |

A view can subscribe to state, but a view rebuild must not create a second connection. Each platform page identifies who creates and who cleans up the client without prescribing an application UI architecture.

## Prepare connection material first

A client must not grant its own identity. The user first signs in to your product. A trusted product backend then returns only the material needed for this connection:

```json
{
  "uid": "alice",
  "token": "short-lived-token",
  "websocketUrl": "wss://im.example.com/ws"
}
```

- `uid` is the stable user identity in your product.
- `token` is short-lived and revocable and grants no Product HTTP management authority.
- `websocketUrl` comes from deployment configuration or from a safe backend selection after calling `/route`.
- Production uses `wss://`, and its reverse proxy supports WebSocket Upgrade correctly.

Complete [Identity & Token](/en/sdk/common-guides/identity-and-token) first. In the default v3 Beta composition, storing data through `/user/token` does not automatically provide production-grade CONNECT validation. A deployment must wire a trusted verifier and prove rejection of invalid, expired, and revoked tokens.

<Callout type="info" title="Device categories are aligned; application code should still use enums">
  All four pinned versions use the same wire values as the [Device Flag dictionary](/en/api/dictionaries/device-flags): APP `0`, WEB `1`, and PC `2`. Mobile clients use `.app` / `APP`, while the browser defaults to WEB; do not copy integers into product code. Aligned device values do not prove the remaining protocol shapes are compatible: the iOS and Android tutorials still document their payload or field blockers.
</Callout>

<Callout type="error" title="Close sensitive SDK logging before production">
  The pinned source on all four platforms has logging paths that can expose tokens or payloads: some Android `v1.0.3` parse-error logs ignore `debugLogging`, the iOS `v1.0.3` JSON-logging setting does not actually gate output, and Flutter `v1.0.4` plus Web `v2.0.2` log complete requests or responses. Each platform tutorial records its exact boundary. Production remains blocked until the SDK is fixed, the built artifact is inspected, and redaction tests pass.
</Callout>

## Accept with Alice and Bob

Every platform uses the same minimal loop:

1. Obtain a UID, short-lived token, and WebSocket address separately for Alice and Bob.
2. Create two independent SDK instances or run two independent application processes.
3. After both clients observe a successful connection, have Alice send a text payload to Bob's person Channel.
4. On Alice, record the returned message ID, sequence, and Reason Code when exposed by that SDK.
5. On Bob, independently observe the realtime message event and deduplicate by `messageId`.
6. Send once from Bob to Alice and verify the reverse direction.
7. Remove listeners and disconnect when the page, Activity, Widget, or application exits.

This loop proves only connection and online messaging in the current environment. Offline recovery, conversations, push, multi-device behavior, reconnect boundaries, and production security require separate evidence.
