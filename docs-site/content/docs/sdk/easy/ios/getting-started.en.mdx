This page turns the legacy “5-minute integration” into an acceptance-friendly iOS loop. A product backend supplies connection material first; Alice and Bob then connect separately, exchange one message, and remove their listeners correctly.

The install → initialize → listen → connect → send learning order comes from the [legacy iOS EasySDK tutorial](https://docs.githubim.com/en/sdk/easy/ios/getting-started). That page supplies only the learning sequence; the method signatures, versions, and limits below are governed by the pinned `v1.0.3` tag, source revision, and distributed artifact.

<Callout type="warn" title="Evidence boundary">
  The example is aligned with the official [WuKongEasySDK-iOS](https://github.com/WuKongIM/WuKongEasySDK-iOS) `v1.0.3` source at revision `643848f85be70e3e3f2be22fceb86ae428b6cc38`; the published package is available on [CocoaPods](https://cocoapods.org/pods/WuKongEasySDK). This is a source-level tutorial, not runtime verification, and it does not expand the executable client scope under [Versions & Compatibility](/en/sdk/compatibility).
</Callout>

<Callout type="error" title="v1.0.3 JSON logging blocks production adoption">
  In this tag, `LogManager.logJsonData` does not enforce the `enableJsonLogging` or log-level guard and writes JSON-RPC requests and responses. Token fields are masked where recognized, but message payloads can still reach device logs. Setting `enableJsonLogging: false` is not sufficient. Before production, upgrade or fix the SDK and verify the Release artifact plus every log-collection path contains no sensitive data.
</Callout>

<Callout type="error" title="v1.0.3 still cannot pass the current v3 messaging loop unchanged">
  `v1.0.3` corrects the device wire values to APP `0`, WEB `1`, and PC `2`, so the default `.app` no longer classifies a mobile client as Web. The current server still represents SEND and RECV `payload` as Base64-encoded bytes, while this tag sends a JSON object directly and decodes a received payload as a dictionary. The unmodified client can therefore fail during send or receive parsing. The code below documents the public API and acceptance scaffold; first adopt an upstream release with the payload fixes or a reviewed fork, then run Alice and Bob.
</Callout>

## What you will have

- An iOS dependency pinned to `1.0.3`.
- One application-level client object that owns initialization, listeners, connection, and logout.
- A two-client acceptance scaffold for Alice's send result and Bob's realtime message event.
- Explicit follow-up work for tokens, WSS, offline recovery, and production acceptance.

## Before you begin

Prepare the following:

- Set the iOS deployment target to **iOS 15 or later**. The package manifest declares iOS 13, but the public `WuKongEasySDK` class in `v1.0.3` is marked `@available(iOS 15.0, ...)`, so this tutorial uses the more conservative API limit.
- Use an Xcode toolchain that supports Swift 5.7 packages.
- Run a WuKongIM single-node cluster or multi-node cluster whose `/readyz` is healthy and whose WebSocket Gateway is reachable from the device.
- Have the product backend return `uid`, a short-lived `token`, and `websocketUrl` separately for Alice and Bob.

Read [Identity & Token](/en/sdk/common-guides/identity-and-token) first. Never embed a fixed token in the app, source repository, logs, or screenshots.

## Step 1: install an exact version

### Swift Package Manager

In Xcode, choose **File → Add Package Dependencies** and enter:

```text
https://github.com/WuKongIM/WuKongEasySDK-iOS.git
```

Choose **Exact Version** and enter `1.0.3`. If the project owns a `Package.swift`, use an exact rule:

```swift
dependencies: [
    .package(
        url: "https://github.com/WuKongIM/WuKongEasySDK-iOS.git",
        exact: "1.0.3"
    )
]
```

### CocoaPods

```ruby
target 'YourApp' do
  pod 'WuKongEasySDK', '1.0.3'
end
```

Run `pod install`, then open the `.xcworkspace`. Choose one installation method, not both.

## Step 2: receive connection material from the product backend

Map the product-backend response into an application model. The real implementation obtains this over HTTPS and does not call Product HTTP management routes from the client:

```swift
struct IMBootstrap: Decodable {
    let uid: String
    let token: String
    let websocketUrl: String
}
```

`websocketUrl` may use `ws://` during local development. In production, the product backend selects and returns a `wss://` address.

## Step 3: own the client lifecycle

The following object registers listeners before connecting. On exit it removes each listener with the returned `EventListener`, preventing duplicate handling after a view is opened again.

```swift
import Combine
import Foundation
import WuKongEasySDK

@MainActor
final class EasyChatClient: ObservableObject {
    @Published private(set) var isConnected = false
    @Published private(set) var messages: [Message] = []

    private var sdk: WuKongEasySDK?
    private var listeners: [EventListener] = []

    func start(with bootstrap: IMBootstrap) async throws {
        stop()

        let config = try WuKongConfig(
            serverUrl: bootstrap.websocketUrl,
            uid: bootstrap.uid,
            token: bootstrap.token,
            connectionTimeout: 15,
            requestTimeout: 15,
            maxReconnectAttempts: 5,
            enableDebugLogging: false,
            logLevel: .error,
            enableJsonLogging: false // v1.0.3 still needs its source guard fixed.
        )
        let sdk = WuKongEasySDK(config: config)

        listeners.append(sdk.onConnect { [weak self] _ in
            Task { @MainActor in self?.isConnected = true }
        })
        listeners.append(sdk.onDisconnect { [weak self] info in
            Task { @MainActor in
                self?.isConnected = false
                print("Disconnected: \(info.code) \(info.reason)")
            }
        })
        listeners.append(sdk.onMessage { [weak self] message in
            Task { @MainActor in
                guard self?.messages.contains(where: { $0.messageId == message.messageId }) == false
                else { return }
                self?.messages.append(message)
            }
        })
        listeners.append(sdk.onError { error in
            print("WuKongEasySDK error: \(error.localizedDescription)")
        })

        self.sdk = sdk
        do {
            try await sdk.connect()
        } catch {
            stop() // Release the socket and listeners after timeout, auth, or network failure.
            throw error
        }
    }

    func sendText(to uid: String, text: String) async throws -> SendResult {
        guard let sdk, isConnected else { throw WuKongError.notConnected }

        let payload: MessagePayload = [
            "type": 1,
            "version": 1,
            "content": text
        ]
        return try await sdk.send(
            channelId: uid,
            channelType: .person,
            payload: payload
        )
    }

    func stop() {
        if let sdk {
            listeners.forEach { sdk.removeListener($0) }
            sdk.disconnect()
        }
        listeners.removeAll()
        sdk = nil
        isConnected = false
    }

    deinit {
        // The view or application lifecycle should still call stop() explicitly.
    }
}
```

Do not discard the anonymous closure passed to `onMessage`: `removeListener` needs the listener object returned during registration. The sample bounds connection and request handling at 15 seconds and calls `stop()` after failure; automatic reconnect is capped at 5 attempts, while the UI remains not ready. In SwiftUI, let a higher-level `@StateObject` own `EasyChatClient` and call `stop()` on logout or when the application-level owner exits.

### Hand ownership to the SwiftUI account root

The account or application root should own `EasyChatClient`; do not recreate it in a leaf view such as a message list. This compact example shows only the ownership handoff: `start(with:)` retains the 15-second connection/request bounds and failure cleanup above, send stays disabled until `onConnect` has set `isConnected`, and a real account exit calls `stop()`. Ordinary navigation does not tear down the account-level connection.

```swift
import SwiftUI

struct AccountChatRoot: View {
    let bootstrap: IMBootstrap
    let onAccountExit: () -> Void

    @StateObject private var chatClient = EasyChatClient()
    @State private var draft = ""
    @State private var startupError: String?

    var body: some View {
        VStack {
            if let startupError {
                Text(startupError).foregroundStyle(.red)
            }

            TextField("Message", text: $draft)
            Button("Send to Bob") {
                let text = draft
                Task {
                    do {
                        _ = try await chatClient.sendText(to: "bob", text: text)
                        draft = ""
                    } catch {
                        startupError = error.localizedDescription
                    }
                }
            }
            .disabled(!chatClient.isConnected || draft.isEmpty)

            Button("Sign out") {
                chatClient.stop()
                onAccountExit()
            }
        }
        .task(id: bootstrap.uid) {
            startupError = nil
            do {
                try await chatClient.start(with: bootstrap)
            } catch {
                startupError = error.localizedDescription
            }
        }
    }
}
```

This is not a chat UI architecture. The product Session owner must start each account root only once and call `stop()` when the account exits, the root owner is replaced, or the application explicitly ends that Session.

### Drive UI state from public events

| Public callback | UI state | Application response |
| --- | --- | --- |
| `onConnect` | Ready | Mark connected and enable send; a WebSocket open alone is not sufficient. |
| `onDisconnect(info)` | Not ready | Disable send immediately and, if useful, display the safe `info.code` and `info.reason`; wait for a new `onConnect` instead of creating a duplicate client. |
| `onMessage(message)` | Connection state unchanged | Deduplicate by `messageId` before updating the list; a realtime event does not prove offline synchronization is complete. |
| `onError(error)` | No automatic connection transition | Give the UI only a redacted, generic error and keep send gated by `isConnected`. Never log a token, payload, or complete JSON-RPC record, and do not assume an error enum the public source does not expose. |

When `connect()` throws or reaches the bound above, keep the root not ready and expose an explicit retry. Reuse the same trusted connection material, or refresh it through the product backend before starting again.

## Step 4: send the first message

The device flag is aligned in this release. First upgrade or patch the remaining payload contract above. After product login, obtain Alice's `IMBootstrap` and start the client:

```swift
let aliceBootstrap = try await productAPI.fetchIMBootstrap()
try await chatClient.start(with: aliceBootstrap)

let result = try await chatClient.sendText(
    to: "bob",
    text: "Hello from iOS EasySDK"
)
print("SEND result: \(result.messageId), seq=\(result.messageSeq)")
```

The returned `SendResult` means Alice received a server result for the send. Bob must independently observe the same product payload through `onMessage`; a local list insertion is not proof of peer receipt.

## Step 5: accept with Alice and Bob

1. Sign in as Alice and Bob on two devices or in two independent app processes.
2. Enable send only after both sides observe `onConnect`.
3. Have Alice send to the person Channel `bob`, retaining `messageId` and `messageSeq`.
4. On Bob, verify `fromUid == "alice"`, the Channel, and the payload in `onMessage`.
5. Send from Bob to Alice and prove the reverse direction.
6. On a real account exit or account-root replacement, call `stop()` and confirm that no duplicate listener or background connection remains; ordinary leaf-view navigation should not tear down the account-level connection.
7. Inspect the Release artifact and device logs to prove tokens, payloads, and complete JSON-RPC data are not recorded. Unmodified `v1.0.3` must not pass the production gate.

Unmodified `v1.0.3` is expected to expose a SEND-payload or RECV-payload failure in this loop; never hide that failure as local success. Even after a fixed build passes, this covers only the online loop. Design network recovery, offline synchronization, and the UI-ready state separately with [Reconnect & Errors](/en/sdk/common-guides/reconnect-and-errors).

## Troubleshooting

- **The compiler says the API requires iOS 15:** raise the deployment target to iOS 15; do not rely only on the lower platform declaration in `Package.swift`.
- **Connection never succeeds:** reach the returned WebSocket address from the device network and inspect proxy Upgrade, certificates, and `wss://`. Never return a container-only address to the phone.
- **Authentication fails:** refresh the short-lived token issued by the product backend. A successful `/user/token` call does not prove that the default deployment validates CONNECT tokens.
- **JSON still appears after disabling `enableJsonLogging`:** this is the known missing log guard in `v1.0.3`. Upgrade or patch the source and verify the Release artifact; configuration alone is insufficient.
- **SEND reports payload decoding failure, or RECV cannot build `Message`:** compare against the server's Base64 byte contract. The object-send and dictionary-receive paths in `v1.0.3` do not directly match current v3; upgrade or patch the SDK.
- **The device category is unexpected:** ensure product code has not overridden `.app`, then compare the wire values as APP `0`, WEB `1`, and PC `2`. `v1.0.3` fixes the enum; do not carry forward an older literal.
- **Messages appear more than once:** register listeners only once and merge realtime and later synchronized results by `messageId`.
- **Alice gets a send result but Bob sees nothing:** inspect Alice's send result, Bob's realtime connection, and the product's later offline-sync path separately. Do not automatically resend a message that may already be committed.
