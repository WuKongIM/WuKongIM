This tutorial is for developers integrating WuKongIM into a browser application for the first time. It uses framework-independent TypeScript, a loopback-only BFF, and separate Alice/Bob sessions to show the complete client lifecycle without requiring React or Vue.

<Callout type="warn" title="Understand the current scope first">
  The tutorial pins `wukongimjssdk@1.3.5` and the Chromium target from the compatibility snapshot. It can prove installation, connection, two-way persistent messaging, reconnect, and offline recovery in this sample. It does not automatically attest another browser, JavaScript SDK, runtime, or platform version.
</Callout>

## Who this is for

- You are building a browser chat, support, collaboration, or realtime-notification interface.
- You can provide UID, token, and connection material from a trusted backend.
- You want to prove an observable message loop before integrating a framework and application state.

If you have not decided between EasySDK and WuKongIMSDK, start with [Choose an SDK](/en/sdk/choose-sdk). This tutorial uses WuKongIMJSSDK; do not copy its method names to another SDK.

## What you will build

```text
Alice browser ─┐                         ┌─ Gateway WebSocket
               ├─ localhost BFF ────────┤
Bob browser ───┘   identity, route, sync  └─ WuKongIM single-node cluster
```

- The browser SDK manages connection, send, receive, and reconnect state.
- The BFF represents a trusted product backend, calls Product HTTP, and binds only to loopback.
- The WuKongIM cluster owns persistent-message order, commit, routing, and online delivery.

The browser never receives Product HTTP management capability. In a real product, replace the sample BFF with your backend login, authorization, and token lifecycle.

## Prepare for the first run

- A WuKongIM single-node cluster that passes `/readyz`.
- Node.js `>=20.11` and npm.
- Free ports `5001`, `5200`, and the loopback port used by the sample.
- The current repository source, including `docs-site/examples/javascript-web-quickstart`.

## How the first message travels

| Stage | What you do | What you should observe |
| --- | --- | --- |
| Install | Install the pinned SDK from the lockfile | Tests, TypeScript, and build checks pass |
| Identity | Alice and Bob each request a development identity from the BFF | The browser receives UID, temporary token, and WebSocket address |
| Connect | The SDK registers listeners and connects | Both sides independently become `connected` |
| Send | Alice sends Bob a persistent text message | Alice gets SENDACK; Bob gets a `realtime` event |
| Disconnect | Bob disconnects and Alice sends again | Alice still gets SENDACK; Bob gets no realtime event |
| Recover | Bob reconnects and synchronizes | Bob observes one `recovered` result |

SENDACK, online receipt, and offline recovery are separate outcomes. The tutorial makes each observable instead of reducing them to one ambiguous “send succeeded” state.

## Completion check

- You can explain why token and connection address come from a backend instead of browser constants.
- You can locate connection-status, message, and send-acknowledgement listeners in code.
- You can distinguish persistent commit, online delivery, and synchronized recovery.
- You know which production gates remain after the sample passes.

## Common failures

- **Installation fails:** return to the lockfile and Node.js version; do not bypass them with `latest`.
- **Identity creation fails:** check cluster `/readyz`, BFF output, and the Product HTTP address.
- **Connection remains pending:** inspect the `/route` result and Gateway WebSocket port.
- **The peer receives nothing:** check SENDACK, online events, and offline sync separately.
