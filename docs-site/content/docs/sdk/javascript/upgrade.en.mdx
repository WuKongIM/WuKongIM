This guide targets `wukongimjssdk@1.3.5` at source commit [`3c507ea3ebc08eae9d74fc1f76b150c380752008`](https://github.com/WuKongIM/WuKongIMJSSDK/tree/3c507ea3ebc08eae9d74fc1f76b150c380752008). It does not treat an npm semver increment as a compatibility guarantee.

<Callout type="warn" title="Treat a minor upgrade as a migration">
  Source changes from `1.3.0` to `1.3.5` include a protocol default and stream/event API changes. Do not update the version and publish immediately, and do not use a floating version to bypass a failure.
</Callout>

## 1. Freeze the pre-upgrade baseline

Record this on an isolated branch:

```bash
node --version
npm --version
npm ls wukongimjssdk
git status --short
```

Also preserve `package.json`, `package-lock.json`, the built-artifact digest, and at least one real scenario result. Assert connection, SENDACK, peer realtime receive, disconnect, and offline recovery separately. A page that merely opens is not an upgrade baseline.

Find every SDK call site:

```bash
rg -n "WKSDK|streamManager|streamNo|dataText|eventManager|dataJson|protoVersion" src test
```

Replace `src` or `test` with the actual source roots when needed. Inventory custom `MessageContent`, Provider callbacks, device values, runtime adapters, and listener cleanup too.

## 2. Install exactly and commit the lockfile

```bash
npm install --save-exact wukongimjssdk@1.3.5
npm ls wukongimjssdk
```

Confirm `package.json` does not contain `^1.3.5` or `~1.3.5`, then review package version, resolved URL, and integrity changes in `package-lock.json`. CI should use `npm ci` so an uncommitted or unreproducible lockfile fails closed.

The pinned installation path for this site's golden sample is:

```bash
npm --prefix docs-site/examples/javascript-web-quickstart ci --no-audit --no-fund
npm --prefix docs-site/examples/javascript-web-quickstart run check
```

## 3. Audit from the actual starting version

### `1.3.4 → 1.3.5`

For a direct upgrade from pinned `1.3.4` commit [`533a60cdd1b9229fc4a87d7d22b5b860eb4aa43c`](https://github.com/WuKongIM/WuKongIMJSSDK/tree/533a60cdd1b9229fc4a87d7d22b5b860eb4aa43c), the application-visible migration is `WKEvent.dataText?: string` becoming `dataJson?: any`. The `1.3.5` event constructor parses JSON immediately, so test valid JSON, schema mismatch, and non-JSON input. Renaming the field is not sufficient acceptance.

The `1.3.4` package also contained orphan declaration files that were neither exposed from the package root/export map nor backed by matching implementation. Their removal in `1.3.5` is package cleanup, not a root public-API deletion. See the [exact comparison](https://github.com/WuKongIM/WuKongIMJSSDK/compare/533a60cdd1b9229fc4a87d7d22b5b860eb4aa43c...3c507ea3ebc08eae9d74fc1f76b150c380752008).

### `1.3.0 → 1.3.5`

The application-relevant changes between pinned commits are:

| Change | Migration action |
| --- | --- |
| `WKConfig.protoVersion` default changed from `4` to `5` | Remove unevidenced overrides; test CONNECT, SEND/RECV, events, and reconnect with the target server. |
| `streamManager` and exported `Stream` were removed | Stop using old stream listeners; evaluate `eventManager` against the application protocol instead of mechanically renaming it. |
| `Setting.streamNo` and `Message.streamNo` / `streamId` / `streamFlag` were removed | Redesign every UI, storage, and dedupe path that used those fields. |
| `eventManager`, `WKEvent`, `EventType`, and event packets were added | Pair add/remove listeners and cover ordering, duplication, disconnect, and recovery with scenarios. |
| `WKEvent.dataText` became parsed `dataJson` | Remove string assumptions; validate the application payload schema and JSON failure policy. |
| `sdkVersion` became build-generated | It should match the installed package, but it is not a server compatibility negotiation result. |

Compare the source directly between the [`v1.3.0 commit 3747f44`](https://github.com/WuKongIM/WuKongIMJSSDK/commit/3747f44) and [`v1.3.5`](https://github.com/WuKongIM/WuKongIMJSSDK/commit/3c507ea3ebc08eae9d74fc1f76b150c380752008). If your starting version is older, inspect the exact lockfile version commit-by-commit instead of applying only this table.

### Event migration skeleton

```ts
import { EventType, type WKEvent } from 'wukongimjssdk';

const onEvent = (event: WKEvent) => {
  if (event.type === EventType.TextMessageContent) {
    const data = event.dataJson;
    // Validate data with the application schema before state management.
  }
};

sdk.eventManager.addEventListener(onEvent);

// At lifecycle teardown
sdk.eventManager.removeEventListener(onEvent);
```

The event API is not a field-for-field replacement for `streamManager`. TypeScript does not constrain the application shape of `dataJson`; validate it with your protocol schema and define behavior for missing, duplicate, or reordered start/content/end events.

## 4. Recheck configuration and Provider contracts

- Keep `uid`, `token`, and WebSocket routing behind a trusted backend; never put a development token in a frontend environment variable or static file.
- Whether using a direct address or `connectAddrCallback`, define timeout, failure, and route-refresh behavior.
- Align `syncMessagesCallback` sequence boundaries, direction, limit, and dedupe with the server/BFF contract.
- Re-run encode/decode round trips for every custom content type; unknown `contentType` must degrade safely.
- Pair every `addConnectStatusListener`, `addMessageListener`, `addMessageStatusListener`, and `addEventListener` with removal using the same reference.
- If using `config.platform`, test that runtime separately. This site's Chromium receipt does not cover uni-app, mini-programs, or WebViews.

## 5. Close the logging-leak gate

The `1.3.5` source emits logs not guarded by `config.debug`, including a decrypted receive packet and a retried send packet. Inspect the final bundle, not only application source:

```bash
npm run build
rg -n "消息内容|重试消息|console\.log" dist
```

Adjust `dist` for the project. The repository golden sample strips `console` through its builder. If production must retain logs, apply field-level redaction in a controlled fork or build step and prove that tokens, payloads, and keys do not reach logs.

## 6. Verify in layers

Run project static checks and unit tests first, then a real environment:

```bash
npm run check
npm run verify:acceptance
```

The second command is this site's golden-sample entry point; map it to an equivalent command elsewhere. Its report deliberately retains `production_readiness.result=not_assessed` and does not prove TLS, token verification, capacity, alerts, or rollback.

At minimum, test:

1. CONNECT with accepted and rejected tokens;
2. successful and rejected SENDACK without treating local `Promise<Message>` resolution as server success;
3. peer realtime receive, self-message dedupe, and custom-content decoding;
4. state, reconnect, offline sync, and duplicate control after network loss;
5. event start/content/end lifecycle and malformed JSON;
6. production bundles, sourcemaps, and browser logs for sensitive payload leakage.

## 7. Canary and rollback

Bind the SDK version, server revision, lockfile hash, browser/runtime, and scenario receipt into one release unit. Canary internally or to a small cohort while watching connection rejection, kicks, SENDACK reason codes, reconnect count, sync duplication, and frontend exceptions.

Rollback `package.json` and `package-lock.json` together, run `npm ci`, rebuild, and execute the old baseline scenario. If the upgrade also changed application event schemas, client storage, or server protocol, rehearse whether the old bundle can read the new state. Swapping a JavaScript file alone is not proof of rollback.

After the migration, record the exact combination in [Compatibility](/en/sdk/compatibility) and use the [API Reference](/en/sdk/javascript/api-reference) to recheck the adopted export surface.
