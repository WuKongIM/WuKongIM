A WuKongIM SDK manages the connection, message exchange, and protocol state between a client and the Gateway. You do not need to learn the wire protocol first. Start from your platform and outcome, prove a minimal loop, and then add production behavior.

<Callout type="info" title="Start your first integration here">
  If you have not selected a repository, begin with [Choose an SDK](/en/sdk/choose-sdk). Android `1.5.5`, iOS `1.1.1`, Flutter `1.7.9`, and HarmonyOS `1.1.7` now have full-SDK tutorials aligned to source/distribution artifacts, but none has a corresponding platform runtime receipt on this site. For a browser path carrying this site's executable scenario evidence, begin with [WuKongIMJSSDK Installation](/en/sdk/javascript/installation). The old UniApp SDK is deprecated; existing projects should use the [UniApp migration guide](/en/sdk/uniapp) to evaluate migration to `wukongimjssdk@1.3.5`. The four pinned WuKongEasySDK versions now have a server-side wire receipt for JSON-RPC CONNECT and online bidirectional messaging. Logging-security fixes are merged to each repository's `main` branch but are not in the current distributions; platform builds, device runs, and production token verification remain deployment-owned as well.
</Callout>

## What a complete integration looks like

1. **Choose and pin an SDK:** confirm the platform, required capabilities, and exact version instead of guessing from `latest`.
2. **Prepare product identity:** the user signs in to your product first; a trusted backend then returns the UID, short-lived token, and connection material.
3. **Initialize and register listeners:** configure the current user and attach connection, message, and send-status listeners before connecting.
4. **Connect and recover state:** wait for a real SDK connection; after reconnect, synchronize and deduplicate missing messages before marking the UI ready.
5. **Send and receive messages:** handle send acknowledgement, online receipt, and product processing as distinct outcomes.
6. **Complete the product experience:** add custom messages, conversations and unread state, mobile push, and multi-device policy as required.
7. **Finish release acceptance:** exercise failure and recovery paths, then separately close authentication, TLS, rate-limit, capacity, audit, and rollback gates.

Class names and callback shapes differ by platform, but these responsibilities and acceptance questions remain. The [SDK Common Guides](/en/sdk/common-guides) explain shared behavior in this order; each platform repository owns its exact API.

## What the Web tutorial proves

After [Installation](/en/sdk/javascript/installation) and the [Quickstart](/en/sdk/javascript/quickstart), you will observe:

- Alice and Bob each complete a connection;
- Alice receives SENDACK after sending, while Bob separately receives the realtime message;
- Alice can still commit a persistent message while Bob is disconnected;
- Bob recovers that message through synchronization after reconnect, without labeling recovery as realtime receipt.

This is more useful than a single “send succeeded” result because durable commit, online delivery, and offline recovery are genuinely different outcomes.

## Common questions

- **Which repository should I choose?** List the platform, minimum runtime, and required capabilities, then use [Choose an SDK](/en/sdk/choose-sdk) to compare them.
- **I need only connection and online messages:** start from the pinned [EasySDK tutorials](/en/sdk/easy) and use the [JSON-RPC support matrix](/en/api/client-protocols/json-rpc) to confirm the online boundary. Offline sync, push, production authentication, and platform execution remain separate work.
- **I need local messages, conversations, and unread counts on iOS:** begin with the [iOS installation and quickstart](/en/sdk/ios) for the `1.1.1` online path, then use the Common Guides. Offline and conversation recovery do not yet have site runtime evidence.
- **I need local messages, conversations, and unread counts on Android:** begin with the [Android installation and quickstart](/en/sdk/android) for the `1.5.5` synchronization gate and online path. Source/AAR alignment is not a device runtime receipt.
- **I need local messages, conversations, and unread counts on Flutter:** begin with the [Flutter installation and quickstart](/en/sdk/flutter) for the `1.7.9` singleton, synchronization, and send path. A macOS build is not an Android/iOS/macOS runtime receipt.
- **I need local messages, conversations, and unread counts on HarmonyOS:** begin with the [HarmonyOS installation and quickstart](/en/sdk/harmonyos) for the `1.1.7` HAR, deep-path API, synchronization, and send path. Source/HAR alignment is not a DevEco or device runtime receipt.
- **How should I integrate UniApp?** The official `WuKongIMUniappSDK` repository is deprecated and points to the JavaScript SDK. Follow the [UniApp migration guide](/en/sdk/uniapp) to remove the old package and pin `wukongimjssdk@1.3.5`, then validate each target runtime independently instead of projecting browser support.
- **The Web sample builds but does not connect:** follow the Quickstart checks for cluster `/readyz`, route address, Gateway port, and BFF output.
- **Sending succeeds but the peer shows nothing:** separate SENDACK, online receipt, and synchronized recovery, then diagnose each path.

## Security and responsibility boundary

An SDK does not own product accounts, authorization, or token issuance. A client must not receive WuKongIM Product HTTP management capability; those APIs belong behind a trusted product backend. The default v3 Beta Gateway also does not automatically turn stored tokens into production-grade identity verification. Android `1.5.5`, iOS `1.1.1`, Flutter `1.7.9`, and HarmonyOS `1.1.7` all carry raw-TCP, local-data/credential, queue-isolation, or Payload-logging blockers. Add authentication, TLS, network isolation, log redaction, local-data protection, rate limits, audit, and revocation before release.
