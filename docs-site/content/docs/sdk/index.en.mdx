SDK documentation now has two layers. Common Guides use current server and wire contracts to explain identity, connection, messaging, conversations, offline behavior, and multi-device boundaries every integrator faces. The JavaScript/Web golden path remains the only executable client sample eligible for a receipt.

## Goal and completion criteria

Developers first design cross-SDK behavior and then map it to one exact platform version. The JavaScript compatibility receipt still decides whether this build carries complete executable evidence. Publishing common guides does not verify Android, iOS, Flutter, UniApp, or HarmonyOS.

## Compatibility target

Phase 12 pins `wukongimjssdk@1.3.5` and records server revision, Node.js, and Chromium in the [compatibility snapshot](/en/sdk/compatibility). Phase 13 aligns common guides and protocol dictionaries with current source without expanding that platform-support scope.

## Prerequisites

- A WuKongIM single-node cluster that passes `/readyz`;
- Node.js `>=20.11` and npm for the golden sample;
- a product backend that owns accounts, policy, and the Product HTTP trust boundary;
- an understanding that the browser calls only the localhost BFF, never Product HTTP.

## Expected result

After the common guides, you have a reviewable client state machine and release-evidence checklist. When the golden path passes, Alice and Bob each connect; two-way messages show SENDACK separately from realtime receipt; a message committed while Bob is disconnected appears as sync recovery after reconnect.

## Troubleshooting

- **You are unsure which SDK to choose:** Phase 12 verifies only JavaScript/Web; do not infer support from another platform's planned menu.
- **A platform SDK exists but lifecycle design is unclear:** define behavior from Common Guides, then consult that SDK's exact-version API.
- **Versions differ:** return to the compatibility snapshot and use the lockfile instead of `latest`.
- **The sample connects but fails security review:** it is a development path without production token validation or HTTP business authentication.

## Security and responsibility boundary

An SDK does not own product accounts, authorization, or token issuance. The default v3 Beta Gateway does not automatically validate stored tokens. Production must add identity enforcement, TLS, rate limits, audit, and revocation.
