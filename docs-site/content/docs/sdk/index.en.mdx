SDK documentation now publishes one narrow but complete JavaScript/Web path: install an exact version, create development identity through a localhost BFF, connect to a real cluster, exchange persistent messages, and verify offline recovery after disconnect.

## Goal and completion criteria

From this page, developers should enter the published compatibility target instead of mistaking planned SDK menus for support. The compatibility snapshot's receipt status decides whether this build carries complete verification evidence. After the JavaScript/Web Quickstart, they should distinguish durable commit, realtime delivery, and offline synchronization.

## Compatibility target

Phase 12 pins `wukongimjssdk@1.3.5` and records server revision, Node.js, and Chromium in the [compatibility snapshot](/en/sdk/compatibility). This is not a support matrix for every platform or browser.

## Prerequisites

- A WuKongIM single-node cluster that passes `/readyz`;
- Node.js `>=20.11` and npm for the golden sample;
- an understanding that the browser calls only the localhost BFF, never Product HTTP.

## Expected result

When the golden path passes, Alice and Bob each connect; two-way messages show SENDACK separately from realtime receipt; a message committed while Bob is disconnected appears as sync recovery after reconnect.

## Troubleshooting

- **You are unsure which SDK to choose:** Phase 12 verifies only JavaScript/Web; do not infer support from another platform's planned menu.
- **Versions differ:** return to the compatibility snapshot and use the lockfile instead of `latest`.
- **The sample connects but fails security review:** it is a development path without production token validation or HTTP business authentication.

## Security and responsibility boundary

An SDK does not own product accounts, authorization, or token issuance. The default v3 Beta Gateway does not automatically validate stored tokens. Production must add identity enforcement, TLS, rate limits, audit, and revocation.
