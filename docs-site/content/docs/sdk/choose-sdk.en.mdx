Choose by runtime and required capabilities before choosing by repository name. The legacy documentation grouped clients into EasySDK and WuKongIMSDK families. This page preserves that useful discovery path, but no longer treats “chat app or non-chat app” as the only decision.

<Callout type="warn" title="Source availability is not verification">
  An official repository, a tutorial on this site, and an executable compatibility receipt are three different things. Android `1.5.5`, iOS `1.1.1`, Flutter `1.7.9`, and HarmonyOS `1.1.7` are aligned to source and their corresponding distribution artifacts, but none of those tutorials has a site runtime receipt. Only the JavaScript/Web golden path with `wukongimjssdk@1.3.5` currently has an executable verification entry point on this site.
</Callout>

## Write requirements before choosing a family

Family names are only discovery labels. They do not establish the capabilities of any repository or version. Prepare the following information, then inspect every candidate in the platform table individually:

| Question to answer first | What to verify |
| --- | --- |
| Where will the application run? | Browser, native system, or cross-platform framework, plus minimum runtime and build-tool versions |
| What must the first release do? | Required connection, messaging, conversations, unread state, offline recovery, push, multi-device, and custom-message behavior |
| Which capabilities does the product own? | Accounts, contacts, policy, business data, push devices, receipts, and UI state |
| What would prove adoption is safe? | The candidate repository's exact tag, installable artifact, included example, and your minimal acceptance result |

Inspect the README, APIs, examples, and changelog for the exact tag of each candidate before deciding. If your target is a browser and you want to run this site's existing sample first, use the WuKongIMJSSDK path marked as published below. That is the current tutorial entry, not a ranking of SDK families.

Before integration, inspect the repository README, examples, tags or releases when the repository provides them, changelog, LICENSE, and open issues. Pin an exact distribution version or artifact and record its matching source revision. Do not assume every repository has a tag; a default branch or `latest` is not a compatibility statement.

## Answer six questions before choosing

1. **Where will it run?** Record the browser, native system, cross-platform framework, and minimum runtime version.
2. **What must the first release do?** Mark required direct chat, groups, custom messages, conversations, unread state, offline recovery, push, and multi-device behavior.
3. **Which state belongs to the product?** Assign owners for accounts, contacts, policy, push devices, business receipts, and UI state.
4. **Which exact version will you pin?** Record the server revision, SDK tag or package version, runtime, and build tools together.
5. **How will you accept the minimal loop?** At minimum prove connection, send acknowledgement, online receipt, reconnect, offline recovery, and deduplication.
6. **What remains before release?** Review token verification, TLS, network isolation, rate limits, audit, capacity, upgrades, and rollback separately.

If a candidate repository cannot answer one of these questions, build a small proof first instead of expanding the choice directly into a production application.

## Follow this path after choosing

### EasySDK

1. Read the [EasySDK overview](/en/sdk/easy) and the relevant platform tutorial to inspect the pinned API, lifecycle, and adoption blockers.
2. Then read the [JSON-RPC support matrix](/en/api/client-protocols/json-rpc). The Product Gateway does not currently support CONNECT, so the tutorials are for source evaluation only. Do not begin production integration until the runtime supplies authentication, request correlation, and bridge mappings and passes end-to-end tests.

### JavaScript / Web

1. Run the locked TypeScript sample in [Installation](/en/sdk/javascript/installation).
2. Use the [Quickstart](/en/sdk/javascript/quickstart) to connect Alice and Bob and prove online messaging plus offline recovery.
3. Use the [Common Guides](/en/sdk/common-guides) to design identity, connection, conversations, push, and multi-device behavior.
4. Close release gates with [Platform Capabilities](/en/sdk/javascript/platform-capabilities) and [Integration Acceptance](/en/guide/integration/acceptance).

### iOS

1. Use [iOS Installation](/en/sdk/ios/installation) to pin CocoaPods `1.1.1` and review deployment-target and simulator-architecture limits.
2. Use the [iOS Quickstart](/en/sdk/ios/quickstart) in two independent processes to prove Alice/Bob connection, send acknowledgement, and online receipt.
3. Retain runtime evidence for your Xcode, device, and server revision instead of treating source/header alignment as this site's receipt.
4. Before release, close raw-TCP, TLS, RECV Payload logging, and production-authentication blockers, then separately verify offline, conversations, push, and background behavior.

### Android

1. Use [Android Installation](/en/sdk/android/installation) to pin JitPack `1.5.5`, revision `662a559a50d181540a0448454beb57e939b0c50e`, and the AAR checksum.
2. Use the [Android Quickstart](/en/sdk/android/quickstart) in two independent processes to prove the conversation-sync gate, local insert, SENDACK, and online receipt.
3. Retain a runtime receipt for your own AGP, JDK, device, system, and server revision instead of treating source/AAR alignment as Android execution evidence.
4. Before release, close raw-TCP/TLS, SharedPreferences-token, UID-SQLCipher-key, and Payload-logging blockers, then verify offline, push, background, and multi-device behavior separately.

### Flutter

1. Use [Flutter Installation](/en/sdk/flutter/installation) to pin pub.dev `wukongimfluttersdk 1.7.9`, the archive hash, and the application `pubspec.lock`.
2. Use the [Flutter Quickstart](/en/sdk/flutter/quickstart) in two independent processes to prove the conversation-sync gate, local insert, SENDACK, and online receipt.
3. Retain a runtime receipt for your own Flutter, Dart, target toolchain, device, and server revision instead of treating static analysis/macOS build evidence as Android, iOS, or macOS execution proof.
4. Before release, close raw-TCP/TLS, sqflite/SharedPreferences data protection, Payload logging, reconnect-generation, and account-queue isolation blockers, then verify offline, push, background, and multi-device behavior separately.

### HarmonyOS

1. Use [HarmonyOS Installation](/en/sdk/harmonyos/installation) to pin OHPM `@wukong/wkim 1.1.7`, the HAR hash, application `oh-package-lock.json5`, and API 20.
2. Use the [HarmonyOS Quickstart](/en/sdk/harmonyos/quickstart) in two independent processes to prove the conversation-sync gate, local insert, SENDACK, and online receipt.
3. Retain a runtime receipt for your own DevEco, HarmonyOS SDK, ohpm/hvigor, device, and server revision instead of treating HAR/source alignment as install, compile, or device execution proof.
4. Before release, close raw-TCP/TLS, RelationalStore `encrypt: false`, Payload/`hilog.info` logging, database-error propagation, and `sendingMsgMap` account-isolation blockers, then verify offline, push, background, and multi-device behavior separately.

### UniApp migration

1. Follow the [UniApp retirement and migration guide](/en/sdk/uniapp) to remove deprecated `wukongimuniappsdk`, install exactly `wukongimjssdk@1.3.5`, and retain the lockfile.
2. Import only from the `wukongimjssdk` package root and let `1.3.5` detect global `uni`, then `wx`, then native `WebSocket`; do not treat the currently broken explicit `config.platform` adapter path as a fix.
3. In HBuilderX, record build, connection, SENDACK, online-receipt, and recovery results separately for App, H5, and every mini-program target. A Chromium receipt cannot replace that evidence.
4. Let a trusted product backend issue identity and connection material. Unmodified `1.3.5` unconditionally logs plaintext Payload, so review a logging patch and close WSS, authentication, local-data, upgrade, and rollback gates before release.

### Other WuKongIMSDK platforms

1. Select an exact tag or package version from the official repository above and run its included example first. The UniApp repository is deprecated, must follow the migration path above, and is not a new-project candidate.
2. Map [Identity & Token](/en/sdk/common-guides/identity-and-token), [Initialization & Connection](/en/sdk/common-guides/initialization-and-connection), and [Messaging](/en/sdk/common-guides/messaging) to that version's API.
3. Retain your own execution evidence for connection, send acknowledgement, online receipt, and offline recovery.
4. Until this site publishes that platform tutorial, use the repository and your proof as the authority for platform APIs.

## Common mistakes

- **Choosing only from “chat app / non-chat app”:** applications in the same category can have very different local-data, conversation, and push requirements.
- **Treating a reachable repository as compatibility:** the tag, package, server version, and target runtime still need validation.
- **Copying APIs before designing identity:** UID, token, and policy must come from a trusted product backend; a client cannot grant them to itself.
- **Calling Product HTTP directly from a browser:** give the Web client only connection material and keep management APIs behind the trusted backend.
