Choose by runtime and required capabilities before choosing by repository name. The legacy documentation grouped clients into EasySDK and WuKongIMSDK families. This page preserves that useful discovery path, but no longer treats “chat app or non-chat app” as the only decision.

<Callout type="warn" title="Source availability is not verification">
  An official repository, a tutorial on this site, and executable compatibility evidence are three different things. Only the JavaScript/Web golden path with `wukongimjssdk@1.3.5` currently has an executable verification entry point on this site. Links for other platforms support evaluation and source discovery; they do not attest the same version tuple.
</Callout>

## Write requirements before choosing a family

Family names are only discovery labels. They do not establish the capabilities of any repository or version. Prepare the following information, then inspect every candidate in the platform table individually:

| Question to answer first | What to verify |
| --- | --- |
| Where will the application run? | Browser, native system, or cross-platform framework, plus minimum runtime and build-tool versions |
| What must the first release do? | Required connection, messaging, conversations, unread state, offline recovery, push, multi-device, and custom-message behavior |
| Which capabilities does the product own? | Accounts, contacts, policy, business data, push devices, receipts, and UI state |
| What would prove adoption is safe? | The candidate repository's exact tag, installable artifact, included example, and your minimal acceptance result |

Inspect the README, APIs, examples, and changelog for the exact tag of each candidate before deciding. If your target is a browser and you want to run this site's existing sample first, use the WuKongIMJSSDK path marked as published below. That is the current tutorial entry, not a ranking of SDK families.

## Answer six questions before choosing

1. **Where will it run?** Record the browser, native system, cross-platform framework, and minimum runtime version.
2. **What must the first release do?** Mark required direct chat, groups, custom messages, conversations, unread state, offline recovery, push, and multi-device behavior.
3. **Which state belongs to the product?** Assign owners for accounts, contacts, policy, push devices, business receipts, and UI state.
4. **Which exact version will you pin?** Record the server revision, SDK tag or package version, runtime, and build tools together.
5. **How will you accept the minimal loop?** At minimum prove connection, send acknowledgement, online receipt, reconnect, offline recovery, and deduplication.
6. **What remains before release?** Review token verification, TLS, network isolation, rate limits, audit, capacity, upgrades, and rollback separately.

If a candidate repository cannot answer one of these questions, build a small proof first instead of expanding the choice directly into a production application.

## Follow this path after choosing

### JavaScript / Web

1. Run the locked TypeScript sample in [Installation](/en/sdk/javascript/installation).
2. Use the [Quickstart](/en/sdk/javascript/quickstart) to connect Alice and Bob and prove online messaging plus offline recovery.
3. Use the [Common Guides](/en/sdk/common-guides) to design identity, connection, conversations, push, and multi-device behavior.
4. Close release gates with [Platform Capabilities](/en/sdk/javascript/platform-capabilities) and [Integration Acceptance](/en/guide/integration/acceptance).

### Other platforms

1. Select an exact tag from the official repository above and run its included example first.
2. Map [Identity & Token](/en/sdk/common-guides/identity-and-token), [Initialization & Connection](/en/sdk/common-guides/initialization-and-connection), and [Messaging](/en/sdk/common-guides/messaging) to that version's API.
3. Retain your own execution evidence for connection, send acknowledgement, online receipt, and offline recovery.
4. Until this site publishes that platform tutorial, use the repository and your proof as the authority for platform APIs.

## Common mistakes

- **Choosing only from “chat app / non-chat app”:** applications in the same category can have very different local-data, conversation, and push requirements.
- **Treating a reachable repository as compatibility:** the tag, package, server version, and target runtime still need validation.
- **Copying APIs before designing identity:** UID, token, and policy must come from a trusted product backend; a client cannot grant them to itself.
- **Calling Product HTTP directly from a browser:** give the Web client only connection material and keep management APIs behind the trusted backend.
