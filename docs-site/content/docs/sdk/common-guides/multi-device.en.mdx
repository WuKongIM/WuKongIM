One UID can have multiple device categories and active Sessions. Integrators first define which endpoints may coexist and which state is shared by UID, then map that policy to the SDK.

<Callout type="info" title="Cross-SDK behavior guide">
  This page is a **cross-SDK behavior guide** and does not claim identical multi-device APIs across platforms. Executable compatibility evidence still covers only the [JavaScript/Web snapshot](/en/sdk/compatibility).
</Callout>

## Goal and completion criteria

The product has a device registry mapping one stable UID to concrete installations, category, push token, credential status, and last activity. Connection conflicts, message recovery, and device removal each have testable rules.

## Protocol device dimensions

See complete [Device Flags and Device Levels](/en/api/dictionaries/device-flags):

- `APP=0`, `WEB=1`, and `PC=2` are client device categories.
- `SYSTEM=99` is server-reserved and unavailable to end-user clients.
- `device_id` distinguishes concrete installations in one category.
- `DeviceLevelSlave=0` allows same-category endpoints to coexist.
- `DeviceLevelMaster=1` declares same-category single-active conflict policy.

Device Level is not a client permission role. It participates only in conflicts for the same UID and `device_flag`; it does not express administrator, paid-user, or group roles.

## Current enforcement boundary

When token metadata is updated as Master, the user use case persists device metadata and schedules matching-category owner-local Sessions to close. Presence authority also fences Master conflicts for the same UID and category.

However, the default v3 Beta Gateway has no stored-token verifier, so CONNECT Sessions receive Slave level by default. Writing Master metadata through `/user/token` alone does not prove a later CONNECT enforces the intended conflict policy. Production must wire token verification together with device level and test it end to end across nodes.

## Suggested product policy

| Scenario | Recommendation |
| --- | --- |
| Phone, Web, and PC online together | Use different `device_flag` values and manage each concrete `device_id` |
| Multiple same-category devices allowed | Use Slave and make local message plus notification handling device-idempotent |
| Only one endpoint in a category | Backend issues Master; observe old Session closure after the new connection succeeds |
| Application reinstalled | Create a new `device_id`, revoke old credentials, and migrate or invalidate the old push token |
| User removes a device | Revoke credential, close online Session, then delete product device state |

## Which state is shared

- Channel messages and sequences are cluster-authoritative; every permitted device recovers from the same logs.
- Conversation, `read_seq`, deletion visibility, and activation state are UID-owned and normally shared across devices.
- Download progress, drafts, encrypted cache, and UI scroll position are device-local.
- Provider push token, OS permission, and background restrictions belong to a concrete device.
- Presence is an active owner route, not the product device registry or proof of the last reliable login.

When one device clears unread, another device may see the newer UID-owned badge floor during its next conversation sync. Clients allow newer server state to replace an older local projection.

## Messages and notifications

An ordinary durable message may deliver to multiple online Sessions. RECVACK is independent per Session, so one device's ACK proves nothing about the others. `msg.offline` supplies UID candidates rather than every offline device; the product device registry still decides per-device push.

## Logout and identity switch

Stop old-UID send admission, finish or cancel local tasks, close the old Session, clear old-UID message and conversation cursors plus push binding, then initialize the new UID. Do not replace identities concurrently inside one SDK singleton.

## Troubleshooting

- **Master devices still coexist:** verify that the Gateway verifier actually returns the persisted Device Level.
- **Different platforms replace each other:** inspect accidental reuse of one `device_flag`.
- **Old installation remains online after reinstall:** verify old token, device ID, and owner Session revocation and closure.
- **One device gets no push:** do not inspect UID presence alone; inspect concrete device token and product push policy.

## Security boundary

A device list is sensitive account data. Viewing or removing devices requires reauthentication, audit, and anti-automation controls. Never return another device's complete token, address, or Session identity.
