Offline message recovery and system notification solve different problems. Recovery reads message truth from WuKongIM committed logs. A notification only attempts to bring a device back to the application.

<Callout type="info" title="Cross-SDK behavior guide">
  This page is a **cross-SDK behavior guide** and promises no platform background-execution or push API. The executable disconnect, reconnect, and sync baseline is the [JavaScript/Web compatibility snapshot](/en/sdk/compatibility).
</Callout>

## Goal and completion criteria

Without a provider notification, the application still recovers every visible durable message after reconnect. Duplicate or delayed notifications cause no duplicate business action, and notification payloads never become message truth.

## Two independent paths

```text
ordinary durable message
  -> Channel durable commit
  -> client online: RECV
  -> client offline: sequence-based synchronization after reconnect

post-commit online-route decision
  -> msg.offline candidate webhook (best effort)
  -> durable product outbox
  -> APNs / FCM / another provider
  -> user opens app, reauthenticates, and synchronizes WuKongIM
```

WuKongIM currently does not call APNs, FCM, or another mobile-push provider directly. The product owns provider credentials, device tokens, silent/display policy, quiet hours, collapsing, retries, and provider receipts.

## Offline recovery

1. Persist the locally committed sequence for every Channel.
2. After reconnect and successful CONNACK, read committed messages from the known position.
3. Accept an empty page and continue according to `more`, range, or completion signals instead of guessing.
4. Realtime RECV and sync pages may overlap; deduplicate by message identity.
5. Commit messages and local cursor before updating UI and issuing receive feedback.
6. Promote connected state to ready only after recovery completes.

Only ordinary durable messages provide this recovery baseline. `SyncOnce`, request-scoped `subscribers`, and transient `NoPersist` do not produce the ordinary `msg.offline` effect. Command recovery uses separate CMD synchronization.

## What `msg.offline` means

- It reports **UID candidates** with no online route, not every offline device.
- If one UID has any online route, it may be absent. Per-device push therefore needs the product's own device registry.
- A person Channel candidate set may contain the sender; product policy filters sender and service identities.
- Large UID sets may use gzip plus Base64 `compress_to_uids`; receivers support both that and plain `to_uids`.
- The webhook queue is bounded, in memory, retry-limited, and not crash-replayed. Loss does not change SENDACK.

## Push receiver

1. Authenticate ingress through private networking, mTLS, or a controlled reverse proxy. The current sender has no built-in signature header.
2. Bound the body and allowlist `event=msg.offline`.
3. Persist `event + message_id + uid` into a product outbox, then return HTTP 200 quickly.
4. Asynchronously resolve device token, quiet-hour and presence policy, call the provider, and retry within bounds.
5. Carry only a safe summary and product locator in the notification, never a complete sensitive message or WuKongIM token.

## When a client opens a notification

Treat it as “state may have changed.” Restore product login, establish the WuKongIM Session, synchronize messages, then navigate to the target conversation. Provider message IDs, webhook arrival, and notification clicks never replace WuKongIM `message_id` or Channel sequence.

## Troubleshooting

- **Message synchronizes but no notification arrived:** inspect webhook admission, product outbox, device token, and provider; do not resend the message.
- **Notification arrives before the message is visible:** wait for durable sync and visibility checks; never trust notification text as truth.
- **One device receives duplicates:** deduplicate by message, UID, and provider device and use provider collapsing.
- **One offline device is absent from candidates:** the UID may have another online route; use product device state for per-device decisions.

## Security boundary

The push service is trusted product infrastructure, but it still receives neither Manager credentials nor direct message-storage mutation. Treat notification text as lock-screen-visible and minimize it by default. The default v3 Beta composition does not enable stored-token CONNECT verification; production must wire a trusted verifier and prove that invalid, expired, and revoked credentials are rejected.
