A Conversation is not another source of message truth. The current server constructs it transiently from one UID's membership directory and Channel committed state. The Channel log remains authoritative for messages.

<Callout type="info" title="Cross-SDK behavior guide">
  This page is a **cross-SDK behavior guide** and does not claim that every platform already exposes the same conversation API. Only the narrow recovery scenario in the [JavaScript/Web compatibility snapshot](/en/sdk/compatibility) is verified; confirm complete conversation APIs against your selected SDK version.
</Callout>

## Goal and completion criteria

The client separately maintains the conversation-list page cursor, per-Channel message pull cursor, badge floor, locally displayed position, and product-level end-user read state. These values never share one integer.

## Current conversation model

```text
UID membership directory
  + Channel committed head / last message
  + join / delete / retention visibility floors
  + UID-owned read_seq and activated_at
  -> transient Conversation
```

- `activated_at` participates in active-conversation ordering.
- `read_seq` is a badge floor, not a message pull cursor or peer read receipt.
- `deleted_to_seq` hides content before a sequence for the current UID; it does not delete the Channel log for other members.
- A disbanded Channel projects a delete. Temporary hydration failure is unresolved, not silent conversation loss.
- SEND, online receive, and message pull do not automatically mutate `read_seq` or `activated_at`.

## Client-local model

Store at least these values separately for every conversation:

| State | Purpose |
| --- | --- |
| `channel_id + channel_type` | Stable conversation key; direct-chat UI may use peer UID but never exposes the internal canonical person ID |
| `last_committed_seq` | Known Channel head used to detect gaps |
| `last_local_seq` | Position committed atomically to local storage and used to continue pulling |
| `displayed_seq` | Position shown by the UI; product policy may use it but it is not automatically server `read_seq` |
| `read_seq` / badge floor | Server unread baseline for the current UID |
| conversation cursor | Membership-directory pagination; it cannot replace a Channel message cursor |

## Synchronization and pagination

1. Page with the opaque conversation cursor; never parse or synthesize its fields.
2. An empty page does not necessarily mean completion. Only `done=true` completes one scan.
3. Retry `unresolved` keys within bounds instead of converting them to permanent deletes.
4. Recover each returned conversation with its own Channel sequence.
5. Realtime receive and sync can overlap; deduplicate by message identity while preserving Channel order.
6. Commit conversation cursor, messages, and local sequence through recoverable transactions.

Legacy `/conversation/sync` has different pagination and envelope semantics and fails the whole request when temporary hydration remains unresolved. Do not mix its raw-array behavior with canonical list `unresolved` and `done` semantics.

## Unread and read state

Unread is a projection, not an instantly consistent counter across devices. Update the badge floor with a monotonic sequence and make repeats idempotent. If the product needs “peer has read,” send a separate business receipt naming Channel and sequence; RECVACK is not that receipt.

Multiple devices normally share UID-owned conversation state and `read_seq`. Clearing unread on one device can change the badge returned to another device, so UI reconciliation must allow newer server state to replace older local state.

## Troubleshooting

- **Conversation exists but latest message is empty:** inspect Channel hydration, visibility floors, and temporary unresolved state.
- **Unread moves backward:** confirm monotonic updates and that a pull cursor was not written as `read_seq`.
- **Pagination loses conversations:** never infer done from “fewer than limit”; continue with the opaque cursor.
- **Direct chat appears twice:** inspect mixing of peer UID with internal canonical person-Channel ID.

## Security boundary

A conversation list can expose relationships and activity timing. Return only membership and messages observable by the current UID, and avoid complete UID or Channel samples in logs.
