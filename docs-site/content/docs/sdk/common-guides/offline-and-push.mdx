离线消息恢复与系统通知解决不同问题：前者从 WuKongIM 已提交日志恢复消息真相，后者只尝试提醒某个设备重新进入应用。

<Callout type="info" title="跨 SDK 行为指南">
  本页是**跨 SDK 行为指南**，不承诺任何平台的后台保活或推送 API。可执行的断开、重连和同步基线见 [JavaScript/Web 兼容快照](/zh/sdk/compatibility)。
</Callout>

## 目标与完成标准

应用在没有收到厂商通知时仍能通过重连同步恢复全部可见持久消息；收到重复或延迟通知时不会重复业务动作；通知 Payload 不成为消息真相。

## 两条独立链路

```text
普通持久消息
  -> Channel durable commit
  -> 客户端在线：RECV
  -> 客户端离线：重连后按 sequence 同步

提交后在线路由判断
  -> msg.offline 候选 Webhook（best effort）
  -> 业务接收端持久 Outbox
  -> APNs / FCM / 其他厂商
  -> 用户点击后重新认证并同步 WuKongIM
```

WuKongIM 当前不会直接调用 APNs、FCM 或其他移动推送厂商。业务系统拥有厂商凭据、设备 Token、静默/展示策略、免打扰、折叠、重试和厂商回执。

## 离线恢复

1. 本地持久保存每个 Channel 已提交 sequence。
2. 重连并完成 CONNACK 后，从已知位置读取已提交消息。
3. 接受空页；根据合同中的 `more`、范围或完成信号继续，而不是盲猜。
4. 实时 RECV 与同步页可能重叠，按消息身份去重。
5. 先提交消息与本地游标，再更新 UI 和发送接收反馈。
6. 恢复完成后才把应用状态从 connected 提升到 ready。

普通持久消息才能提供这条恢复基础。`SyncOnce`、请求级 `subscribers` 和瞬时 `NoPersist` 不产生普通 `msg.offline` 效果；命令恢复使用独立 CMD 同步。

## `msg.offline` 的真实含义

- 它表示没有在线路由的 **UID 候选**，不是每一台离线设备；
- 一个 UID 只要有任一在线路由，就可能不在候选中，按设备推送需要业务自己的设备表；
- person Channel 的候选可能包含发送者，业务策略应过滤发送者与服务身份；
- 大批 UID 可能使用 gzip + Base64 的 `compress_to_uids`，接收端必须同时支持普通 `to_uids`；
- Webhook 队列有界、内存内、有限重试且不做崩溃重放，丢失不会改变 SENDACK。

## 推送接收端

1. 在私网、mTLS 或受控反向代理上验证入口身份；当前发送器没有内置签名 Header。
2. 限制 Body，并允许列表检查 `event=msg.offline`。
3. 以 `event + message_id + uid` 持久化到业务 Outbox 后快速返回 HTTP 200。
4. 异步查询设备 Token、免打扰与在线策略，调用厂商并有界重试。
5. 通知只携带安全摘要和业务定位键，不携带完整敏感消息或 WuKongIM Token。

## 客户端打开通知

把通知视为“可能有新状态”的提示：恢复业务登录，建立 WuKongIM Session，执行消息同步，再导航到目标会话。厂商 message ID、Webhook 到达和通知点击都不能替代 WuKongIM `message_id` / Channel sequence。

## 失败诊断

- **消息可同步但没有通知**：检查 Webhook admission、业务 Outbox、设备 Token 和厂商，不要重发消息。
- **通知到达但消息暂不可见**：等待 durable sync 与可见性检查，不要信任通知正文作为真相。
- **同一设备多次通知**：按 message + UID + provider device 去重并使用厂商折叠能力。
- **某台离线设备没进候选**：UID 可能还有其他在线路由；改用业务设备状态决定按设备通知。

## 安全边界

推送服务是受信业务组件，但仍不能获得 Manager 凭据或直接修改消息存储。通知内容按锁屏可见信息处理，默认最小化。
