SDK syntax varies by platform, but integration usually follows the same path: prepare identity, initialize, connect, exchange messages, handle disconnects, then add conversations, push, and multi-device behavior. These guides explain the problem and completion signal at each step without requiring wire-protocol knowledge first.

<Callout type="info" title="Cross-SDK behavior guide">
  This remains a **cross-SDK behavior guide**, not a platform API reference. Take classes and methods from the repository version you pin after [choosing an SDK](/en/sdk/choose-sdk). The [JavaScript/Web snapshot](/en/sdk/compatibility) is the only receipt that executes a client artifact and browser; [EasySDK](/en/sdk/easy) separately has four wire fixtures and a real server-process E2E using the iOS/Android profiles.
</Callout>

## What you will have when finished

After this guide set, you will have a product-backend/client responsibility checklist, a client flow from login through offline recovery, and repeatable release cases. You should be able to answer:

- who creates, rotates, and revokes the UID, device identity, and token;
- when a TCP/WebSocket is merely open and when the session may send;
- what SENDACK, realtime RECV, RECVACK, and offline synchronization each prove;
- which layer owns conversations, unread state, push, and multi-device state;
- which failures may retry with the same idempotency key and which require identity or policy repair first.

## A releasable loop

```text
product login
  -> trusted backend issues session material
  -> discover Gateway ingress
  -> SDK CONNECT; inspect CONNACK separately
  -> recover and deduplicate missing durable messages
  -> expose an application-ready state to the UI
  -> SEND; retain client_msg_no and SENDACK separately
  -> RECV; process and then send RECVACK
  -> conversation/unread projection and mobile push converge independently
```

Do not treat “socket open” as the final readiness signal. Application readiness normally requires successful connection, still-valid identity, completed recovery, and merged local state.

## Release evidence

Retain repeatable evidence instead of one “message sent” screenshot:

1. connect with a named server revision, exact SDK version, and reviewed configuration;
2. exchange durable messages both ways and observe SENDACK separately from realtime receipt;
3. send while the receiver is offline, then recover from durable sync after reconnect;
4. deduplicate duplicate or overlapping results by message identity;
5. drive invalid credentials, denied policy, stale routing, network change, and server pressure into expected states;
6. prove logs, metrics, and error reporting contain neither tokens nor complete sensitive payloads.

## Security boundary

The default v3 Beta composition does not yet enable stored-token CONNECT verification, and Product HTTP has no general product-authentication middleware. These common guides do not present the development sample as a production identity design. Add authentication, TLS, network isolation, rate limits, audit, and revocation tests before release.
