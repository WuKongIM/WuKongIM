“Automatic reconnect” is not an infinite loop around connect. Reliable recovery first identifies the failed phase, then chooses route refresh, identity rotation, idempotency-key reuse, backoff, or stop.

<Callout type="info" title="Cross-SDK behavior guide">
  This page is a **cross-SDK behavior guide** and does not assume identical error classes across SDKs. The verified reconnect and offline-recovery baseline is the [JavaScript/Web compatibility snapshot](/en/sdk/compatibility).
</Callout>

## Goal and completion criteria

Every failure records a low-sensitivity phase, current application state, Reason Code or HTTP status, attempt count, and terminal action. The client has maximum backoff, a total recovery deadline, and visible degradation instead of creating a reconnect storm.

## Locate the phase first

| Phase | Typical evidence | Authoritative action |
| --- | --- | --- |
| Network / DNS / TLS | Dial, certificate, proxy, or WebSocket-upgrade error | Repair network and back off; no product send retry yet |
| Route discovery | HTTP status and endpoint-specific error | Reauthenticate or choose trusted ingress; never parse it as a Reason Code |
| CONNECT | CONNACK Reason Code or authentication timeout | Stop on auth rejection, refresh route on node drift, back off on temporary pressure |
| SEND admission | Local queue full or Session not ready | Wait for capacity or recovery; server commit has not begun |
| SENDACK | Reason Code plus `client_msg_no` | Classify by Reason Code; idempotent retry reuses the key |
| Message sync | HTTP status, item error, range, and `more` | Retain committed cursor and retry only the failed page or unresolved key |
| Product handler | Payload validation, database, or downstream failure | Use product idempotency and queues; never roll back Channel commit |

HTTP status, Product HTTP JSON, CONNACK, and SENDACK do not share one universal `{data,error}` envelope. Identify the phase first, then parse that endpoint or packet.

## Reconnect algorithm

1. Atomically mark the Session as unable to send and freeze new ordinary SEND.
2. Finish or safely cancel current receive work and preserve the last locally committed cursor.
3. Decide whether credentials remain valid from the close reason; authentication rejection does not auto-retry.
4. Rediscover ingress for network, stale-route, or node-mismatch failures.
5. Use exponential backoff with jitter plus dial timeout, maximum interval, maximum attempts, and total deadline.
6. After CONNECT, enter recovering rather than ready.
7. Synchronize missing durable messages, deduplicate, and commit the cursor atomically.
8. Publish ready only if this reconnect generation is still current, so an old attempt cannot overwrite a newer Session.

## Suggested retry classification

- `ReasonAuthFail`, missing membership, deny/allow-list rejection, ban, and disband: repair identity or product state before user/product retry.
- `ReasonNodeNotMatch`: refresh routing and reuse `client_msg_no`.
- `ReasonSystemError` or explicit temporary pressure: bounded backoff.
- Protocol-upgrade requirement: stop retrying and upgrade to a compatible client.
- Unknown Reason Code: preserve the raw number, fail closed, and never default to success.

See [Reason Codes](/en/api/dictionaries/reason-codes) for the complete classification. Enum presence does not mean every current path can emit a value.

## Idempotency and uncertain outcomes

If the connection closes after SEND but before SENDACK, the outcome is uncertain rather than failed. First search for the same product message during recovery. If a retry is required, reuse `client_msg_no`. Overlapping protocol attempts use distinct nonzero `client_seq` values so a late ACK cannot complete the wrong future.

When SENDACK succeeded but the receiver missed realtime delivery, do not create a new `client_msg_no` and duplicate the business message. The receiver recovers from the durable Channel log.

## Prevent reconnect storms

- One connection owner handles all network-change events.
- Coalesce foreground/background and OS network callbacks.
- Use full jitter and cap concurrent dialing per process and account.
- Increase delay during server maintenance or sustained 503 responses.
- Expose offline, recovering, and reauthentication-required states instead of an endless spinner.
- Application termination and explicit logout cancel timers and forbid later automatic connection.

## Observability

Record phase, Reason Code, SDK/server compatibility snapshot, backoff bucket, and terminal state. Never put UID, Channel ID, `client_msg_no`, address, token, or complete error payload into metric labels. Correlate detailed identity only in controlled, redacted request logs when needed.

## Release drills

Cover Wi-Fi/cellular change, DNS failure, TLS error, Gateway restart, route movement, invalid or revoked token, same-category Master conflict, lost SENDACK, empty sync page, sync overlap, and server backpressure.

## Security boundary

Infinite retry after authentication failure is both a security and capacity risk. When a token expires or is revoked, return to product login instead of probing multiple ingress points with the old credential.
