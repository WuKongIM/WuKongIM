This page explains how to migrate to the documentation's pinned snapshot. It does not invent a per-version changelog. The goal is to know the current state before the change, reproduce dependency and acceptance evidence afterward, and avoid blind downgrade over an unknown database or unresolved send queue.

<Callout type="warn" title="Evidence state">
  The target source and AAR were inspected, but this is **not Android runtime verification**. This site did not run your Gradle build, R8, database migration, device loop, or rollback drill. Those results are also absent from the JavaScript/Web `compatibility.json`.
</Callout>

## What version history can prove

The official [tag list](https://github.com/WuKongIM/WuKongIMAndroidSDK/tags) exposes source snapshots across `1.0.x`, `1.1.x`, `1.2.x`, `1.3.x`, `1.4.x`, and `1.5.0`–`1.5.5`. The target tag resolves to the pinned revision, but the `1.5.5` repository root does not carry a complete release changelog suitable for claims here.

### Exact `1.5.4` → `1.5.5` source diff

The official [`1.5.4...1.5.5` compare](https://github.com/WuKongIM/WuKongIMAndroidSDK/compare/1.5.4...1.5.5) pins both endpoints: `1.5.4` revision `65493fa7368636784981ff6b0ce8886769537d85` and `1.5.5` revision `662a559a50d181540a0448454beb57e939b0c50e`. That compare adds only seven lines to [`WKIMApplication.java`](https://github.com/WuKongIM/WuKongIMAndroidSDK/blob/662a559a50d181540a0448454beb57e939b0c50e/wkim/src/main/java/com/xinbida/wukongim/WKIMApplication.java):

- On `Build.VERSION_CODES.O` (Android 8.0) and `Build.VERSION_CODES.O_MR1` (Android 8.1), `isNetworkConnected()` now uses `getActiveNetworkInfo()` and the `NetworkInfo.isConnected()` result. The source comment limits the motivation to some VPN implementations whose active network lacks the `INTERNET` capability.
- Other Android 6.0-and-newer releases retain the `NetworkCapabilities.NET_CAPABILITY_INTERNET` path. The pre-Android-6.0 `NetworkInfo` path is unchanged.
- The branch checks the OS release, not the VPN transport. Non-VPN active networks on Android 8.0/8.1 therefore take the same fallback, so acceptance must cover both VPN and non-VPN cases.
- The compare has **no public Java signature changes**: no public class, method name, parameter, or return type is changed. That statement describes only this two-tag Java source diff; it does not replace AAR compilation, dependency, or runtime compatibility evidence.

This is a **source-diff fact, not runtime certification**, and it cannot be generalized to another VPN provider, device, or Android release. An application moving from `1.5.4` should add these targeted cases to its exact device/OS/VPN/server tuple:

| Dimension | Targeted case | Evidence to retain |
| --- | --- | --- |
| VPN | Connect, disconnect, and reconnect the target VPN separately on Android 8.0 and Android 8.1 | Whether `getActiveNetworkInfo()` exists and reports connected, `noNetwork`/`connecting`/final accepted states, VPN implementation and version |
| non-VPN | Exercise connected/disconnected Wi-Fi and cellular paths on Android 8.0/8.1 | Confirm that the release-gated fallback does not misclassify an ordinary active network |
| network switch | In an accepted session, switch Wi-Fi ↔ cellular and non-VPN ↔ VPN | Per-attempt status sequence, stale-callback fencing, duplicate connection, and message duplicate/loss signals |
| reconnect | Restore an outage or VPN tunnel, then wait for a new final accepted state | Reconnect latency, timeout, second `connecting`, `fail`/`noNetwork`, and activation epoch |
| message acceptance | After each network path is accepted, send one Alice → Bob text | Alice local insert, terminal `send_success` SENDACK, Bob single online receipt, and `clientMsgNO`/`messageID` correlation |

Include at least one non-Android-8.x control device for the unchanged capability path. A passing result remains evidence for that tuple only.

Two rules follow:

1. A tag proves that a source snapshot exists; **do not infer changes without release notes**.
2. Migration decisions come from the actual old/new application API diff, builds, database copies, and runtime scenarios, not semantic assumptions about the version number.

The legacy [Android integration guide](https://docs.githubim.com/zh/sdk/wukongim/android/integration) supplies only a useful checklist order—dependency, initialization, connection, messages, channels, conversations. Do not copy its floating `version`, old repository layout, or manually duplicated legacy dependencies.

## 1. Freeze the pre-upgrade baseline

Before editing the dependency, retain an auditable inventory:

- Current coordinate, resolved dependency graph, `gradle.lockfile`, and `verification-metadata.xml`.
- AGP, Gradle, JDK, Kotlin, compile/target/min SDK, and ABI tuple.
- Debug and minified Release commands/results.
- A redacted copy of the current user's database schema/migration index and retention/erasure requirements.
- Registered route, conversation/channel-sync, media providers, and listener keys.
- Alice/Bob connection, SENDACK, online receipt, offline sync, logout/account switch, and failure-path results.

Never export tokens, plaintext messages, or Product HTTP management credentials into logs or tickets.

## 2. Change only the exact dependency and refresh verification

```kotlin
dependencies {
  implementation("com.github.WuKongIM:WuKongIMAndroidSDK:1.5.5")
}
```

Resolve in a controlled environment and confirm that JitPack records revision `662a559a50d181540a0448454beb57e939b0c50e`. After refreshing dependency locks, regenerate and review `verification-metadata.xml` according to team policy. Require the AAR SHA-256 `5a797f1fac53c4fbcf015afca2686ecbeebd24b5e64dea598881b814b1322792`, then build in strict mode.

Dependency locking constrains version selection; checksum verification constrains downloaded bytes. Review both changes.

## 3. Correct API migration

Compile the caller against pinned [`MsgManager.java`](https://github.com/WuKongIM/WuKongIMAndroidSDK/blob/662a559a50d181540a0448454beb57e939b0c50e/wkim/src/main/java/com/xinbida/wukongim/manager/MsgManager.java) and [`ConnectionManager.java`](https://github.com/WuKongIM/WuKongIMAndroidSDK/blob/662a559a50d181540a0448454beb57e939b0c50e/wkim/src/main/java/com/xinbida/wukongim/manager/ConnectionManager.java):

| Old/risky shape | `1.5.5` target |
| --- | --- |
| Floating or older JitPack version | Exact `1.5.5` plus revision and checksum |
| `sendMessage(content, channelID, channelType)` | Deprecated; use `send(WKMessageContent, WKChannel)` / `sendWithOptions` |
| Caller needs control over the local message | Build `WKMsg`, then call `sendMessage(WKMsg)` |
| Guessed `removeOnSendMsgCallback` | Actual remover is `removeSendMsgCallBack(key)` |
| Guessed `WKConnectStatus.failed` | Actual constants include `fail`, `noNetwork`, and `kicked` |
| Enable send on the first `success` | READ synchronization requires `syncMsg` → `syncCompleted` → accepted `success` |

Remove every `addOn…(key, listener)` under the same key. Provider callbacks must complete once and be rejected when stale by an application activation epoch.

## 4. Reconcile dependencies and R8

The `1.5.5` AAR declares current SQLCipher, SQLite, Kotlin, and Curve25519 dependencies. Remove duplicated old versions copied from legacy material, then inspect the graph for conflicts.

The pinned AAR's `consumer-rules.pro` / `proguard.txt` is empty, even though the repository's own `proguard-rules.pro` contains SDK, xSocket, Curve25519, and SQLCipher rules. The application must own and review its rules and run at least:

- A Debug build.
- A minified Release build.
- Startup, initialization, connection, content reflection/custom types, SQLCipher open, SENDACK, and receive smoke.
- Mapping and missing-class/reflection warning inspection.

Rules present in source are not automatically inherited by consumers.

## 5. Treat database upgrade as a one-way boundary until proven otherwise

[`WKDBUpgrade`](https://github.com/WuKongIM/WuKongIMAndroidSDK/blob/662a559a50d181540a0448454beb57e939b0c50e/wkim/src/main/java/com/xinbida/wukongim/db/WKDBUpgrade.java) applies incrementally indexed SQL under `assets/wk_sql` and records progress. Pinned source publishes **no public downgrade contract**, nor a statement that an older SDK can read the newer schema.

Therefore:

1. Run upgrade first on a redacted database copy.
2. Verify messages, conversations, channels, unread state, and search.
3. Drill rollback with the pre-upgrade snapshot or an isolated fresh install; do not point an older SDK at an upgraded database without evidence.
4. Retain the only recoverable copy until schema and account-data policy are accepted.

This does not claim that rollback is impossible; it means an in-place downgrade is not safe without proof.

## 6. Re-run lifecycle and security acceptance

- `WKIM.init` receives application context, and route/conversation providers activate before connection.
- Connection reaches final accepted readiness within 15 seconds; timeout, kick, `fail`, `noNetwork`, and a second `connecting` are fenced.
- Alice local insert, terminal SENDACK, and Bob online receipt are recorded separately.
- All sends become terminal before `disconnect(false/true)`; same-process account switching remains blocked by `sendingMsgHashMap` risk.
- `setDebug(false)` / `setWriteLog(false)` are effective and the log chain contains no token or Payload.
- Raw `NonBlockingConnection` TCP, SharedPreferences token, and UID SQLCipher key remain production blockers.

## 7. Rollout and rollback decision

Start with a bounded cohort. Compare accepted connection rate, terminal SENDACK rate, message duplicate/loss signals, database migration failures, ANR/crash, and logging exposure. Expand only after the new build and runtime evidence passes.

A rollback must answer whether the APK/AAB is recoverable, server protocol remains compatible, old SDK can encounter the new schema, unresolved sends exist, and account databases have switched. If any answer is unknown, stop an in-place rollback and use a verified isolated recovery path.

## Completion checklist

- Dependency, revision, checksum, lockfile, and verification metadata agree.
- Code uses real `1.5.5` public APIs and deprecated migration is reviewed.
- Debug/minified Release, copied-database migration, and Alice/Bob scenarios have reproducible evidence.
- TCP/TLS, logging, credential, local-key, account-switch, and rollback risks remain visible.
- Source alignment and page publication are not described as an Android `compatibility.json` receipt.
