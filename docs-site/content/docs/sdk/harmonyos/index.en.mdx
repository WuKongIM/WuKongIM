`@wukong/wkim` is the full HarmonyOS NEXT SDK with local message, conversation, channel, and reminder state. Its process singleton, `WKIM.shared`, exposes the managers. The application supplies identity, a TCP route, and synchronization data sources; the SDK owns the protocol connection, HarmonyOS RelationalStore data, and event dispatch.

## What it owns in an application

| Module | SDK responsibility | Application responsibility |
| --- | --- | --- |
| `connectionManager()` | Connection, heartbeat, states, and protocol packets | Trusted identity, DNS/IPv4 `host:port`, and failure policy |
| `messageManager()` | Local insertion, text/media send, SENDACK, and new messages | Attachment upload, UI, business outcomes, and idempotency |
| `conversationManager()` | Recent conversations, unread counts, and synchronization entry | Complete `WKSyncConversation` mapping from a trusted backend |
| `channelManager()` / `channelMemberManager()` | Channel and member caches | User, group, and membership profile sources |
| `cmdManager()` / `reminderManager()` | Command and reminder data | Product command handling and remote synchronization APIs |

The first-message path needs only connection, conversation synchronization, and message managers. History, profiles, media, push, multi-device behavior, background execution, and upgrades are outside this quickstart's proof.

## The real first-connection gate

After installing providers and listeners, call `connection()`. A successful first connection reports:

```text
connecting → success → syncing → syncCompleted
```

- `success` is CONNACK success; recent-conversation synchronization follows it;
- there is no second `success` after `syncCompleted`;
- exact source still emits `syncCompleted` when `syncConversationCallback` is absent;
- the application must therefore require both its own provider-delivered flag and `syncCompleted` from the same one-shot activation before enabling send.

A real account must map conversations, recent messages, and version state from a trusted backend. An empty `WKSyncConversation` is only for brand-new test accounts in the bounded online loop.

## Root entry and deep imports

The HAR root `index.ets` exports only `WKIM`. The official demo obtains `WKChannel`, `WKMsg`, status constants, and `WKTextContent` from **deep import** paths below `src/main/ets/...`. This tutorial uses the paths actually shipped in the artifact, but they are not a stable root-export contract. Recompile on every upgrade instead of assuming those directories remain compatible.

## Current evidence and production blockers

Exact `1.1.7` source has these adoption boundaries:

- `@ohos.net.socket` `TCPSocket` uses raw **TCP** with no authenticated TLS;
- `WKLogger` defaults on and logs the complete outbound Payload; two direct `hilog.info` send traces still log channel/client identifiers when it is disabled;
- `WKConfig.debug` exists but is never read, so `debug = false` is not a logging control;
- decrypted messages enter `${uid}.db` with RelationalStore configured as `encrypt: false`;
- `sendingMsgMap` is not cleared by SENDACK or logout, while its resend flag is never enabled;
- database-open failures are logged and swallowed, so `await WKIM.shared.init(...)` can still fulfill;
- the package has only generated template tests, is unobfuscated, and contains `.DS_Store` files.

WKProto Payload protection does not replace TLS. Run the acceptance as one process, one UID, one connection, and one message; require a **process restart** after completion or any terminal path. Production still requires transport, logging, at-rest storage, database error propagation, queue cleanup, and account isolation to be fixed or explicitly accepted and validated.
