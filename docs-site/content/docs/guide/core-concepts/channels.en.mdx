A Channel is the core unit of message routing, ordering, and persistence. It is identified jointly by `channel_id` and `channel_type`; the same ID under another type is a different Channel.

## Business Channels

| Shape | Typical use | Important consideration |
| --- | --- | --- |
| Person Channel | Messages between two users | The server normalizes both viewpoints into a stable canonical ID |
| Group Channel | Group chat, community, or room | The business system maintains the group lifecycle and synchronizes membership |
| Custom Channel | Notifications, IoT, live interaction, and business topics | Type and value ranges need a stable business/client contract |
| Temporary recipient list | One request targets a bounded recipient set | Request-scoped membership does not replace a persistent group model |

A command Channel is a derived identity for internal compatibility and synchronization semantics. Applications should use supported Send/Sync capabilities instead of constructing internal suffixes.

## Two classes of Channel state

### Slot metadata

Slot stores Channel business metadata, subscribers, denylist, allowlist, ban/disband/send-ban flags, and `ChannelRuntimeMeta`. These values route by the Channel ID's physical hash slot to the current logical Slot Raft Leader.

### Channel message log

Channel runtime stores the sequence-ordered log. Authoritative metadata supplies Leader, Replicas, ISR, Channel Epoch, Leader Epoch, retention boundary, and write fence. Runtime replicas enforce those fences while appending, replicating, and advancing HW.

```text
Slot metadata: policy / members / runtime intent / migration fence
                              |
                              v
Channel runtime: ordered append -> replica progress -> committed HW
```

The Slot Leader and Channel Leader may be different nodes; neither can be inferred from the other.

## Send permission

Depending on Channel type and metadata, the message usecase checks sender ban, Channel ban/disband, subscription, denylist, allowlist, stranger policy, system users, and compatible agent/visitor relationships. The business service still decides who should be a member, when membership ends, and whether content is permitted.

## 100,000-member groups

Ordinary membership mutations are de-duplicated, chunked, and written under one monotonic mutation version. A single underlying membership command has UID-count and encoded-byte limits, so higher layers must operate in chunks. Post-commit fanout pages members, groups them by Presence Authority, and creates bounded delivery plans; it does not persist one message copy per member.

Observe these stages separately:

- Channel append and quorum-commit latency;
- member paging and authority resolution;
- online-delivery queues, owner push, and Session writes;
- CPU, network, and tail latency for hot Channels.

## Lifecycle and migration

A Channel runtime activates on demand and can checkpoint and unload when idle; messages remain durable. Leader transfer or replica replacement uses Slot-authoritative tasks, epochs, and write fences to drain the old Leader before committing the new placement. A node-local timeout cannot clear an authoritative fence.
