title: 集群与节点
description: 理解统一集群模型、节点、物理哈希槽、逻辑 Slot Raft Group 与 Channel 的关系。
---

WuKongIM 没有绕过集群行为的单机模式。一个节点的部署是**单节点集群**；增加节点改变副本和容量布局，但不会切换到另一套业务路径。

## 三层分布式职责

| 层 | 权威内容 | 典型变化频率 |
| --- | --- | --- |
| Controller | 节点成员、物理哈希槽表、逻辑 Slot 放置、集群任务与期望状态 | 低频控制面 |
| Slot | 用户、设备、频道策略、成员、会话、插件绑定和 Channel 运行时元数据 | 分片业务元数据 |
| Channel | 一个频道的有序消息日志、副本进度与提交高水位 | 高频消息数据面 |

Controller、Slot 和 Channel 使用不同的共识与状态边界。Controller Leader 不等于任一 Slot Leader，Slot Leader 也不等于 Channel Leader。

## 256 个物理哈希槽

业务键先通过 CRC32 映射到默认固定的 256 个**物理哈希槽**，再由 Controller 的路由表映射到某个**逻辑 Slot Raft Group**。逻辑 Slot Group 的数量由集群初始化配置决定，可以与 256 不同。

```text
UID / Channel key
       |
       v
CRC32 % 256 physical hash-slot fences
       |
       v
Controller route table -> logical Slot Raft Group -> observed Raft Leader
```

物理哈希槽是迁移和权威 fence；逻辑 Slot 是承载一个或多个物理哈希槽的 Raft Group。不要把“256 个哈希槽”解释成“256 个 Raft Group”。

## 节点是什么

一个 WuKongIM 节点可以同时运行客户端 Gateway、Controller voter 或 mirror、多个 Slot 副本、多个 Channel 副本、节点内运行时和本地 Pebble 存储。具体权威由当前 Controller/Slot/Channel 状态决定，而不是由客户端连接到了哪个节点决定。

客户端可以接入任一可服务的 Gateway。接入节点通过权威路由把元数据或消息工作送到正确节点；它不能因为目标在本机就绕过集群 fence。

## 意图与实时事实

Controller 记录期望的节点和副本布局。运行时是否能处理请求，还取决于实际 Raft Leader、term、配置 epoch、Channel epoch、ISR 和 write fence。诊断数据缺少这些实时证据时，应报告未知或过期，而不是用期望状态推断健康。

## 故障与扩缩容

- 节点失联不会自动证明数据已经安全迁走。
- Slot 或 Channel Leader 变化必须经过对应共识和 epoch fence。
- 缩容需要证明 Slot、Channel、任务、Gateway 与节点内运行时都已排空。
- 单节点集群缺少跨节点冗余；它保留集群语义，但不等于具备多副本容错。
