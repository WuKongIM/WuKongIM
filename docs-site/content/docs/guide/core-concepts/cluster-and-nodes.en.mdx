title: Clusters & Nodes
description: Understand the unified cluster model and the relationship among nodes, physical hash slots, logical Slot Raft Groups, and Channels.
---

WuKongIM has no standalone mode that bypasses cluster behavior. A one-node deployment is a **single-node cluster**. Adding nodes changes replica and capacity placement, but does not switch to another business path.

## Three distributed responsibilities

| Layer | Authoritative content | Typical change rate |
| --- | --- | --- |
| Controller | Node membership, physical hash-slot table, logical Slot placement, cluster tasks, and desired state | Low-frequency control plane |
| Slot | Users, devices, Channel policy, membership, conversations, plugin bindings, and Channel runtime metadata | Sharded business metadata |
| Channel | One Channel's ordered message log, replica progress, and committed high watermark | High-frequency message data plane |

Controller, Slot, and Channel use different consensus and state boundaries. The Controller Leader is not a Slot Leader, and a Slot Leader is not a Channel Leader.

## 256 physical hash slots

A business key is first mapped by CRC32 to one of the default fixed 256 **physical hash slots**. The Controller route table then maps that fence to a **logical Slot Raft Group**. The number of logical Slot Groups is chosen during cluster initialization and can differ from 256.

```text
UID / Channel key
       |
       v
CRC32 % 256 physical hash-slot fences
       |
       v
Controller route table -> logical Slot Raft Group -> observed Raft Leader
```

A physical hash slot is the migration and authority fence. A logical Slot is a Raft Group that hosts one or more physical hash slots. “256 hash slots” does not mean “256 Raft Groups.”

## What a node is

One WuKongIM node can run client Gateways, a Controller voter or mirror, multiple Slot replicas, multiple Channel replicas, node-local runtimes, and local Pebble storage. Current Controller/Slot/Channel state decides authority—not the node on which a client happened to connect.

A client can enter through any serviceable Gateway. The entry node routes metadata and message work to the correct authority; it cannot bypass cluster fences merely because the target appears local.

## Intent versus live fact

Controller records desired node and replica placement. Whether a request can be served also depends on the observed Raft Leader, term, config epoch, Channel epoch, ISR, and write fence. Diagnostics without those live signals should report unknown or stale rather than infer health from intent.

## Failure and scaling

- A missing node does not prove its data has been moved safely.
- Slot or Channel Leader changes must pass the corresponding consensus and epoch fences.
- Scale-in requires proof that Slots, Channels, tasks, Gateway, and node-local runtimes are drained.
- A single-node cluster has no cross-node redundancy. It preserves cluster semantics, but does not provide multi-replica fault tolerance.
