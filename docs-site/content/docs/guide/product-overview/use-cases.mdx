WuKongIM 适合需要大量长连接、频道内顺序、持久消息、离线同步或多设备状态的产品。它提供通信底座，但每种场景仍需要业务系统维护自己的身份、关系和业务流程。

## 场景与职责

| 场景 | 推荐使用的 WuKongIM 能力 | 业务系统仍需负责 |
| --- | --- | --- |
| 单聊与群聊 | 个人/群组 Channel、持久消息、多设备 Session、会话与离线同步 | 好友/群关系、内容审核、账号与产品权限 |
| 超大群与社区 | 大群标记、分页成员读取、有界 Fan-out、热点 Channel 观测 | 成员生命周期、分层推送策略、容量压测与热点治理 |
| 通知与系统消息 | 系统 UID、持久 Channel 消息、在线投递和离线补偿 | 通知偏好、模板、频控，以及 APNs/FCM 等移动推送 |
| 客服与坐席 | Agent/访客关系、Channel 消息、Webhook 或插件扩展 | 排队、分配、工单、服务质量和敏感数据治理 |
| 直播互动 | 自定义 Channel、高连接密度、按负载验证的在线 Fan-out | 房间生命周期、礼物/风控、降级和热点拆分 |
| IoT 与信令 | 稳定 UID/设备标识、双向 Channel、命令式实时消息 | 设备注册、命令授权、状态影子、超时与补偿 |
| AI 通信 | 持久基础消息、消息事件投影、插件或业务服务生成回复 | 模型调用、流控、内容安全、成本和完整结果持久化 |

## 两种常见集成形态

### 客户端消息产品

```text
client SDK <-> WuKongIM Gateway
     |               |
     +-> business API+-> Channel commit / sync / delivery
             |
             +-> accounts, relationships, policy, mobile push
```

客户端通过 SDK 保持连接并恢复离线消息；业务 API 管理账号、关系和策略。服务端 HTTP API 不应直接暴露给不可信客户端。

### 服务端事件与设备通信

业务服务或受信插件把事件发送到 Channel，客户端或设备消费已提交消息。业务动作需要自己的幂等键、超时、授权和结果状态，不能把 SENDACK 当作业务处理完成。

## 默认选择持久消息

需要重连恢复、审计或可靠重放时使用 durable 消息。普通非命令 `NoPersist` 只返回兼容成功，并不会实时投递；命令式 `NoPersist` 虽可进入实时投递，也没有 sequence 和离线恢复保证。不要把任一 `NoPersist` 分支用于必须可靠到达的业务事件。

## 上线前验证

1. 用真实的频道数、在线人数、消息大小、副本数和群规模建立负载模型。
2. 分别压测普通频道、热点频道、超大群 Fan-out、重连同步和移动网络抖动。
3. 验证 Gateway、Channel、投递、Webhook 与插件队列的拒绝和降级行为。
4. 记录 P99、错误率、积压、CPU、内存、磁盘和网络，不只比较平均 QPS。
5. 明确哪些结果由 SENDACK 保证，哪些仍需业务回执或补偿。

如果产品只需要低频后台任务、全局事务队列或离线批处理，而不需要连接、Channel 顺序或同步能力，专用任务队列或数据库可能更合适。
