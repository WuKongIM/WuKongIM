title: 部署方式选择
description: 按环境、升级责任、故障域和运维能力选择 Docker、Linux 或 Kubernetes 路径。
---

先选择谁负责构建、进程生命周期、网络、存储和升级，再选择具体部署工具。运行介质不会自动提供高可用或生产安全。

## 对比

| 维度 | Docker | Linux + systemd | Kubernetes（Beta） |
| --- | --- | --- | --- |
| 制品 | 从当前源码构建本地镜像 | 从当前源码构建二进制 | 从当前源码构建并固定镜像摘要 |
| 进程管理 | 容器运行时 | systemd | 编排控制器 |
| 状态 | 独立 Volume/磁盘 | 独立主机目录/磁盘 | 需要稳定持久卷设计 |
| 网络 | 显式端口和容器网络 | 主机监听与防火墙 | 需要 Service、入口和节点 Transport 设计 |
| 适用 | 已有容器平台的团队 | 熟悉 Linux 运维的团队 | 能维护 StatefulSet、PVC、Secret、网络策略和逐节点升级的团队 |

仓库根目录的 Compose 只用于开发和验证，不等于上表中的生产 Docker 方案。

## 决策问题

1. 所有节点能否固定到同一个提交和制品摘要？
2. 每个节点是否有唯一、稳定且可达的节点间地址？
3. 数据能否落在彼此独立、可监控的持久化设备上？
4. 谁负责 TLS、API 访问控制、Manager 隔离和密钥轮换？
5. 谁在 `/readyz` 失败时阻止切流并执行回滚？
6. 是否完成了备份恢复演练和目标负载容量测试？

如果其中任一问题没有负责人，选择更复杂的编排平台不会消除这个缺口。

## 单节点还是多节点

单节点集群适合开发、功能验证和明确接受单点故障的环境。它使用一个 Slot/Channel 副本，节点或磁盘故障会让服务不可用。

多节点集群用于跨节点复制和故障处理，但只有在节点、磁盘、电源或可用区真正独立时才形成有效故障域。三个容器共享一块磁盘不等于三个独立副本。

## 推荐

- **第一次评估**：使用仓库 Compose，验证三节点配置、就绪和观察面。
- **已有容器平台**：构建不可变镜像，另行维护生产编排、密钥和持久卷。
- **传统主机环境**：使用 Linux 二进制与 systemd，保持配置、状态和日志路径显式。
- **需要 Kubernetes**：使用已发布的 Beta 参考架构，但由平台团队审阅并维护最终 StatefulSet、PVC、Secret、网络和升级证据。
